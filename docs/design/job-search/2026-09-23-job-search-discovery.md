# 求职专业 Agent 设计访谈记录

状态：访谈完成，用户于 2026-09-23 确认共同理解；正式产品要求见 [已批准规格](../../specs/2026-09-23-weknora-job-search-design.md)。此文保留决策过程，不代替正式规格。

## 第一轮已确认

1. 产品归属：WeKnora 内的求职专业 Agent，而非独立产品。
2. 首批用户：中国大陆应届生。
3. 主线：针对岗位制作可信的定制申请材料，并管理整个申请过程；岗位发现和是否值得投递服务这条主线。
4. 跨端资料：通过 WeKnora 服务端同步，默认仅用户本人可访问；与空间管理及合规访问的关系仍待明确。
5. 对外动作：AI 可以发现、评估、起草、辅助填表、跟踪和准备面试；最终投递和发送由用户确认并操作。

## 第二轮已确认

1. 首版先面向中国大陆技术类应届岗位（开发、测试、数据、AI）。
2. 每位求职者使用一个单成员个人求职空间，求职资料与申请记录不混入学校或企业多人空间。
3. 岗位可通过粘贴链接、粘贴 JD、移动端分享导入；用户也可发出指令，让系统聚合招聘平台数据。
4. 最小闭环：基础求职档案 → 岗位评估 → 定制简历 → 网申问答草稿 → 用户确认投递 → 状态跟踪；求职信和面试准备按需生成。
5. Web、原生移动端、微信小程序的求职业务功能一致，三端共享权威数据，交互方式可适配设备。

## 第三轮已确认

1. 岗位聚合来源优先顺序：企业官方校招页 → 国家与高校就业平台 → 综合招聘平台；具体接入逐个核实开放方式和使用条件。
2. 用户指令默认触发一次性搜索。持续关注必须由用户明确开启，且可查看、暂停和修改条件。
3. 毕业年份、学历、地域、实习时长等明确硬条件给出带依据的“符合／不符合／待确认”；缺少资料不得视为符合。
4. 定制材料中的经历、技术栈、成果数字和证书以用户确认的资料为事实边界；缺口需标出，不能编造，关键主张应能关联依据。
5. 申请进度由用户手动更新为权威状态；可选的邮箱识别只提出附来源的变更建议，用户确认后才更新。
6. 可以逐端内部验证；正式版以 Web、原生移动端、微信小程序均完成完整求职闭环为验收门槛。

## 第四轮已确认

1. 产品不锁定毕业届别；记录预计或实际毕业时间，按每个岗位的届别要求判断。首批运营重点可放在 2027 届秋招，同时允许 2026 届等用户使用。
2. 首次建档可上传现有简历，也可通过逐步访谈；AI 抽取的事实须由用户确认。资料不完整仍可搜索，生成简历前提示补齐关键依据。
3. 跨来源岗位仅在高置信度时合并，并保留所有原始链接、来源和获取时间；不确定时并列展示。
4. 定制简历交付 PDF 和可编辑 DOCX，两者对应同一份已确认内容；修改后形成新版本，申请固定引用实际使用版本。
5. 面向公众托管的方向为基础求职流程免费，较高 AI 用量按明确额度收费；付费不影响岗位匹配分数或排序。

## 第五轮已确认

1. 搜索与筛选可在独立任务中进行；每个确定准备的岗位有独立求职申请，关联自己的 WeKnora Task，避免不同公司的材料和进展混在同一条长对话。
2. 职位链接无法取得全文时明确告知用户，由用户粘贴 JD 或手动补充；保留原链接，不把摘要冒充完整要求，也不绕过登录限制。
3. 三端编辑同一份结构化简历内容，支持预览并导出 PDF 和 DOCX；不要求在应用内直接编辑 DOCX 二进制文件。
4. WeKnora 账号是三端共同的身份权威；微信只作为登录或绑定方式，首次登录创建或关联个人求职空间，不产生独立的小程序资料库。
5. 站内待办是提醒的权威记录；原生推送与小程序订阅消息由用户选择开启，通知不展示公司、岗位或面试细节。

## 第六轮已确认

1. 申请有便于筛选的当前阶段，并保留不可覆盖的进展时间线；投递、测评、面试、Offer、拒绝等事件经用户确认后记录。
2. 申请固定保留创建时使用的岗位快照。来源更新或失效时展示差异和检测时间，由用户决定是否重新评估、重新生成材料。
3. 用户标记已投递时选择实际使用的材料版本及渠道；无法确认时明确标为版本未确认，面试准备不能假设对方看到了最新版本。
4. 用户可完整导出求职档案、申请时间线及材料，并删除个人求职空间中的数据；外部招聘平台已有内容由用户到该平台处理。
5. 两个参考项目的能力、评估规则、提示词和适配器选择性移植，保留许可证和来源记录；不整体搬入两套 CLI 工作流或使用受限制的商业品牌名称。

## 第七轮已确认

1. 先展示资格结果（符合／不符合／待确认），再展示技能、项目、地点和意向的分项匹配与证据；总分不得表述为获得 Offer 的概率。用户可以主动覆盖低匹配建议并继续申请。
2. 不同岗位或不同招聘批次建立不同求职申请，可相互关联；同一申请的测评和多轮面试留在其时间线。
3. 聚合来源必须提供原始链接、获取时间、足够完整的岗位要求和失败状态；仅有摘要时降级为待用户补充，不做确定性资格判断。
4. 建档、手动导入岗位、基本资格判断、申请跟踪和少量定制材料免费；持续扫描、批量评估和高用量生成消耗明确展示的额度。额度不足暂停新的收费执行，保留既有资料与申请记录。
5. 面向中国大陆应届生的公开托管版以中国大陆部署为目标，同时保留 WeKnora 自部署能力；具体模型、数据处理与运营条件在实施前核验。

## 第八轮已确认

1. 正式版针对网申问题生成、审阅和复制答案，用户在招聘网站填写与提交；跨站实时表单识别和自动填入留到后续。
2. 邮箱识别申请进度留到后续；正式版由用户手动记录进展、面试时间和提醒。
3. 个人求职空间沿用 WeKnora 的合规访问例外：管理员默认不可查看正文，例外访问须有理由、时限和审计，并向用户说明；删除遵守明确保留规则。
4. 手动导入岗位不限城市；主动聚合首批重点覆盖北京、上海、深圳、杭州，并展示实际覆盖来源和最近检查时间，不宣称全国完整覆盖。
5. 首要成功指标为完成的合格申请和材料可信度，辅以准备时间、错误资格判断率与后续面试反馈；不以海投数量衡量成效。

## 第九轮已确认

1. 岗位硬条件明确不符合时，用户仍可显式决定继续准备，但界面持续标注“不符合该岗位明示条件”，该申请不计入“合格申请”指标。
2. 模型默认只接收完成当前任务所需、已由用户确认的档案事实；证件号码等无关字段默认遮蔽。确需读取原始证明材料时，先告知用户具体用途。

## 当前仓库能力核查

以下是设计约束，不代表求职功能已经实现：

- Web 已有 Agent 对话、附件上传和产物下载等基础能力，见 `apps/web/src/chat/ChatRoutePage.tsx`。
- Taro 小程序已有任务/Agent 入口、附件上传及 PDF/DOCX 打开能力；审批只能安全拒绝，产物下载仍提示回 Web，见 `apps/miniprogram/src/features/execution/pages.tsx`。
- 原生移动端目前主要是部署、认证和账号运行时；`apps/mobile/src/screens/AuthorizedLandingScreen.tsx` 仍是 Task Office 占位页面。
- 因此“三端求职功能一致”属于新交付的正式版验收目标，尤其需要补齐原生端业务页和小程序产物、通知等能力。

## 实施前仍需核验的事实与参数

- 申请阶段、事件、撤回、纠错和重投的接口字典与幂等契约。
- 免费额度数值、超额计价和提醒频率，需要基于成本与用户试点决定。
- 每个拟接入岗位来源的实际开放方式、使用条件、数据完整性与可用性。
- 各端在真实设备完成正式版闭环的验收证据，特别是当前原生端和小程序的能力缺口。
- 首批试点规模与来源适配器清单。
- 中国大陆托管版的模型、数据处理、微信能力及公开运营条件。
