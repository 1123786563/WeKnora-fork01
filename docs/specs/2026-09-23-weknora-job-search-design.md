## 1. 产品定位

为中国大陆技术类应届生提供从建档、发现岗位、判断资格与匹配、准备可信申请材料、由本人投递，到记录笔试面试与结果的连续求职工作台。首批主动聚合重点覆盖北京、上海、深圳、杭州；用户手动导入不限城市。产品不把用户限定在某个毕业届别，而按各岗位要求判断。

它是 WeKnora 的求职专业 Agent，使用既有身份、单成员个人求职空间、Task、权限、预算、云端执行、产物和审计。Web、原生移动端、微信小程序在正式版都能完成同一业务闭环，使用同一服务端事实；每端界面可适应屏幕与系统能力。本规格的“正式版”是求职产品的公开验收门槛，不改变现有移动 AI Office 规格对其自身首版的范围定义。

核心承诺是帮助用户完成更可信、更符合条件的申请。岗位数量、AI 总分和投递数量均不能代替求职者的判断。

## 2. 正式版用户流程

1. **进入与建档**：用户通过统一 WeKnora 身份登录，创建或进入单成员个人求职空间。上传已有简历或接受逐步访谈，填写毕业时间、学历、项目、实习、技能、地点和意向。系统抽取的每一条关键事实须由用户确认，并标记来源；资料不完整仍可搜索。
2. **取得岗位**：用户粘贴链接、粘贴 JD、从移动端分享导入，或发出自然语言找岗指令。找岗默认一次性运行；用户可明确建立、暂停、修改持续找岗规则。搜索结果展示来源和最近检查时间。
3. **判断是否值得准备**：先对毕业届别、学历、地域、实习时长等明确条件显示“符合／不符合／待确认”，再解释技能、项目和意向匹配的证据及缺口。评分不是录用概率。用户可覆盖系统的低匹配建议；硬条件明确不符合时也可显式继续，但警示持续显示。
4. **建立申请**：用户选择一个具体岗位后建立求职申请，并关联独立 Task。申请固定当时用于判断的岗位快照；同公司不同岗位或不同招聘批次分别建申请。
5. **准备材料**：由已确认求职档案生成岗位定制简历与网申问答草稿。经历、技术栈、数字、证书必须可追溯；缺口须明示。用户在三端编辑同一份结构化正文、审阅预览，再导出内容一致的 PDF 和可编辑 DOCX。改动生成新材料版本。求职信和面试准备按需生成。
6. **本人投递**：用户把文件和答案用于招聘网站，亲自执行提交或发送。标记已投递时记录渠道、时间和实际使用的材料版本；未知版本明确标为“未确认”。系统不自动提交申请或发送邮件。
7. **跟进**：用户记录测评、笔试、面试、Offer、拒绝、撤回等事件及相关日期。当前阶段方便筛选，事件时间线保留历史。站内待办是提醒事实源；用户可选择原生推送和小程序订阅消息。
8. **结束或迁出**：用户可以导出求职档案、岗位快照、申请时间线和材料，再按保留规则删除个人求职空间数据。外部招聘平台已持有的资料须由用户在该平台处理。

## 3. 领域关系与权威数据

| 概念 | 边界与关系 |
| --- | --- |
| 个人求职空间 | 一位求职者的单成员 Tenant；所有私有求职资料、任务和计费归此空间。 |
| 求职档案 | 用户确认的事实与意向。导入文件和 AI 抽取建议不是自动生效的事实；修改保留来源与确认记录。 |
| 找岗任务 | 一次性搜索或持续找岗运行的 Task，产出岗位机会；不等于某份求职申请。 |
| 岗位机会／岗位快照 | 岗位机会可有多个来源观察；评估或申请引用固定时间的原文快照，来源更新不改写历史。仅高置信度重复才合并。 |
| 岗位资格判断／匹配评估 | 资格有符合、不符合、待确认三值；匹配解释与依据、模型版本、岗位及档案版本绑定。 |
| 求职申请 | 针对一个岗位及招聘批次的记录，关联独立 Task、岗位快照、材料版本与进展事件。 |
| 申请材料版本 | 一份已确认正文及其 PDF、DOCX 导出结果；投递后不可原地覆盖。 |
| 申请进展事件 | 由用户确认的投递、测评、面试、Offer、拒绝等事实；当前阶段由事件投影，纠错追加更正事件。 |
| 持续找岗规则 | 用户显式开启的条件和频率；关闭后不再后台搜索。 |

建议的申请阶段投影为：准备中、待投递、已投递、测评或笔试、面试、Offer、已结束。拒绝、主动放弃、撤回、重新投递、面试轮次等保留为带日期的事件与结束原因；同一岗位跨招聘批次的新申请另建记录。最终事件字典在实施契约中固定，不能仅依赖客户端标签推断。

关键不变量：

- User、Tenant 与 Task 的权限在服务端校验。三端缓存不是权威；一端修改后其他端读取同一版本。
- AI 只能建议档案事实、资格解释、材料与邮件状态；用户确认决定事实、投递与申请进度。
- 岗位硬条件不符合时不得通过其他分项高分掩盖；用户显式继续的申请也不计入“合格申请”指标。
- 岗位原文是外部不可信输入，只能作为数据参与判断，不得改变 Agent 权限或触发工具指令。
- 每次外部来源读取、评估、材料生成与投递确认保留其输入版本、时间、来源与结果；失败和未知不得展示为成功。
- 下载文件、投递记录与面试准备绑定确定材料版本；没有确认的实际投递版本时显示未知。

## 4. 岗位来源与评估

来源优先顺序：企业官方校招页、国家与高校就业平台、综合招聘平台。来源适配器上线前须核实开放方式、使用条件及可取得的内容；可用结果至少包含原始链接、来源、获取时间、岗位要求和明确的获取状态。首批来源清单与实际覆盖城市在发布前公布，不暗示全国完整覆盖。

链接需登录、被阻止、只返回摘要或内容不完整时，显示“需用户补充 JD”，保留原链接，不绕过登录限制，也不从摘要推断硬条件。职位有截止、过期或下架迹象时标记及复查；来源后来改变时展示与固定岗位快照的差异，用户决定是否重新评估和再生成材料。

跨来源去重以明确岗位编号、企业、地点、岗位和招聘批次等证据为基础；不确定时并列。每条展示保留来源列表及检查时间。持续找岗有用户可见的条件、频率、暂停开关和消耗预估；同一新岗位不反复提醒。

评估先处理招聘条件中的硬约束，再解释岗位要求与已确认档案的逐项对应、证据缺失和可迁移能力。资格不符合或待确认时不将高技能分数表述为“适合投”。硬条件不符合时用户仍可显式继续准备，但界面持续标注具体冲突。模型推断、网页事实和用户确认事实分别标识；模型输出接受结构化校验与人工复核入口。用户覆盖建议不会改写原评估。

## 5. 材料生成与校验

一份结构化材料正文作为三端共同编辑对象；PDF 和 DOCX 是同一版本的导出产物。用户在任何端修改正文后，导出新的不可变版本，旧版本仍可查看。小程序和原生端需能编辑内容、预览和取得两种文件，但无需实现 Word 二进制文件编辑器。

生成过程包括：从岗位快照提取要求、从已确认档案选择事实、起草、独立审阅、用户确认、导出和验证。审阅覆盖虚构经历/数字、关键词对应、可读性、过度模板化及针对岗位的真实相关性。PDF 应检查页面视觉与可提取文本；DOCX 应检查内容完整和可编辑性。仅当验证通过才标记该导出可用于投递；验证失败保留原因并允许修订。

一段网申问答草稿可由用户修改、复制，不能由系统直接提交。求职信和面试准备按需产出；面试准备优先引用用户确认的实际投递版本，版本未知时明示。

## 6. 三端产品面与共享服务

| 工作面 | Web | 原生移动端 | 微信小程序 |
| --- | --- | --- | --- |
| 建档、事实确认、求职意向 | 完整编辑与文件上传 | 完整编辑与文件上传/分享导入 | 完整编辑与文件上传/分享导入 |
| 找岗指令、持续规则、岗位评估 | 完整流程 | 完整流程 | 完整流程 |
| 申请、材料正文、版本比较、PDF/DOCX | 完整流程 | 完整流程，按屏幕适配 | 完整流程，按平台能力适配 |
| 投递确认、事件时间线、面试提醒 | 完整流程 | 完整流程，按需推送 | 完整流程，按需订阅消息 |
| 导出、删除与隐私说明 | 完整流程 | 完整流程 | 完整流程 |

客户端都通过同一组版本化求职服务接口访问个人空间的档案、岗位、评估、申请、材料、找岗规则和提醒；业务权限、任务运行、版本与额度以 WeKnora 后端为权威。三端可以共用合同、领域规则与 API 客户端，呈现层按设备实现。登录、空间切换、通知和文件下载必须沿用现有 WeKnora 安全边界；微信身份绑定到同一 WeKnora 用户，不生成第二份求职资料。

现状约束：Web 已有 Agent 对话、附件与产物基础；小程序已有任务和附件入口，但审批与产物下载尚不完整；原生移动端尚未具备 Task Office 业务页。因此正式版三端一致需要实测完整流程，不能以共享合同、构建成功或页面占位代替验收。

### 6.1 已选交互方向：C「对话指挥台」

用户于 2026-09-24 从三端交互原型的 A／B／C 方案中选择 C。三端以自然语言指令作为找岗主入口；Agent 的岗位结果与资格状态、匹配依据、待核实项、原始来源和可执行的下一步行动在同一对话上下文呈现。用户仍可通过清晰的独立入口完成档案确认、申请管理、材料编辑与版本比较、本人投递确认和进展跟踪，不必依靠聊天指令才能找到这些功能。

三端沿用同一业务状态与权威数据，Web 可以展示较宽的证据侧栏，原生移动端和小程序将证据收进结果卡片；窄屏不得因此隐藏硬条件冲突或来源。视觉使用现有 WeKnora TDesign 亮色主题 token。原型只确认信息架构和交互方向，演示岗位、分数、材料与按钮行为不能作为正式业务逻辑或验收依据。

## 7. 隐私、费用与运营

个人求职空间默认仅本人可访问正文。管理员只能通过现有有理由、限时、留痕的合规访问流程处理例外；隐私说明须解释这一点。默认只向模型提供完成当前任务所需、已由用户确认的档案事实，证件号码等无关字段遮蔽；确需读取原始证明材料时须先向用户说明具体用途。导出与删除入口清楚展示操作范围、保留规则及外部招聘平台内容不受本产品删除影响。原生缓存按用户与空间隔离；通知正文不包含公司、岗位或面试详情。

基础建档、手动导入、基本资格判断、申请跟踪和少量定制材料免费。持续扫描、批量评估和高用量生成在执行前显示额度与预估，超额时暂停新的收费操作，原有档案和记录可继续访问。付费不会改变岗位排序或匹配评估。具体免费数值和价格在成本试点后决定，不写入本行为规格。

公开托管版以中国大陆部署为目标，同时保留自部署。上线前需对实际岗位来源、模型、数据处理、微信能力、个人信息说明及收费流程分别完成运营核验；本设计不把未经验证的接入或合规条件视为已经满足。

## 8. 交付顺序与验收

内部可分阶段完成，但求职产品正式版只有在三端完整闭环后开放：

1. 建立统一领域合同、个人空间开通、档案事实确认及来源记录。
2. 建立手动导入和有证据的来源适配、岗位快照、资格判断、匹配解释与找岗规则。
3. 建立独立申请 Task、版本化材料、PDF/DOCX 验证、投递确认及事件时间线。
4. 补齐 Web、原生移动端、小程序的完整交互，完成隐私、提醒、额度、失败恢复和真实设备验收。

正式版验收情景：

- 2026 届用户面对仅限 2027 届岗位收到有依据的“不符合”；毕业时间缺失为“待确认”。
- 资格不符合的用户可以明确选择继续，但警示始终可见，申请不计入合格申请指标；原始证件号码不得因简历生成进入模型输入。
- 无法读取的职位 URL 明确请求用户粘贴 JD；岗位更新后历史评估及申请仍能打开原快照。
- 同岗多来源只在证据充分时合并；不同招聘批次可分别创建申请。
- AI 不能把缺失的实习、证书或量化成果写进简历；PDF 文本与版面、DOCX 内容及可编辑性均通过验证。
- 用户在 Web 修改材料，原生端和小程序看到同一版本；下载的 PDF/DOCX 对应同一内容，已投递版本不会漂移。
- 用户在外部平台投递第二版材料后，面试准备引用第二版；若版本未确认则明示未知。
- 重试找岗、材料生成或投递确认不会复制申请或重复记录进展；额度不足不会丢失已有记录。
- 另一用户不能访问该个人空间资料；推送不泄露敏感内容；导出和删除按明确规则执行。
- Web、iOS、Android、微信小程序分别在真实环境完成从建档到申请跟进的全流程。

首要效果指标是完成的合格申请及材料可信度，辅以准备时间、错误资格判断率和面试反馈；投递总数不作为主要成功指标。

## 9. 正式版之外

- 自动提交网申、自动发送邮件、跨招聘网站的实时表单识别与填入。
- 邮箱自动读取并推测申请状态；后续若接入仍只向用户提出有来源的建议。
- 在应用内直接编辑 DOCX 二进制文件、保证全国岗位完整覆盖、预测录用概率或保证获得 Offer。
- 两套参考项目的本地 CLI 数据目录、独立身份/账本和商业品牌直接并入 WeKnora。

## 10. 来源与移植边界

[ai-job-search](https://github.com/MadsLorentzen/ai-job-search) 提供建档、匹配、起草-审阅、简历版面及 ATS 文本层验证的可参考流程；[career-ops](https://github.com/career-ops-hq/career-ops) 提供结构化岗位评估、真实性线索、来源扫描、申请追踪与结果校准的可参考流程。二者均是本地 CLI 优先的实现；WeKnora 只选择适用能力移植到自身领域边界，并对实际复用的代码、提示词、模板及第三方资源逐项记录来源与许可证。对外采用 WeKnora 自有名称，不使用 career-ops 商业品牌。
