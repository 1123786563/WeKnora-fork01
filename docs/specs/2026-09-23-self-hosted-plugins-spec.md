# 自行托管插件与清单安装 Spec

日期：2026-09-23。状态：已确认；测试 seam 为管理员安装、成员个人授权到 Agent 远程 MCP 调用的应用边界集成验收。

## Problem Statement

希望自行开发 WeKnora 插件的开发者，目前只能交付远程 MCP 服务，再请空间管理员手工填写服务地址、认证和 Agent 配置。管理员无法通过版本化清单审阅并安装插件；成员没有统一的已安装插件与个人授权入口。远程服务若在同一地址悄悄增加工具或改变 schema，空间管理员没有可靠的升级确认点。现有 MCP 工具默认启用，无法满足新增写操作默认关闭的预期。

## Solution

开发者自行部署远程 MCP 服务，发布插件清单地址。空间管理员粘贴地址后，WeKnora 展示并核验插件版本、执行端点、工具、授权需求和读写分类，确认后在本空间安装。所有空间成员能发现插件；需要外部账号的工具由成员分别授权，独立能力无需账号。Agent 仅调用空间已接受版本中、当前成员有权使用且已启用的工具。新版由管理员审阅差异并手动接受；新增写操作默认关闭，可逐项启用并配置成员审批。

首个纵向案例为：成员连接自己的 Jira 账号，在对话中查询本人本周待办，并收到带 Jira 来源链接的结果。现有手工 MCP 接入路径继续可用。

## User Stories

1. 作为插件开发者，我想自行部署远程 MCP 服务，以便独立维护插件执行环境。
2. 作为插件开发者，我想发布可访问的插件清单地址，以便管理员仅凭地址发现可安装版本。
3. 作为插件开发者，我想为每个版本保留稳定的执行端点，以便旧版空间在升级前继续使用原版本。
4. 作为插件开发者，我想描述插件名称、用途、工具和授权要求，以便管理员了解安装后开放的能力。
5. 作为插件开发者，我想交付不依赖外部账号的工具，以便插件可提供独立 Agent 能力。
6. 作为插件开发者，我想交付需要个人连接的工具，以便成员使用自己的外部服务权限。
7. 作为空间管理员，我想粘贴清单地址预览插件，以便决定是否在本空间安装。
8. 作为空间管理员，我想在安装前核对实际 MCP 工具与清单声明，以便识别清单和执行服务不一致。
9. 作为空间管理员，我想看到工具的读写分类、scope、schema 和执行端点，以便判断授权范围。
10. 作为空间管理员，我想确认安装一个确定版本，以便空间不会因开发者发布新版而自动改变能力。
11. 作为空间管理员，我想停用已安装插件，以便阻止本空间后续调用。
12. 作为空间管理员，我想查看当前版本和候选版本差异，以便决定是否接受升级。
13. 作为空间管理员，我想手动接受新版，以便成员在确认后才使用新版本。
14. 作为空间管理员，我想让新版新增的写工具保持关闭，以便升级本身不会开放外部副作用。
15. 作为空间管理员，我想逐项启用写工具并设置是否要求成员审批，以便控制外部修改操作。
16. 作为空间成员，我想看到本空间已安装插件及其授权状态，以便知道哪些能力可以使用。
17. 作为空间成员，我想单独授权自己的 Jira 账号，以便 Agent 只在我的 Jira 权限内查询。
18. 作为空间成员，我想在授权过期或被撤销时重新授权，以便继续使用需要个人连接的工具。
19. 作为空间成员，我想撤销自己的个人授权，以便停止该插件使用我的 Jira 账号而不影响其他成员。
20. 作为空间成员，我想在对话中查询本人本周 Jira 待办，以便快速获得相关事项。
21. 作为空间成员，我想看到 Jira 事项的可打开来源链接，以便核对 Agent 的回答。
22. 作为空间成员，我想在写操作执行前审阅确定的目标和输入，以便决定批准或拒绝。
23. 作为空间成员，我想在插件不可达时得到明确错误，以便知道查询未成功。
24. 作为空间管理员，我想在清单或候选服务不可达时保留旧版，以便升级失败不影响已接受版本。
25. 作为空间管理员，我想在远程工具清单偏离已接受快照时阻止新增能力，以便服务更新不能绕过版本决定。
26. 作为空间成员，我想在未授权时无法借用其他成员的个人连接，以便个人外部数据不跨成员泄露。
27. 作为空间管理员，我想现有手工 MCP 服务继续工作，以便引入插件安装不会破坏已有集成。

## Implementation Decisions

- 使用既有领域语言：插件是版本化分发单位；应用安装是空间接受插件版本的关系；个人连接是成员对外部账号的授权；操作是通过连接进行的外部查询或变更。清单、安装和个人连接各有独立状态。
- 插件由开发者自行部署，WeKnora 作为远程 MCP 客户端调用；首版不托管插件代码，不通过本机进程执行插件。
- 管理员通过清单 URL 发起安装。安装前校验清单、版本端点及实际工具目录，展示给管理员审阅；清单中的权限声明不能单独构成执行授权。
- 清单至少表达稳定插件身份、版本、展示信息、远程传输与端点、工具能力快照、读写分类、个人授权和 scope 需求、内容摘要。具体 JSON 字段由实施计划确定，不在本 Spec 中固定。
- 空间安装固定在一个已接受版本；新版本需管理员审阅工具、schema、scope、端点和读写分类变化并手动接受。开发者须保留旧版端点可用；平台对远端代码无法物理锁定，但应在发现能力漂移时阻止未经接受的工具扩张。
- 已接受版本的工具列表与 schema 形成运行时核验基准。远程清单出现新工具、移除工具或变更 schema 时，执行不得自动采用候选定义；应提示管理员重新审阅。一个空间的漂移不得影响其他空间。
- 安装后所有空间成员可发现插件。需要个人连接的工具，在成员未授权时不得执行；成员授权按空间、成员和插件连接隔离。插件停用阻止后续调用，个人撤销只影响本人。
- 新增写工具默认关闭；管理员可逐项启用并配置调用时成员审批。审批针对确定的操作目标和输入，拒绝或超时不得派发写操作。无账号工具仍受空间启停及工具策略约束。
- 复用现有 MCP 服务管理、元数据、OAuth、工具注册、启停和审批能力，并为插件安装、版本快照、升级确认及成员可见性增加产品层。现有手工 MCP 服务保持兼容；迁移不得把未审阅的旧工具自动视为已批准插件版本。
- 首个案例采用个人 Jira 授权的只读查询。工具从已授权身份确定账号，不接受模型传入账号令牌或任意目标 URL；服务端限定本周范围并返回事项标识、标题、状态、截止日期与来源链接。
- 清单抓取、端点发现和执行遵守既有网络与租户边界。若使用现有 open-connector 共享运行时，须遵守已接受的共享运行时 ADR；本方案不要求迁入 open-connector，也不让插件直接获得其管理凭据。

## Testing Decisions

- 以**空间管理员安装到成员授权、Agent 实际调用远程 MCP 工具**的应用边界集成测试为主要验收 seam；使用受控的远程 MCP 测试服务和两名成员身份，只断言对外可观察结果，不测试内部函数调用顺序。
- 覆盖安装预览与确认、清单和远程工具不一致、插件停用、只读 Jira 查询、未授权引导、两名成员凭据隔离、个人撤销和授权过期。
- 覆盖旧版继续可用、候选版本差异、管理员接受升级、候选不可达、远程工具漂移，以及新版新增写工具保持关闭。
- 覆盖逐项启用写工具、成员批准、拒绝和超时；用有记录的测试服务确认拒绝或超时后没有外部写入。
- 覆盖无需账号的独立能力、空间成员可见性、跨空间隔离和原有手工 MCP 服务兼容性。
- 现有先例包括 MCP 元数据快照、OAuth 主体隔离、MCP 工具目录与启停、Agent 工具调用、AppConnector 的远程定义 pin 与集成测试；复用这些测试基础设施，在一个应用边界 seam 上验证完整用户行为。

## Out of Scope

- 公开第三方插件市场、平台代管插件代码、上传代码包、平台执行任意开发者进程。
- 空间共用 Jira 账号和空间连接；首个外部连接案例仅为成员个人授权。
- 本机 `stdio` 插件执行；首版使用后端可访问的远程 MCP 传输。
- 在首个案例中创建、修改或删除 Jira 工单；写操作只用于升级默认关闭和审批策略的验收。
- 改造 WeKnora 对外提供 MCP Server 的方向，或要求所有已有 MCP 服务立即迁移为插件。

## Further Notes

- 当前 MCP 服务已有个人 OAuth、工具发现和逐工具启停/审批，但未知工具默认为启用，且服务 URL 可变；这些是本 Spec 的明确差距，不能把现有手工配置视为满足版本治理。
- 已有 App、Installation、Connection、Action 领域模型与 open-connector 共享运行时 ADR 不应被新的插件术语覆盖。实施计划须明确插件安装和已有应用安装如何共用身份、授权和审计语义。
- 版本端点稳定是开发者交付约定；平台能核验可观察的工具目录、schema 与权限快照，不能保证开发者未在相同端点改变内部代码。产品界面应明确这一自托管信任边界。
- 正式实施前需固定清单协议、网络抓取限制、版本漂移处置、OAuth 身份映射、数据迁移与回退方案；这些不改变本文已确认的用户行为。
