# T10/T11 React Web live SSE chat evidence — 2026-09-12

## Scope

This is an isolated local browser run against a Lite Go backend and a local
OpenAI-compatible streaming model stub. It proves the React Web session,
message, transport, reducer and server-persisted assistant response path. It
does not prove a real third-party model, RAG retrieval, Agent tools,
continue-stream recovery, or native chat behavior.

## Environment

- Worktree: `codex/react-multiclient` at `190459c`
- React Web: `http://127.0.0.1:5175/` with `VITE_API_BASE_URL=http://127.0.0.1:18082`
- Backend: isolated Lite binary on `http://127.0.0.1:18082`
- Database/files: `/tmp/weknora-react-web-chat-20260912/`
- Model stub: `http://127.0.0.1:19998/v1` (loopback was explicitly allowed
  only in this isolated backend process)
- Browser: Codex in-app browser tab 1; the browser-use runtime could not load
  its Node native dependency on this host, so the same visible browser flow
  was completed through the connected browser control surface. This is
  recorded as a browser runtime limitation, not as Playwright evidence.

## Evidence sequence

1. The React login page was opened, an isolated account was registered, and
   login redirected to `/platform/knowledge-bases`. The page loaded the
   server-backed empty state; the browser scope key contained the API origin,
   user ID, tenant ID and `knowledge-bases` resource.
2. A remote `KnowledgeQA` model was created in the isolated tenant with base
   URL `http://127.0.0.1:19998/v1`. The server returned HTTP `201` and exposed
   only credential configured-state metadata in the response.
3. Navigating to `/platform/creatChat` and activating `New chat` created
   session `2072c0d5-6dd9-4167-be5c-4e426f02b256` through the React page. The
   route became `/platform/chat/<session-id>` and rendered the empty
   conversation.
4. Typing `hello from React Web SSE` and activating `Send` caused the React
   page to render the user message, then the streamed assistant answer
   `React live SSE answer`; the transient `Sending…` state disappeared after
   the stream completed and the send control returned to its enabled state.
5. The model stub log recorded a streaming `POST /v1/chat/completions` with
   `stream: true`; it received four incremental content chunks and the
   terminal completion. The backend SSE response contained the expected
   `agent_query`, incremental `answer`, and `complete` events.
6. A fresh authenticated `GET /api/v1/messages/<session-id>/load` returned
   HTTP `200`, exactly four rows for the direct control turn plus the React
   turn, with role order `user, assistant, user, assistant`; every row had
   `is_completed: true`, and the React turn's assistant content was exactly
   `React live SSE answer`.

## Boundary and limitations

The model response is intentionally a local stub, so this is real backend
and browser evidence but not third-party provider evidence. The direct
control turn was used to verify the same backend stream before the UI turn;
it is not counted as a second React UI interaction. The run did not exercise
RAG retrieval over indexed documents, Agent tool approval/OAuth/steer,
`Last-Event-ID` recovery, cancellation timeout, or a Wails/Expo runtime.
The Lite process logged the pre-existing `tenant_skills` table warning; it is
unrelated to the chat result and remains tracked in the migration ledger.
