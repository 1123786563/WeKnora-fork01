# T06/T17 React Web live backend evidence — 2026-09-12

## Scope

This is an isolated local browser run against a fresh SQLite database. It
covers the React Web login path, the knowledge-base create/update slice, and
the tenant settings read/update slice. It does not certify the full T06
knowledge-base journey, document processing, the remaining T17 settings
sections, or the complete browser role/OIDC matrix.

## Browser and backend evidence

1. Opening the React root displayed the real sign-in form. Creating the
   isolated account returned the UI message `Account created. Sign in to
   continue.`; the backend log records `POST /api/v1/auth/register` with
   HTTP `201`.
2. Signing in navigated to
   `/platform/knowledge-bases`. The page rendered the server-backed empty
   state and a scope key containing the API origin, user ID, tenant ID, and
   `knowledge-bases` resource. The backend log records `POST
   /api/v1/auth/login` HTTP `200`, `GET /api/v1/auth/me` HTTP `200`, and
   `GET /api/v1/knowledge-bases?creator=all` HTTP `200`.
3. Submitting `React live knowledge base` created a real document knowledge
   base. The UI then rendered one returned row with `Open documents`, `Edit`,
   and `Delete`; the backend log records `POST /api/v1/knowledge-bases` HTTP
   `201` and a server-generated ID.
4. Editing the row to `React live knowledge base updated` returned to the
   list only after the server response. The backend log records `PUT
   /api/v1/knowledge-bases/<server-id>` HTTP `200`, followed by a fresh list
   request that rendered the updated name.
5. Direct navigation to
   `/platform/settings?section=tenant` loaded the active tenant from the
   shared `auth.me` response. The visible page showed tenant ID `1`, status
   `active`, the owner scope, and editable name/description controls.
6. Saving `React Web live settings current` updated the description. The
   backend log records `PUT /api/v1/tenants/1` HTTP `200` with the exact
   description, and the React page rendered the returned value and updated
   server timestamp.
7. Direct navigation to `/platform/chat/session-1` kept the authenticated
   React route mounted and rendered the server result `session not found`
   instead of a blank page. This is a deep-link/error-state observation, not
   a claim that a nonexistent session was created.
8. The Web bundle's `/embed/channel-1` path rendered the explicit
   `Embed must use its isolated entrypoint` guard. The separate Embed Vite
   entry at `http://127.0.0.1:5176/embed/channel-1` loaded independently and
   rendered `Unable to start chat` / `Missing embed token.` without redirecting
   to the authenticated Web login. This confirms entrypoint isolation and
   fail-closed behavior for an absent token; a valid third-party token/session
   remains unverified in this run.

The browser screenshot captured after step 6 showed the `Tenant information`
panel, the server-owned tenant name, the saved description, and the `Read` /
`Save` capability labels. No production account, database, file, or provider
credential was used.
