# Serialize Agent security decisions with new work admission

## Context

Issue #64 and the approved Agent Marketplace specification require a revoked Release or an exactly locked revoked dependency to block new Task/Run work while retaining historical data. The current AgentRun admission transaction serializes on the session row, while security revocation serializes on the tenant row. A standalone verdict read before admission can race a revocation, and reversing the lock order can deadlock. Workbench also preserves idempotent replay of an existing request. AgentQA has quick-answer and agent modes, persists uploads before its current entry point returns, and has no durable turn admission record that revocation can enumerate.

## Decision

New use of an adopted Agent is admitted only by a short transaction guarded by the source tenant's security lock. The transaction resolves the published local Variant to its fixed Release, rejects ambiguous Variant mappings, evaluates that Release and its exact dependency lock using the revocation rows on the same transaction, and commits the durable Run or chat-turn admission before any external work. The tenant guard is acquired before session, request, Variant, or Run rows. For shared Agents, source-tenant and session-tenant guards are acquired in ascending tenant-ID order before session/share/Variant/claim rows. Existing admitted-request replay remains available and does not become a new admission. Variant admission binds both the local Agent ID and the server-derived immutable `LocalAgentVersionID`; stale, mismatched, unpublished, or ambiguous mappings fail closed, and the chosen Version is frozen in the Run or claim.

AgentQA receives a durable, tenant-scoped turn claim uniquely keyed by `(session_tenant_id, session_id, owner_id, request_id)`. The claim records a canonical request hash, server-generated assistant and user message IDs, source tenant, session tenant, session, nullable local Agent Version and pinned Release, lease owner/expiry, monotonic fencing generation, and lifecycle state. For adopted Agents both Version and Release are required and bound to the published Variant; for a confirmed non-Marketplace Agent both are NULL and execution retains the authorized current `CustomAgent`. Claim creation and assistant placeholder insertion occur in one transaction, so Stop always has a concrete message identity. A blocked decision creates no claim, message, upload, live-run slot, or SSE response. Claim creation is the admission point; uploads, parsing, streaming, Redis, and model calls happen after the guard transaction commits. The claim uses the existing `X-Request-ID` header as its request key and hashes all validated execution-affecting request fields; a retry is idempotent only when it reuses that ID and hash. Same-key/different-hash conflicts. AgentQA executes only a newly created claim; an active or terminal replay returns HTTP 409 with the existing assistant message ID/state before SSE and side effects, and a later explicit turn uses a new request ID. Every continuation, user-message write, assistant-message update, and final write checks active generation and unexpired lease and writes the message in the same transaction. Since `types.Message` has no tenant or owner columns, the repository verifies its parent Session under lock using the claim's session tenant/session/owner, then binds the Message by ID, session, request ID and role and updates only mutable message fields. `GetForHandler` returns terminal state/reason as well as active state and reports lease validity separately; it cannot hide a cancellation behind an active-state filter. A prior lease/read check cannot authorize a later unfenced write. Lease expiry fences the old handler and terminalizes an orphan placeholder rather than restarting work. Handler completion uses a lease-owner-fenced terminal transition. User Stop uses a distinct `CancelByOwner` operation: it finds a source-tenant hint without a lock, acquires source/session tenant guards in ascending order, then re-reads and revalidates session tenant, session, owner, and exact assistant message under lock; no handler lease is supplied by the caller. Revocation with `allow` leaves earlier claims and placeholders active. Revocation with `cancel` appends its audit, marks matching active claims cancelled, and terminalizes their bound assistant placeholders in the same guarded transaction; a failed placeholder update rolls back the revocation and audit. The owning AgentQA handler observes durable state and cancels the exact message's generation context. The handler stops scheduling external work on terminal state, lease loss/expiry, or a claim-read failure; polling recovers a lost stop notification while reads succeed.

Run cancellation is scoped to the exact published Variant identity `(tenant_id, local_agent_id, local_agent_version_id, release_id)`, including retired Variants. New Runs pin Version and Release in immutable sidecar columns; the existing JSON Run snapshot remains byte-stable. A revocation committed with `cancel` also commits a durable `run_cancellation_state='pending'` obligation. Immediate processing and the periodic startup reconciler acquire the tenant guard, recheck the tenant-scoped ledger row under lock, then apply exact Run/event/session-slot cancellation and update the cumulative `canceled_run_count` plus obligation state to `complete` in the same transaction. A crash before processing leaves the obligation pending for retry; a second process that finds `complete` does nothing. Prior nonzero cancellation counts are preserved. A partial unique index on `(tenant_id, local_agent_id)` for non-NULL local Agent IDs, immutable-identity triggers, an insert trigger that rejects older unpinned Marketplace Run writers, and a migration preflight/backfill establish and preserve attribution for active legacy Runs in sidecar columns. The preflight reports duplicates and timestamp-inconsistent mappings and lists active Runs without a current Variant row for operator classification. Supported application history assigns fresh Agent IDs at Variant publication and preserves Variant rows; this is an explicit assumption for distinguishing unmapped non-Marketplace Runs from out-of-band lineage loss. Operators review every unmatched active Run before rollout; ambiguous rows block rollout and are never widened to Agent-only cancellation or silently skipped.

The existing `checkReleaseAdmissionTx` predicate remains the source of exact Release/dependency revocation semantics. A shared repository seam will resolve and check a local published Variant for the exact server-derived local Agent Version inside a caller-held tenant-guarded transaction so Run and chat admission cannot drift.

## Alternatives considered

- **Service precheck followed by existing admission:** rejected because revocation can commit between the check and Run/turn creation.
- **Hold the tenant guard across upload, extraction, budget/network work, or SSE:** rejected because external work would serialize unrelated requests for the tenant and could hold a database lock indefinitely.
- **Use only Redis live-run markers or message rows:** rejected because quick-answer turns do not necessarily set the marker and message rows have no atomic security admission state.
- **Append a stop event without durable claim cancellation:** rejected because a process or stream delivery failure can lose the notification while generation continues. Durable cancellation commits with the revocation ledger; watcher polling recovers notification loss.
- **Change the meaning of existing replay:** rejected because current workbench retries return their previously admitted result.

## Consequences

- New Run and AgentQA admission must use the same source-tenant guard and exact Release predicate as revocation.
- Run revocation cancellation must compare the exact pinned Release and Version. Migration preflight/backfill and immutable-identity triggers run on both SQLite and PostgreSQL; duplicate or unprovable active legacy mappings intentionally block migration pending operator repair. The reconciler retries durable `cancel` obligations after restart, while `allow` is terminal immediately.
- The AgentQA claim requires paired SQLite and PostgreSQL migrations, tenant-scoped repository methods, an atomic claim/message write API, handler dependency injection, and SQLite schema coverage. The current migration heads are SQLite `000125` and versioned `000204`; the next candidates are `000126` and `000205` and must be rechecked before implementation.
- Production rollback may retain the forward schema only with a security-compatible binary that preserves both exact AgentRun admission and AgentQA claim admission/fencing. A pre-Task8 binary must not run while adopted AgentQA or Workbench ingress is reachable; if no compatible binary is available, keep the current build or disable and verify those ingress routes before older code starts.
- Chat claim completion/cancellation must be idempotent and observable by the handler that owns the live generation. Claim polling adds bounded database reads while a custom-Agent turn is active. All handler-owned claim mutations include `lease_expires_at > transaction_now`; an expired generation cannot write even before a later admission performs expiry cleanup.
- AgentQA reports blocked admission as HTTP 409 and claim/version-store infrastructure failure as HTTP 500 before SSE headers; OpenAPI documents both on AgentQA only. This maps the approved new-use refusal into the existing API error contract.
- A crash after claim commit but before work starts may leave a nonterminal claim. Recovery never starts a second generation automatically. Lease expiry fences the prior generation and terminalizes any orphan assistant placeholder; a new explicit turn uses a new request ID and message identity. The lease interval is a runtime constant selected from the bounded handler heartbeat interval and tested at expiry boundaries.
- For shared Agents, the source tenant is `effectiveTenantID`; for tenant-local Agents it is the owning session tenant. The session tenant remains the scope for message and upload persistence. The implementation must not accept a client-selected source tenant without successful `resolveAgent` authorization.

## Status

Proposed. Requires a fresh independent architecture review of exact Run cancellation and legacy attribution/reconciliation, the resolved owner-authorized Stop operation, atomic claim/message fencing, nullable non-Marketplace Version invariant, handler DI seam, request replay contract, and AgentQA HTTP contract before Task8 implementation. Client inspection found no automatic AgentQA stream retry or promise that a retry resumes SSE; the current API client builder does not expose a request-ID option. The request-collision 409 is an implementation ruling for explicit callers that reuse the echoed ID; it prevents duplicate generation and allows history reload by assistant ID. Task9 must assert status, no SSE and no side effects without binding tests to exact error text. The ruling must remain covered by independent review before the plan is approved. This ADR records an implementation seam for the existing approved security behavior; it does not change the product's `cancel` / `allow` choices or authorize deletion of historical data.
