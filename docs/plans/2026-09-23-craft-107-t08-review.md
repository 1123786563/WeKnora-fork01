## Findings

### T08-1 — Medium — Prior Task grant becomes live again after tenant rejoin

**Evidence:** `CraftAccessService.Role` requires an active tenant member and then reads `craft_task_grants` (`internal/application/service/craft_access.go:82-102`). `ListAccessibleTaskIDs` likewise checks current membership then joins the persistent grant (`:193-209`). Neither path removes or invalidates a grant when tenant membership ends. The SQLite and PostgreSQL `craft_task_grants` migrations have no membership lifecycle binding or invalidation field. `TestCraftT08Journey` covers Task revocation, but not tenant removal followed by rejoin.

**Impact:** An explicitly granted Viewer or Collaborator loses access while outside the tenant, then regains the private Task on rejoining without a new Task Owner decision. This conflicts with private-by-default, explicitly granted collaboration when a new membership term should not inherit a prior private invitation. It also makes an old grant silently effective after a tenant administrator removes and later reinstates a person.

**Smallest defensible correction:** Invalidate Task grants for a user when their tenant membership is removed, or bind a grant to the active membership incarnation and require it to match during `Role` and listing. Add a persisted remove → rejoin journey proving direct read and listing remain denied until the Owner grants again. If product policy intentionally preserves grants across tenant rejoin, record that decision in the approved authority before treating this as conforming.

### T08-2 — High, integration gate — Existing HTTP reads and downloads lack proven Task checks

**Evidence:** T08 only adds `RegisterCraftAccessRoutes` (`internal/handler/session/craft_access.go:31-38`), which is not mounted in this checkpoint. `CraftAccessService.ListAccessibleTaskIDs` explicitly leaves application to T20 (`internal/application/service/craft_access.go:190-209`). The lane report states that session direct read, existing list, preview ticket issuance and file resolution, and version download still need central injection and that full HTTP denial is not asserted. The HTTP test uses a fake access service only on the new membership routes (`internal/handler/session/craft_access_test.go:16-71`).

**Impact:** Issue #126's revocation criterion for listing, direct access, preview, and download is not delivered by this checkpoint. Existing shared-session or ordinary admin access could still expose private Craft content until all central and byte-serving paths enforce the checker. This is an integration blocker, not a claim that the lane was assigned central files.

**Smallest defensible correction:** T20 must inject this service into every Craft operation and apply its list filter before results are returned; preview redemption and download byte-serving need a fresh check. Add authenticated HTTP tests that grant, read, revoke, then retry list, direct read, old preview ticket, and download, including ordinary admin and shared-session paths.

### T08-3 — Medium — Authorization and audit behavior lacks an end-to-end behavioral test

**Evidence:** `TestCraftT08Journey` directly calls `CheckTaskAccess`, `Grant`, `Revoke`, and `ListAccessibleTaskIDs` against a local database (`internal/application/service/craft_access_test.go:15-68`). `TestCraftAccessHTTPDerivesAuthority` checks context extraction with a fake that does not persist or enforce membership (`internal/handler/session/craft_access_test.go:16-71`). The lane report records real SQLite migration coverage for grant/revoke, but no test exercises a guarded Craft HTTP resource path with a real access service or checks denial audit at that path.

**Impact:** The tests establish policy and persistence but cannot prove the ticket's server-enforced private content boundary or its audit requirement on actual requests. A route wiring error or alternate retrieval path could pass every T08 test.

**Smallest defensible correction:** During T20, add the highest available authenticated API journey using the real service and migration, assert externally visible responses and persisted audit for grant/revoke and relevant denied access, and keep the test bound to the same integrated checkpoint. The source-open test must also prove the viewer's own original-resource ACL in T10.

## Conforming evidence and scope notes

- Role policy permits Owner/Collaborator/Viewer reads and previews, Owner/Collaborator writes, and Owner-only sharing; unknown actions fail closed (`internal/modules/craft/access.go:19-31`). It does not purport to give source authority: T10 must reauthorize originals with the requester's own permissions.
- `Grant` refuses unknown roles, self-grants, inactive or foreign tenant targets, and non-owner callers; grant/revoke writes and success audit records are in one database transaction (`internal/application/service/craft_access.go:122-167`). Real SQLite migration test verifies the table and audit schema agree.
- Handler body decoding rejects client-supplied tenant/owner fields, and `craftScope` derives tenant and principal from the authenticated request context. The new access routes themselves enforce authorization through the service. The owner panel hides mutation controls from a Viewer; UI hiding is only a projection, with server policy authoritative.
- The T08 lane stayed within its declared source ownership. Central route registration, checker injection, session/list/version/preview hooks, T10 original-source ACL, and T09 collaborator Run grants remain downstream work. No independent claim is made that the lane's reported tests were rerun here.
