# T19/#138 F3: durable pause and charge dispatch fence

Read-only architecture note, 2026-09-23. Sources: `CONTEXT.md`; approved `docs/specs/2026-09-23-craft-web-artifact-spec.md` (#138, lines 52, 69, 78); ADR-0004; T19 brief; integration `2026-09-23-craft-107-t19-review.md` finding F3; T19 fix-1 plan/report; current T19 worktree code. No source change is proposed as completed.

## Invariant and current gap

For a tenant-scoped durable Run, once `waiting_user` with `budget_exhausted` commits, no **new external model or sandbox invocation may begin** for that Run. A pre-pause invocation may finish or remain unknown, with its commercial hold retained until reconciliation. Reservation and invocation are distinct: a `dispatched` G4 row is accounting evidence, not proof that the external action actually started.

`CraftBudgetService.requireRunChargeable` reads `agent_runs` before the call record, G4 `BudgetStore.Reserve`, and `MarkReservationDispatched`; `pauseOnDenial` separately updates `agent_runs` (`craft_budget.go:740-784`). G4 reserve is an internal transaction over account, Task, reservation, and lots (`budget_reservation.go:22-~200`); marking dispatched is an independent UPDATE (`:319-337`). `AgentRunStore.SetStatus` changes status/revision under its own transaction and lease fence (`agent_run.go:498-525`). Thus workers A and B can both read `running`; A commits pause after cap denial; B then reserves, marks dispatched, and invokes. A status check *inside reserve alone* also leaves a commit-to-external-call gap. An in-memory mutex cannot order processes.

## Recommended minimum durable boundary

1. **One shared database coordinator owns admission.** Add a narrow `CraftChargeCoordinator` repository API with `AdmitAndStart(ctx, tenant, run, session, grant, activityKey, upper, start func(context.Context) (StartResult,error))`. It requires the same SQL database/transaction handle as G4 `BudgetStore`, and exposes a G4 `ReserveInTx`/`MarkDispatchedInTx` primitive or an equivalent private repository composition. Keep the existing G4 public calls for unrelated callers. The coordinator owns tenant/Run identity, grant/call-cap allocation, G4 reservation, durable activity key, and dispatch state. Application service supplies the concrete model/sandbox start callback and maps typed denial/unknown outcomes; it must not write G4 counters itself.
2. **Serialize on the `agent_runs` row through the actual start boundary.** Acquire a write lock on `(tenant_id,run_id)` in a short, bounded transaction; verify `session_id`, allowed status, current revision/epoch or lease authority, and no pause intent. In that transaction allocate the Craft call slot and G4 hold once by stable activity key. Under the same lock, mark the reservation dispatched and initiate the external request. Release the lock only after the transport confirms that initiation happened or returns an ambiguous outcome; commit a durable started/unknown journal result accordingly. A definite pre-send failure rolls back/reverts an unstarted hold. A timeout after possible send is **unknown** and retains the hold; never silently retry under a new key. The transaction must have a strict timeout and no long-running model/sandbox completion inside it. If the external provider supports fencing, carrying a Run generation token is preferable, but neither model nor sandbox is shown to offer that today.
3. **Pause uses the same Run lock and a monotonic state transition.** `pauseOnDenial` obtains that row lock, rechecks the status/revision, then commits `waiting_user` and `budget_exhausted` with a revision increment. It cannot overtake an invocation inside `AdmitAndStart`; an admission arriving after pause sees the parked row and creates no new hold or external call. Preserve an already dispatched/unknown hold. A stale worker cannot turn a newer state into `waiting_user`; extension/resume must advance revision and maintain the same serialization rule. Do not expire an invocation gate and assume a paused worker is unable to send: a partitioned worker may wake and call the provider. A durable pause-requested/drain state is an alternative if holding a SQL lock over request initiation is unacceptable, but pause may become `waiting_user` only after every in-flight start is confirmed or definitely canceled. Unresolved gates keep pause pending and require reconciliation, not a clock-based unlock.

**Ordering:** B locks first: its external initiation occurs before A can commit pause; A then parks, leaving B's dispatched/unknown hold. A locks first: B observes `waiting_user` and never starts. A crash before external initiation rolls back the transaction and B cannot infer a start; a crash or timeout after possible send is treated as unknown and keeps the hold. This requires an explicit durable start journal or conservative recovery path because `MarkReservationDispatched` alone currently conflates intent with possible effect. Holding a database transaction across even a bounded network send raises pool/lock contention and is the principal change cost; this is the smallest way to prove the literal start-order invariant without cooperation from the external system. Merely committing an admission token before the call proves only *authorization* ordering, not physical start ordering.

## Controlled two-worker verification

Use one migrated database with **two independent DB connections and service instances** (PostgreSQL is the strongest production proof; run SQLite separately). Seed a real tenant/Session/Run, a Task budget with room for B, and a Craft call cap whose final slot A exhausts. Barrier B immediately before its lock/transaction and hold A immediately before committing `waiting_user`; release in both orders. In A-first ordering assert B's start callback count is zero, no new dispatched reservation/call slot, and persisted pause. In B-first ordering block B inside the start callback, assert A cannot commit pause while it is blocked, then confirm initiation and release; assert A subsequently commits pause and B has exactly one dispatched or unknown hold. Repeat with the same activity key, an injected definite pre-send failure, a post-send timeout, worker crash/transaction abort, and a stale Run revision. Assert no duplicate external start on retries and no release of an unknown effect. Avoid a test that only starts B after pause has already committed; it misses F3.

## Migration and review risks

The coordinator requires a shared DB transaction, so G4 repository API refactoring is necessary; do not inject `agent_runs` knowledge into the commercial domain type. A journal column/table may be needed to distinguish `intent`, `started`, `unknown`, and `definitely_unstarted`; use a tenant + activity-key uniqueness constraint and migration for durable replay. Audit all Run status writers and all Lead/sandbox outbound paths before claiming the invariant. The lock must be short and bounded; a slow transport should produce an unknown state, retain the hold, and defer a final pause if its start cannot be ordered. A database failure must fail closed before external invocation. External provider idempotency, where available, should receive the same activity key, but local accounting idempotency by itself cannot stop duplicate remote effects.
