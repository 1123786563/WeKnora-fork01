## Findings

1. **Medium — The claimed process-restart replay is not exercised at the composed Execute seam.** Evidence: `TestLocalCraftRuntimeAcceptsIdenticalKnowledgeRetryAndRestart` in `internal/container/craft_knowledge_runview_h2_test.go:127-147` uses `restarted := *fixture.runtime`; it retains the same provider, in-memory binding map, material resolver, knowledge builder, records, and acceptance closure. It proves a second invocation of the same assembled state, but cannot detect a fresh provider failing to recover the existing container/material binding or a fresh resolver failing to reload the published digest. The separate provider restart test in `craft_runview_container_provider_test.go:841-865` does not compose that recovery with the final knowledge verification and `inner.Execute`. **Impact:** the H2 plan's reconstructed-runtime acceptance and handoff's process-restart behavior remain unproven. **Smallest correction:** add one Execute test that creates a new provider over the same durable layout and fake engine, reconstructs the material and accepted-record resolvers, and asserts exactly one inner dispatch with identical package bytes and no new search/publication.

2. **Medium — Candidate-only and changed-seal denials lack zero-dispatch tests at the final Execute boundary.** Evidence: `TestCraftKnowledgeRunViewFinalVerifierRequiresPublishedExactPackage` in `internal/container/craft_knowledge_runview_h2_test.go:19-61` tests candidate-only and changed manifest bytes by calling `VerifyAcceptedForRun` directly. `TestLocalCraftRuntimeRejectsKnowledgeMutationAfterResolver` at lines 64-125 exercises missing published package and foreign digest, but has no candidate-only or seal mutation case. A direct verifier error does not assert that the composed runtime stops before `inner.Execute`. **Impact:** two explicit H2 Fix 1 acceptance cases are missing behavioral proof at the requested dispatch seam. **Smallest correction:** add candidate-only and changed `seal.json` cases to the runtime table and assert zero spy calls, using the same after-resolver mutation point as the existing negatives.

## Verdict and evidence

- **Scoped Spec behavior: PASS with a private-host-volume boundary.** `verifyRunViewKnowledgeRoot` in `craft_runtime.go:285-329` opens the mounted root and nested directories with `O_NOFOLLOW`, requires only `runs/<accepted RunID>`, and rejects extra entries. `Execute` calls it around `knowledgeVerifier`, then calls provider reinspection immediately before `inner.Execute` (`craft_runtime.go:224-242`). `VerifyAcceptedForRun` reloads the actor-scoped published record and exact digest, rejects a candidate alongside the published path, and resumes the package bytes (`craft_knowledge_runview.go:132-188`). `RevalidateMaterialHandle` checks the generation layout and running provider binding; exact bind source, read-only flags and mount count are validated in `craft_runview_container_provider.go:452-607`. These close the prior H2 High 1–2 implementation gaps within the existing trusted private host filesystem model. H3 authority recheck and production wiring remain gated separately.
- **Scoped quality/acceptance: FAIL pending the two Medium test findings.** The implementation paths appear to deny the listed mutations, but H2 Fix 1 specifically requires observable zero-dispatch evidence for each and reconstructed-runtime replay. Tests 1 and 2 are the smallest missing proof; no source defect in the reviewed fix was established.
- **Linux proof: sufficient for the actual mount.** `TestCraftRunViewProviderCreatedLinuxContainerKnowledgeMount` creates the container through the provider, inspects its actual knowledge bind, reads the accepted Run manifest at the generation destination, and verifies a root write through that bind fails (`craft_runview_live_engine_h2_test.go:79-169`). It removes the probe and asserts container/network cleanup. The older ad hoc bind test remains supplemental only. The checkpoint reports a PASS on the pinned `weknora-craft-runtime@sha256:9678e13bd1c7dc9650aef26623ef8ab276d46565bbd6cb006b8e308229968f11` Linux Docker image; this review did not rerun Docker.
- **Provider isolation adjustments:** created-state acceptance still requires exactly one named private attachment and matching `HostConfig.NetworkMode`; running-state inspection requires exact network ID and private IP (`craft_runview_container_provider.go:549-566`). The Docker adapter projects configured tmpfs from `HostConfig.Tmpfs`, while the provider still requires the exact `/tmp` mount and no extra mounts (`craft_runview_live_engine_h2_test.go:288-303`, provider lines 586-618). XDG state/cache are routed under the existing generation-owned writable OpenCode data bind; rootfs, knowledge and inputs remain read-only (`craft_runview_container_provider.go:610-637`). No unexpected isolation weakening was found in these adjustments.
- **Residual race:** the host filesystem and engine inspection are sequential pathname checks. A privileged actor able to mutate the private generation tree or container after the last check could create a check/use gap; the engine API shown does not atomically pin the accepted bytes and the prompt dispatch. This is a trust-model limit, not a demonstrated in-scope bypass by the delegate, and should not be described as an atomic proof against a hostile host writer.
- **Checkpoint and verification:** all eight current owned files and the task-local patch match the SHA-256 values in `h2-fix1-checkpoint/checkpoint.json`. Independent focused normal and `-race` container test commands passed; `git diff --check` on the owned files passed. The checkpoint's Linux proof and image identity are recorded above. No OCR was invoked.

H3 should remain gated until the two Medium proof gaps are corrected and independently checked.
