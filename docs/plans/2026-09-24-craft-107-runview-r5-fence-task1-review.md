## Findings

1. **Medium — the admitted digest is transported but not compared with the authoritative Run at the Task/material boundary.** `CraftDelegateTool.Execute` copies one claimed Fence digest into both `craft.Task.SnapshotDigest` and `task.Fence.SnapshotDigest` (`internal/modules/agentruntime/agent/tools/craft_delegate.go:264–275`). `validateDelegateTask` compares those two copies (`internal/application/service/craft_delegate.go:87–93`), while `CraftStore.PrepareTask` locks and reads the Run but only checks scope (`internal/application/repository/craft_workspace.go:273–283`). The current material resolver reads the Run and compares only the Workspace ID (`internal/container/container.go:2770–2789`). The Task1 tests prove that changing query/model/input/knowledge/seed changes the digest, but none retains an original Task digest and proves that a different, internally consistent durable Run digest is rejected. **Impact:** a same-Workspace Run snapshot and persisted digest changed together after the original claim can pass the current Task checks and reach material resolution under an old Task identity; this leaves the R5 immutable-snapshot acceptance unproved and the prior R5 finding open. The production material gate remains default-off, limiting present exposure. **Smallest correction:** under the Run transition lock in `PrepareTask`, compare Task digest/version with the persisted row and independently recompute the row digest from its snapshot; then enforce the same identity in the material operation authority before any allocation or external call. Add a real-DB test that retains the original Task while changing each valid snapshot field and its row digest in the same Workspace, and asserts rejection before side effects. A comparison of Task and Fence copies alone is insufficient.

2. **Low — idempotent admission replay returns a Craft Run without validating its persisted digest.** The existing-row branch of `AgentRunStore.Admit` checks only digest version and nonemptiness (`internal/application/repository/agent_run.go:414–430`), then returns `existing.view()`. `ClaimDriver` does recompute and reject a malformed or mismatched digest (`:1149–1160`), so execution fails later, but a replay can report an invalid admitted identity as success. **Impact:** admission replay gives an inconsistent result and defers corruption detection to claim; there is no replay regression test for a mutated snapshot/digest. **Smallest correction:** call `validCraftAdmittedSnapshot(existing)` before returning the replay and add a focused corruption/unknown-version case.

## Spec compliance verdict

**FAIL for Task1's full frozen-identity acceptance; the persistence and transport portion passes.** The digest has an explicit `craft-admitted-snapshot-v1\0` domain and version, canonicalizes the complete final seeded JSON with duplicate-key and numeric handling, and is inserted in the same admission transaction as the Run. ClaimDriver validates stored bytes and rejects absent/unknown/mismatched Craft identity before returning a Fence. Runtime context, Task construction, and service validation preserve the typed identity without deriving it from a later `Get`. Finding 1 leaves the required Task-versus-durable-Run comparison and the same-Workspace changed-snapshot denial unresolved. Task2/3 should not treat this checkpoint as satisfying that acceptance.
