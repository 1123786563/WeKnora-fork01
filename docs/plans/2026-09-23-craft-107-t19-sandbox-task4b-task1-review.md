## Findings

1. **High — Post-send invalid receipt is classified as a plain validation error.** In `StartRemoteExec` lines 102–109 and `StartRemoteCreate` lines 122–129, `StartExec`/`StartCreate` may have been accepted before the helper rejects an empty, mismatched, or malformed receipt. The helper returns only `ErrRemoteOperationInvalidReceipt`, discards the provider ref, and `IsRemoteOperationUnknown` is false. The test at `remote_operation_test.go:100–106` explicitly codifies this for a mismatched operation key. T19 requires possible acceptance to remain unresolved and prohibits a second physical start; a caller using typed classification could treat this error as a safe non-start and release the G4 hold or retry. **Smallest correction:** distinguish pre-dispatch input errors from post-dispatch receipt failures; after a start call, return an error that is both invalid-receipt diagnostic and `RemoteOperationUnknown` (preserving any usable ref for investigation), then test that the ambiguous classification survives invalid/missing exec and create receipts.

2. **Medium — Exec target provenance is checked after provider invocation and is incomplete.** `StartRemoteExec` lines 102 and 106 invoke the initiator before checking `handle == nil`; it never checks `handle.Provider() == client.Provider()` or a nonempty sandbox ID. Thus a chargeable start can be sent with a nil or foreign-provider handle, and its returned sandbox ID may pass validation if it matches that foreign handle. The returned `ErrRemoteOperationInvalidReceipt` can then also hide possible acceptance. **Smallest correction:** reject nil, empty-ID, and provider-mismatched handles before calling `StartExec`; validate the returned provider, sandbox ID, operation key, and operation ID after the call, with any post-call failure classified as unknown. Add call-count tests proving no physical start for malformed/foreign handles.

3. **Medium — Arbitrary adapter errors can escape without unknown classification.** Both helpers return `err` unchanged at `remote_operation.go:103–104,123–124`. The optional interface does not encode a pre-send versus may-have-sent result, so a transport timeout or cancellation represented as a normal Go error is not recognized by `IsRemoteOperationUnknown`; the comments rely on every future adapter getting this right. The Task 1 unknown test uses an adapter that already returns the desired typed error, so it does not exercise this contract failure. **Smallest correction:** make the initiation result explicitly classify proven pre-send failure versus possible send, or conservatively wrap all errors returned after invocation as unknown unless the adapter supplies a verifiable pre-send classification. Add timeout/cancellation/raw-error tests for exec and create.

## Scoped verdict

**Spec compliance: FAIL for Task 4b Task 1 acceptance.** The new optional interfaces and helpers do prevent synchronous `Create`/`Exec` fallback, and no current provider advertises the capability. However, the helper currently loses the required unknown semantics after an ambiguous provider call or invalid receipt. Receipt/provenance checks are too late for the exec target.

**Code quality: NEEDS FIX.** Tests cover the happy receipt and one typed ambiguous result, but miss the post-send malformed-receipt, raw transport error, and pre-dispatch target-validation behaviors that protect the charge boundary. Static interface conformance alone does not prove bounded start, durable receipt lookup, or same-key replay safety; Task 2 must establish those with adapter behavior and persistence before advertising a provider. This checkpoint adds no production caller or provider adapter, so it does not establish T19 sandbox charging or the complete T19 acceptance criteria.
