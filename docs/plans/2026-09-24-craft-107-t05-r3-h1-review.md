## Finding

### Medium — the builder does not re-establish the handle's verified generation layout

**Evidence / affected symbol:** `validateCraftKnowledgeRunViewHandle` in `internal/container/craft_knowledge_runview.go:169-184` checks the Run key, nonempty generation/directory, canonical root, and `knowledge == root/knowledge`. It never checks that `directory == craftRunViewSpecForGeneration(generation).Directory`, that `root` is the generation-derived layout root, or the layout identity and directory inode/mode proof established by `MaterialHandle` through `verifyGenerationLayout` (`internal/container/craft_runview_material.go:80-93`; `craft_runview_container_provider.go:709-747`). `BuildForRun` then constructs the publisher from `material.root` (`craft_knowledge_runview.go:84-85`). The H1 tests construct a handle directly with a temporary root and arbitrary `generation-1`/`directory`, so they do not exercise a provider-issued handle or a replaced generation directory.

**Impact:** A stale handle whose root directory was removed and recreated, or an internally mismatched handle, can pass H1's root check and cause the accepted package to be published in a directory no longer proven to belong to the persisted RunView generation. This violates H1's verified same-Run generation root contract. H2 may later reject that material, but H1 would already have durably accepted and published the package at the wrong root. The package-private handle limits who can construct an arbitrary value; it does not make a previously verified filesystem identity permanent.

**Smallest defensible correction:** Give the builder a narrow provider-backed verification of the generation/layout immediately before constructing the publisher, including the identity manifest and canonical `knowledge` directory, or carry an immutable layout identity from `MaterialHandle` and compare it against current filesystem identities. Check the generation-derived directory and root relationship. Add tests for a genuine provider-issued handle, changed generation/directory/root, and a root replaced after handle issuance. Preserve the existing publisher's exact seal and path validation.
