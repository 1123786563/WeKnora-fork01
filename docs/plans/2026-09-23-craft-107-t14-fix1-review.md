## Finding

### T14-F1 — High, release gate — browser protection can be asserted without attestation

**Evidence and affected symbol:** `CraftPreviewConfig.BrowserNavigationProtected` is an exported `bool` (`internal/application/service/craft_preview.go:67-71`). `Issue` and `Open` trust its value directly (`:242`, `:315`); there is no live render-browser policy check, bound session, or attestor. The in-process fixture sets it to `true` with `previewNoEgress{}` (`internal/handler/session/craft_preview_test.go:228-236`), which checks neither a user's browser nor a remote render boundary. The current central constructor leaves it unset, so the current assembly is closed; the type nevertheless permits another caller to set `true` on insufficient evidence. The integration architecture note explicitly requires live attestation and says a static flag alone is insufficient.

**Impact:** A future wiring or environment flag could reopen the known R1 navigation leak while satisfying all current Go journey assertions. The bool is a manual release claim, not enforcement. This finding does not mean the present central assembly leaks; it means the proposed enabling interface cannot make unsafe enabling impossible.

**Smallest defensible correction:** Before enabling the preview, replace the boolean gate with a narrow injected browser-boundary dependency that verifies the actual render session and its effective deny-by-default network policy for the bound Task/Version on issuance and each read or reconnect. Keep the default disabled until the deployed remote browser, fixed preview ingress, and browser/network probes are verified on the same selected configuration. At minimum, prohibit any production static true setting and add a regression test showing a missing, stale, or failing attestor refuses issuance and reads.
