## Findings

1. **Medium — production authentication is not exercised.** `TestCraftB5JoinedCurrentProduction`, lines 111–160, builds `gin.New()` and replaces `middleware.Auth(...)` with `X-Test-User`/`X-Test-Key` context injection. It does invoke the real `registerSessionRoutes`, Viewer RBAC and API-key route authorizer, and its Craft reads use persistent access checks. But production `NewRouter` mounts `middleware.Auth` (`internal/router/router.go:270`), whose JWT/API-key paths resolve tenant and active membership (`internal/middleware/auth.go:127–190, 201–260`). The fixture can admit a synthetic nonmember or stale member to route guards in a way the production authenticator would reject earlier. **Impact:** the report's “production auth” and anonymous/API-key policy claims are stronger than this test proves; the test cannot catch drift in Auth's tenant, role or key-context construction. **Smallest correction:** drive this journey through `NewRouter` with credential service fakes at the verification edge, or mount the real `middleware.Auth` with narrowly scoped credential/tenant/member service fixtures. If that is impractical, label this as a production route-guard and persistent-access test, with authentication verified separately on the same route family.

2. **Medium — the `/p/` assertion never reaches the preview gate.** Lines 278–281 send `httptest.NewRequest` without setting `Host`, so it defaults to `example.com`; the service is configured for `preview.example.test` at lines 90–94. `CraftPreviewHandler.CraftPreviewFile` rejects `!AcceptsPreviewHost` before calling `Open` (`internal/handler/session/craft_preview.go:116–120`), and `AcceptsPreviewHost` compares the request host to the configured preview origin (`internal/application/service/craft_preview.go:223–231`). **Impact:** the 404, zero bytes and zero opens would pass even if preview capability handling failed open on its configured origin. **Smallest correction:** set the request Host to `preview.example.test` and assert the same denial; keep a separate wrong-host assertion if desired. This still remains disabled-state evidence, not successful ticket/capability coverage.

3. **Low — the list denial assertion permits an unavailable or rejected list.** In `assertDenied`, lines 185–199 skip a status assertion for `/api/v1/craft/sessions`; a 401, 403, 404 or 500 body without the marker passes. **Impact:** it does not prove the private Task is omitted from an otherwise usable list, as Task 1 step 3 requires. **Smallest correction:** require HTTP 200 for the list and inspect the parsed session IDs for absence of `task-b5`.

4. **Low — audit assertions do not establish the expected mutation sequence.** Lines 320–334 filter success audit actions and require six rows with nonempty targets, but do not match each action to Viewer/Collaborator and the later fresh Viewer grant. A wrong target or duplicate grant/revoke distribution could still total six. **Impact:** the durable attribution check is useful, but the reported grant/revoke audit coverage is narrower than stated. **Smallest correction:** compare exact `(action, target_user_id)` counts for three grants and two revokes plus the explicit stale-grant setup, and assert the denied Viewer mutation adds no audit side effect. Keep denial-read auditing explicitly open until its contract is decided.

5. **Low — global Gin mode is not restored.** Line 46 calls `gin.SetMode(gin.TestMode)` without cleanup. The registered Craft session and preview globals are restored at lines 96–103, and the DB is fresh per test, but Gin mode remains changed for later tests in the package. **Impact:** package test order can alter unrelated routing behavior or logging. **Smallest correction:** save `gin.Mode()` and restore it in `t.Cleanup`, or avoid changing the process-wide mode for this engine.
