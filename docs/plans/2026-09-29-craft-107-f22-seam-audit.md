# Craft #107 F22 seam audit

Read-only architecture assessment, 2026-09-29. Sources: `CONTEXT.md:209,348-349`; approved `docs/specs/2026-09-23-craft-web-artifact-spec.md:57-69,73-78`; ADR-0004; current OCR `docs/plans/craft-107-ocr-final-1.md:379-386`; prior recovery analysis `docs/plans/2026-09-23-craft-107-t19-docker-exec-recovery-design.md:1-29`; current worktree code. The worktree has unrelated ongoing modifications; this audit changed no source or tests.

## Verdict

**F22 cannot truthfully be closed by a service-only terminal classification.** The service branch at `internal/application/service/craft_docker_normal_exec.go:354-369` is unreachable with the sole production normal provider: `ObserveAttachedExec` returns `unknown` for every non-running inspect when its `positiveStartEvidence` input is false (`internal/modules/execution/sandbox/docker_normal_exec.go:424-444`). A durable send claim is evidence that one caller *may* send, not evidence that Docker started or never started. `ExecInspect` gives ID, container, Running, and ExitCode, but its non-running/zero shape is shared by a lazy unstarted exec and a completed successful exec (prior design analysis, lines 12-19; provider test `docker_normal_exec_test.go:414-429`). Thus absence of start evidence cannot be promoted to definitive failure, and an empty sealed output row cannot be asserted.

This is a **provider lifecycle evidence contract gap**. The owner is the Docker normal exec provider (`internal/modules/execution/sandbox/docker_normal_exec.go`) and its composition seam (`internal/container/craft_exec_policy_wiring.go:73-76`), with repository/coordinator changes only if a durable event or start marker is introduced. The service consumes the result (`internal/application/service/craft_docker_normal_exec.go:342-382`). The approved spec requires authoritative sandbox inspection before recovery and no duplicate work or false success (`docs/specs/2026-09-23-craft-web-artifact-spec.md:65,78`); parking Unknown is therefore correct until the stronger evidence exists.

## Producer to consumer trace and crash windows

1. `CreateAttachedExec` creates an inert Docker exec and verifies the exact exec/container IDs (`docker_normal_exec.go:149-213`). The service binds its full receipt before claim (`craft_docker_normal_exec.go:166-185`; receipt type `internal/application/repository/craft_docker_normal_input.go:501-509`). Crash before binding may orphan an inert exec; that does not prove a start.
2. `DockerNormalSendOperation.Claim` performs the durable CAS and grants a single-use local permission only to the winner (`internal/application/service/craft_docker_send_coordinator.go:207-229`). A crash immediately after claim and before `ExecAttach` leaves no physical start. The same durable row also covers a crash after the start POST reached Docker. The row cannot separate these histories.
3. After claim, the service opens a durable output sink, checks cancellation, consumes permission, then calls `StartAttachedExecOnce` (`craft_docker_normal_exec.go:192-216`). These pre-dispatch failures can be known **inside that invocation**, but the claim remains consumed; a restarted observer cannot infer which instruction was reached from the claim alone.
4. Provider preflight inspect and `started.LoadOrStore` precede `ExecAttach` (`docker_normal_exec.go:236-261`). That `sync.Map` and the service's `started` map (`craft_docker_normal_exec.go:217-239,346-350`) vanish on restart or cap reset. Attach errors may mean the POST was accepted before response loss; the provider deliberately returns Unknown (`docker_normal_exec.go:261-282`). A successful attach sets in-process `StartEvidence=true`, but that is not persisted as a durable lifecycle marker.
5. Replay is observation-only after claim (`craft_docker_normal_exec.go:159-164,185-190`). It passes the volatile boolean to the provider (`:342-353`). Running is positive start evidence. Non-running plus no positive evidence is Unknown (`docker_normal_exec.go:429-444`); 404, identity mismatch, and daemon event loss are also inconclusive, not proof of no side effects (`:447-459`; prior design analysis lines 12-19).

The existing Docker event observer is **useful positive evidence**, not a negative receipt. It matches an exact `exec_start`/`exec_die` pair by container and exec ID (`internal/modules/execution/sandbox/docker_exec_events.go:50-103`), but only exposes `DockerOutputlessExecReceipt` and a complete pair. A missing half returns `unavailable`; event eviction or daemon restart can erase history (`:105-169`). Reusing it could recover a *started and completed* normal exec when both events are retained, but `unavailable` cannot establish *never started*. A durable pre-dispatch marker has the same limitation: it records that the process intended to send, not whether Docker executed. A marker written **after** positive start acknowledgement improves later attribution but has a crash window between Docker acceptance and marker commit.

## Recommendation and minimal scoped follow-up

Keep F22 open as a provider evidence dependency; remove or rewrite the unreachable service promise only as an honesty cleanup, without turning Unknown into Failed. A safe vertical improvement within the current architecture is **positive lifecycle recovery**: add an exact normal-exec event observer in `internal/modules/execution/sandbox/docker_normal_exec.go` (potentially share the parser in `docker_exec_events.go`); expose a typed observation with `started`/`terminal` evidence through `internal/container/craft_exec_policy_wiring.go:73-76`; consume it in `internal/application/service/craft_docker_normal_exec.go:342-382`. If the evidence must survive daemon event eviction, add a durable provider event receipt to the existing journal/repository and coordinator, with exact receipt identity and monotonic CAS. Tests should cover start/die pair, start-only, no event, replay gap, daemon restart, claimed-before-send crash, accepted POST with lost response, output unavailable, and no second attach. A recovered terminal process must still keep output/transport partial unless the durable sink proves completeness (`craft_docker_normal_exec.go:248-266,377-382`).

That improvement **does not close the specific claimed-never-started claim**. To make never-started definitive, the external Docker side must provide an authoritative, durable, queryable per-exec lifecycle receipt whose negative result is guaranteed complete across the relevant claim/start interval, or the sandbox command protocol must atomically record a durable start decision on the execution side. The current Docker inspect and retained event API offer no such negative guarantee. The provider/API owner must define retention, exact identity, delivery completeness, daemon restart behavior, and the race boundary before a service can map absence to Failed. Until then Unknown preserves the single-writer and no-duplicate-work invariants of the approved spec.
