# Craft #107 T01 R4 Task 2b — post-terminal draft and candidate seam

Read-only architecture recommendation, 2026-09-24. Sources: `CONTEXT.md` (Workspace, Craft webpage, Task Artifact); approved `docs/specs/2026-09-23-craft-web-artifact-spec.md`; ADR-0004, ADR-0008, ADR-0009; R4 version plan and Task 2a plan; current runtime, collector, draft store, Run transitions and recovery code. The R4 version plan's explicit ruling supersedes the older promoted-Version seed in the R3/R4 design note.

## Findings and boundary

1. `localCraftRuntime.Execute` currently returns an unresolved error after successful inner execution; Task 2a intentionally leaves collection unassembled. Its new source is bound to the verified generation, while `pointWorkspaceOutput` is the old shared pointer and must stay outside this route.
2. `CraftArtifactService.CollectForKind` owns validation, upload and `VersionStore.Publish` in one method; the configured `SandboxArtifactSource` is singleton and accepts only a session ID. Passing the Run source into that method would publish before T15 and can accidentally reuse a source across Runs.
3. `CraftDraftHeadStore.Advance` locks the head and Run transition rows, checks scope, terminal status (`succeeded|failed|canceled`), empty session active writer slot, no pending tools/delegations, and one revision per source Run. An active `Execute` cannot call it. `AgentRunStore.Finalize` atomically marks success and clears the slot; `SetStatus(failed)` also clears the slot. A terminal *delegation* result is not a terminal *Run*.
4. `CraftRecovery.Reconcile` can return an already saved delegation result without re-execution. Therefore a post-terminal capture must have its own durable work item and replay logic; an in-memory callback is insufficient. `waiting_user`, `queued`, `running`, `recovering`, and unknown sandbox state are not quiescence proof.

## Recommended interfaces and ownership

* Introduce a **per-Run collection input** at the application seam, for example `CollectCandidate(ctx, task, kind, source SandboxArtifactSource) (Candidate, error)`. The source is made by the container from the admitted Task/fence and Task 2a verified material handle. It is never stored in the singleton service. Refactor the existing collector's stage/validate/upload logic into a shared private routine; preserve legacy `CollectForKind` behavior for non-RunView callers. Candidate ID is deterministic from workspace, Run and manifest digest; its immutable row contains scope, Run/generation identity, files, evidence and validation checks, but has no default-visible Version pointer. Only T15 may call a separate guarded promotion operation after build, entry, reachable preview and page-load evidence. `VersionStore.Publish` must not be the candidate writer unless the store proves that Publish does not make it visible/default; current semantics should be treated as publication.
* Add a **post-terminal capture coordinator** at the application/worker boundary, not inside `Execute`: `CaptureQuiescentDraft(ctx, scope, workspaceID, runID, verifiedGeneration)`. It re-reads authoritative Run, session slot, pending tool/delegation rows, generation/mount identity and fenced output; it uploads a sealed bounded manifest, then calls `DraftHeadStore.Advance` with the Run's frozen predecessor revision. It works for succeeded, failed and canceled Runs. Unknown remains fenced until authoritative reconciliation yields terminal and no live writer. The coordinator must not infer safety from `inner.Execute` returning, an OpenCode finish flag alone, or process death.
* Durable record keyed by `(tenant, workspace, run)` should track frozen predecessor revision/digest, generation identity, capture state (`pending|capturing|sealed|advanced|blocked`), sealed manifest digest and refs, optional candidate ID/state, and last error. State is server owned and append/audit friendly. Use a transactional outbox or equivalent terminal-transition hook to enqueue capture when `Finalize`/terminal `SetStatus` clears the slot. A recovery scan must also find terminal Runs with missing capture receipts, since the process can die after terminal commit and before enqueue.
* Keep the Run-bound source and host paths private to `internal/container`; application receives only the narrow source interface and opaque verified identity. The repository owns CAS and immutable records. T15 owns promotion/default pointer. The container must not reach into version publication or set a default as a side effect of `Execute`.

## Exact order and replay rules

1. Admission persists the frozen draft predecessor and writer fence before prompt; RunView materialization seeds only that revision into the generation's private output. Task 2a source stays bound to that Run/generation.
2. `Execute` dispatches/observes and stores the delegation outcome. Successful execution may trigger bounded candidate staging through the per-Run source, but the candidate remains private and cannot be called a Version/default. Failed/stopped execution may skip candidate staging; its output remains eligible for draft capture. If output read/upload fails, record the error and preserve the last default.
3. The Run worker commits the *Run* terminal state and clears the session slot. Only then does a capture worker check authoritative quiescence and stage the exact output bytes. It calls `Advance(expectedFrozenRevision, sourceRunID, files)` after all objects are durable. A later Run must not be admitted against an uncaptured predecessor if that would lose a repairable draft; admission should either wait for capture or explicitly block with a recoverable reason.
4. On crash/retry, read the durable record first. A sealed manifest is verified against object bytes and source identity; retry uses those exact refs, never re-collects a changed filesystem as the same capture. `Advance` success followed by receipt-write failure is detected by `ReadRevision`/head source Run plus digest and recorded as success; differing digest/revision is conflict. Current `Advance` rejects same-Run replay, so this idempotency check belongs in the coordinator (or a narrow store method) and must not treat every conflict as success. Candidate insert is likewise unique by Run/content digest; changed bytes or generation under the same Run fail closed. Orphan uploads follow existing deferred reclamation.
5. T15 checks the four validation facts against the *same candidate digest* and atomically promotes that candidate to the default Version. Old Version bytes/history remain immutable. A failed check leaves the candidate/draft available for diagnosis and the previous default intact.

## Failure and security invariants

* A terminal Run can still have a live sandbox writer or pending tool: capture waits. A stopped Run is eligible only after confirmed abort/quiescence; stop intent alone is not proof. Unknown never releases its fence or exposes partial output.
* Revalidate the Task 2a source at list and every read. Reject changed container/generation/mount identity, symlink or hard link, special file, traversal, extra file, list/read replacement and over-quota tree. A manifest must be sealed from one consistent snapshot; a file changing during capture aborts the attempt.
* Objects and rows are scoped by tenant, owner/session, Workspace, Run and generation. Candidate and draft references are not client supplied. No shared output symlink, previous Run directory, HOME/state, inputs or knowledge may be copied or mounted into capture. Output bytes are untrusted content; validation/evidence claims from the page do not grant promotion.
* Candidate, draft head and default Version are distinct authorities. A repairable failed draft can become the next Run's predecessor even while the previous successful Version stays default. Candidate visibility to T15 does not imply user-facing success.

## Minimal implementation sequence and tests

1. **Application/repository task (preceding runtime wiring):** candidate store and per-Run collection API; durable capture receipt/outbox and post-terminal coordinator; explicit replay semantics. Own `internal/application/service/craft_artifacts.go`, new candidate/capture service files, repository schema/store files and focused tests. Preserve existing collector callers. T15 promotion contract must be agreed before implementation, but T15 itself follows this task.
2. **Container/worker task:** wire Task 2a source into candidate staging and terminal capture trigger/recovery scan; own `internal/container/craft_runtime.go` and worker assembly/hook files with focused tests, serially after Task 2a review and the application seam. This task must not modify collector repository files concurrently.
3. **T15 task:** four-check evidence bound to candidate ID/digest and guarded default promotion. Integrated A→B/C acceptance follows real engine, T05 material handoff and central assembly; production dial remains off until then.

Required tests: failure and canceled Run with output produces D2 after authoritative terminal/quiescence; next Run seeds D2 while V1 remains default; unknown/waiting/pending tool and stop-requested Run produce no draft; terminal commit/crash before enqueue is recovered; upload/crash before and after seal and Advance is idempotent; same-Run changed bytes or wrong predecessor conflicts; two Runs cannot race head CAS; stale source/generation and list/read replacement reject; candidate cannot appear in default/history before four checks; each missing/failed check preserves V1; successful promotion preserves V1 bytes and binds exact candidate evidence. Include actual Linux mount and A→B acceptance because fake provider tests cannot establish host confinement.
