# T19 model egress identity: implementable boundary and release gate

**Status:** read-only architecture recommendation, 2026-09-24. **Scope:** approved Craft Spec #107 story 34–35 and T19/#138 acceptance in `2026-09-23-craft-107-dag.md`; no production or test edit. Integration worktree is moving; recheck HEAD and ownership before implementation.

## Evidence and decision

`CONTEXT.md`, the approved Craft Spec, and relevant ADRs do not grant OpenCode authority to spend. T19 requires budget admission before each model activity, attribution once, and durable pause/recovery. `2026-09-24-craft-107-t19-activity-id-protocol.md` establishes only that pinned OpenCode 1.18.4 has `chat.headers`; it does **not** establish a durable per-provider-attempt hook, retry identity, or direct-egress prevention. `docker/craft/runtime-config.json` states gateway-only model access, but the Dockerfile currently bakes no provider route or attempt plugin. `internal/handler/craft_model_gateway.go` currently accepts a syntactically valid `X-Craft-Activity-ID`, derives the charge key, and forwards after `BeginBinding`; scope hashing is not proof that the identifier came from the physical attempt. The reviewed T01 RunView provider has a generation-scoped private container/network and inspected immutable labels, but egress/sidecar and credential wiring are not assembled.

**Recommendation:** introduce a server-owned, private **per-Run model egress adapter** as the only OpenCode provider endpoint. The adapter owns a durable attempt journal and the narrowly scoped gateway execution credential; OpenCode receives neither that credential nor an upstream API key. The gateway accepts an adapter-issued proof only after checking the journal against its authenticated credential and current RunView generation. Do not enable this path until the pinned Linux image proves its provider route and the network policy proves no bypass. This design does not claim the current OpenCode plugin can supply an ordinal.

## Trust boundaries and data flow

1. The platform resolves the persisted `(tenant, task, run, delegation, RunView generation, container ID, session ID)` and provisions one adapter instance/identity and one private network for that generation. A host-owned controller, not OpenCode or workspace files, supplies adapter configuration and a short-lived execution credential. Credential renewal/revocation is bound to the same generation and survives adapter restart through a server-side secret store, never the OpenCode HOME volume.
2. OpenCode has only the adapter's private provider endpoint. Engine inspection verifies its image digest, labels, mounts, single network attachment, effective UID, endpoint config and DNS/egress policy on creation **and recovery**. Network enforcement denies all provider IPs/domains and the gateway directly from the OpenCode container; only adapter ingress is reachable. A provider-specific bypass, arbitrary custom base URL, BYOK route, redirect or proxy environment variable fails admission. The adapter alone can reach the Craft gateway; the gateway alone holds provider credentials. An ordinary Docker bridge plus application URL config is insufficient isolation.
3. The adapter authenticates the local peer by a generation-scoped network identity/capability delivered outside OpenCode's writable filesystem, verifies route/method/model/body limit, and strips all caller `Authorization`, `X-Craft-*`, upstream URL and credential fields. The adapter cannot trust a body hash, TCP connection, OpenCode session header or plugin-supplied UUID as a model-call key. It writes the journal before forwarding; its proof is generated from the committed row.
4. The gateway verifies its own execution credential, adapter service identity (mTLS or equivalent host-controlled channel), proof signature/MAC and key ID, expiry, row state, tenant/run/delegation/generation/model/body-digest binding, and one-way nonce use. It reloads the current RunView and rejects a stale generation, revoked credential, caller-chosen ID, changed body or conflicting replay **before** `BeginBinding`. Gateway and adapter must share one durable authoritative store or a transactionally published attempt row; an uncommitted sidecar file is not sufficient proof to the gateway. `BeginBinding` remains the one-shot budget/start fence; response headers alone are not final usage evidence.
5. The gateway response is returned to the adapter only after its bounded body/usage resolution. The adapter durably records the outcome before returning it to OpenCode. A crash before durable outcome leaves `unknown`, even if bytes may have reached OpenCode. Secrets/proofs are redacted from logs and never placed in workspace artifacts.

## Journal and protocol

Use a server-side SQL table shared with gateway validation, with a unique `(tenant_id, run_id, generation, model_call_ordinal, physical_attempt_ordinal)` and unique opaque `attempt_id`. Minimum columns: `tenant_id`, `task_id`, `run_id`, `delegation_id`, `generation`, `container_id`, `opencode_session_id`, `model_call_id` (only if a verified upstream source exists), `model_call_ordinal`, `physical_attempt_ordinal`, `attempt_id`, `request_digest`, `model_id`, `credential_grant_id`, `proof_key_id`, `state`, `gateway_activity_key`, `gateway_journal_ref`, `result_digest`, `usage_state`, `created_at`, `forwarded_at`, `resolved_at`, `lease_owner`, `lease_epoch`, `error_class`. Store no prompt/body or provider key. States: `prepared` (committed, not sent), `forwarding` (send may have occurred), `completed` (full gateway result and usage durably observed), `definitely_unstarted` (transport provably never invoked), `unknown` (anything after send intent without complete observation), `reconciled` (authoritative gateway/provider result), `parked` (unresolvable). State transitions use compare-and-swap and a fenced lease; unique attempt ID survives process restart. The adapter commits `forwarding` before network `Do`, because a crash after beginning `Do` is ambiguous. Only `prepared` with proof of no `Do` may be abandoned and reallocated.

Proof payload: version, attempt ID, tenant/run/delegation/generation, model and request digest, grant ID, expiration, nonce; MAC/signature under an adapter service key unavailable to OpenCode. The gateway checks the corresponding durable row and marks proof use or ties it to the existing gateway journal atomically with charge admission. Repeated proof can only retrieve/reconcile the same attempt; it cannot invoke the provider again. Key rotation retains validation of unresolved rows until reconciliation/retention closes them.

**Retry policy:** a network timeout, adapter crash, gateway timeout, stream/body error, unknown usage or ambiguous provider result moves the attempt to `unknown`. On any subsequent inbound request while an attempt is unresolved, the adapter performs a read-only gateway/journal reconciliation; it does not forward. If an explicit, *verified* OpenCode model-call ID exists, an exact retry may be associated with the old attempt ID and returned a recorded result or unresolved conflict. Without that ID, the adapter reports a Run-level `ACTIVITY_UNRESOLVED` and parks **all** model egress for this Run until authoritative reconciliation or an authorized new Run generation. It must not label the inbound request as either retry or new call from content or timing. A new model-call ordinal is allowed only after the preceding call is definitively completed/reconciled or definitely unstarted, and the adapter has observed a new inbound request; a new physical-attempt ordinal after unknown is forbidden. If OpenCode requires automatic provider retries, disable them or require a verified retry-aware hook/protocol that supplies a durable call ID and exact retry decision before forwarding.

**Counterexample:** OpenCode sends POST body B; gateway/provider processes it, but the response disappears. OpenCode retries POST B. Separately, OpenCode may intentionally make a second model call with exactly B (same model, messages and parameters). At the adapter's HTTP boundary those POSTs can have identical headers/body and arrive on different connections after restart. A fresh UUID per POST double charges/replays the unknown first call; a body hash merges two legitimate calls. No local stateless proxy or `chat.headers` value can decide which history occurred. The safe behavior is to retain the first attempt's ID/journal and reject or reconcile later traffic, with no second provider send.

## RunView and recovery invariants

The attempt row's generation/container/session must equal the persisted RunView binding and inspected engine facts on **each** forwarding/reconciliation path. Retain the adapter journal and RunView HOME across crashes and stop requests; no new container/adapter generation may replace an unknown one. On restart, the controller reattaches only the exact labeled generation, rechecks network routes and credentials, loads `forwarding` as `unknown`, and queries gateway journal/usage by attempt ID. If journal, secret material, provider result or container identity is missing/contradictory, keep the Run paused/parked and budget hold intact. Revocation stops new admission immediately; it never erases unresolved accounting. Cleanup waits for durable terminal Run, no unresolved attempt/start journal, and retention expiry.

## Acceptance and environmental gates

Unit/property tests: duplicate row/nonce, process crash after journal commit and before `Do`, after `Do` and before headers, after headers and before body, lost response after provider success, two workers racing one attempt, changed body/model, stale RunView, canceled/expired grant, DB outage, result-write failure, key rotation and retention. Assert provider invocation count, charge row count, budget hold and exact journal state; an HTTP status alone is insufficient.

Live fixture: build the pinned Linux image, configure its actual provider base URL to the adapter, trace one real OpenCode call through adapter/gateway/mock provider, then inject a lost response and restart OpenCode, adapter and platform independently. Verify the same attempt ID remains in journal, no second provider invocation occurs, a distinct call after complete resolution gets a new ID, and budget exhaustion blocks traffic before provider contact. Inspect container network and attempt direct gateway/provider/IP/DNS/proxy/custom-provider connections; all must fail. Test both supported architectures or constrain deployment to the tested one. Publish image digest, network policy, route trace, DB evidence and verification commands. Until those gates pass, T19 activity identity remains open and paid model egress stays disabled.
