# Issue 72 R8 producer audit (read-only)

Observed integration HEAD: `5b071dcea17ce57ceec8f6681bffe222eabd870e5` (`.worktrees-issue72/lago-int`). Source review only; no DB/Docker execution and no application changes.

## Verified producer paths

- **Payment confirmation:** `internal/handler/payment_callbacks.go:64-184` verifies channel callbacks and calls `OrderStore.ConfirmPayment`. `internal/modules/commercial/repository/commercial/order.go:706-854` is the durable admission point. In one transaction it guards pending→paid by order version, then inserts `commercial_outbox_events` kind `fulfill`, key `fulfill:<order-id>`. A duplicate winning transaction is a no-op; a distinct later successful collection records `commercial_payment_anomalies` and inserts kind `over_payment` keyed by order/provider/merchant/transaction. `RecordPaymentAnomaly` for amount/currency mismatch runs after the confirmation transaction rolls back (`order.go` after ConfirmPayment; `payment_anomaly.go:90-155`), so mismatch retention is durable but does not enqueue an outbox event.
- **Fulfillment/recovery:** `internal/modules/commercial/service/commercial/fulfillment.go:176-236` `Recover` leases pending `fulfill` and `over_payment` events; `:242-279` uses guarded `lease_until`/`lease_token` updates and increments attempts. `:283-405` validates the event envelope, re-reads the order, finds existing benefits before applying, and only marks sent/fulfilled after explicit external receipts. `:407+` validates and disposes over-payment anomalies. `StartBackground` (`:200-236`) runs an immediate pass plus a 30-second ticker; container registration/clean shutdown is `internal/container/container.go:2489-2501`.
- **Usage / settlement:** final usage facts are recorded by `internal/modules/commercial/repository/commercial/usage.go:90+`; only final revisions emit `usage_settlement` in the same transaction. `internal/modules/commercial/service/commercial/settlement.go:180-290` (`Finalize`/`persistFinalize`) atomically writes usage, settlement record, reservation conversion, and outbox key `usage_settlement:<tenant>:<call>:<attempt>:<revision>`. `:336+` `Dispatch` scans pending events and replays the stable key; indeterminate gateway results leave the event pending and settlement unknown, while confirmed evidence is required before release. There is no scheduler shown in this service; callers must invoke `Dispatch`.
- **Refund/admin action:** `internal/modules/commercial/repository/commercial/refund.go:270-340` approval (`Approve`/review path) atomically moves refund to pending and emits `refund_payout:<refund-id>`. `MarkRefundChannelResult` (`:342-400`) applies guarded version transitions, stores unique provider refund identity, releases locks only on confirmed failure/not-created, and marks payout outbox sent after leaving pending. The repository contains no autonomous refund ticker in the inspected path; dispatch/worker wiring requires caller inspection.
- **Channel queries / anomaly admin:** callback verification and lookup are in `internal/modules/commercial/service/commercial/order.go:380-730` and handler adapters; they call `ConfirmPayment` or `RecordPaymentAnomaly`, not a separate queue. `internal/handler/commercial.go:1221-1234` exposes admin anomaly resolution, which only guarded-updates anomaly state/version and does not enqueue work. `OrderStore.HasUnresolvedPaymentAnomaly` is a read-side attention signal.
- **Generic outbox contract:** `internal/modules/commercial/repository/commercial/outbox.go:24-78` defines `pending/sent/dead`, unique event key, and `EnqueueTx` atomic insertion. The store itself has no producer allowlist and does not expose an operational drain/fence API.

## Verified replay / retry properties

- Payment callback replay is protected by payment-attempt transaction identity and guarded order version. Outbox duplicate keys return `ErrOutboxEventDuplicate` (over-payment path treats it as success).
- Fulfillment has durable leases but lease expiry allows a later worker to retry after a crash. Per-line `FulfillmentRecord` keys and remote `FindBenefit` before `ApplyBenefit` provide the intended exactly-once/recovery behavior; transient/unknown outcomes remain pending or attention.
- Settlement replay is keyed by final revision. `errSettlementReplay` rolls back the entire finalize transaction; dispatch leaves indeterminate events pending for same-key retry. `Dispatch` itself does not claim/lease rows, so concurrent invocations can both call the gateway unless the gateway/idempotency contract prevents duplication.
- Refund state transitions are optimistic-version guarded and provider refund IDs unique; the inspected code does not establish how pending refund outbox events are selected, leased, retried, or drained.

## Control-plane evidence that can prove admission/in-flight/drain (and limits)

Evidence sufficient for payment/fulfillment admission: query `commercial_outbox_events` grouped by `kind,state`, inspect `event_key`, `attempt_count`, `lease_until`, and non-empty `lease_token`; join `commercial_orders` and `commercial_fulfillment_records` to show paid vs fulfilled and external receipt IDs. A point-in-time sample where no pending eligible rows exist, no unexpired leases exist, and all paid orders have terminal fulfillment state supports “drained at that instant.” It cannot prove no callback can arrive after the sample.

For anomalies, query `commercial_payment_anomalies` by state/version and compare over-payment rows to corresponding `over_payment` events. Admin resolution is state-only and cannot prove disposal completion; the event must be `sent` and the anomaly retained/resolved according to policy.

For usage, query settlement records joined to `usage_settlement` events: pending/unknown/dispatched/accepted states are in-flight or unresolved; confirmed plus sent is the strongest local completion evidence. Because `Dispatch` has no lease/fence, local DB state cannot prove that two concurrent dispatchers were excluded; provider idempotency and gateway audit evidence are needed.

For refunds, local proof requires refund state, `channel_attempts`, provider refund identity, allocation locks, and payout event state. The inspected repository does not prove a running worker, global admission fence, or complete drain. Any R8 runbook must identify the concrete refund dispatcher/scheduler separately.

## Inference / recommendation

Inference: the commercial payment/fulfillment path is durable and replay-oriented, but fencing is per fulfillment event lease, not a global commercial admission fence. Recommendation: before declaring a maintenance window drained, freeze callback ingress and all producer endpoints, record a timestamped snapshot of the above tables, stop/verify fulfillment background loop, and independently verify settlement/refund dispatchers and external provider in-flight work. Code alone cannot prove external calls have quiesced or that a later callback will not create a new event.
