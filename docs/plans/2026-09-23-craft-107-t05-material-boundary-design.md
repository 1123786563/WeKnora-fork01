# T05 / #124: enforceable selected-material boundary

Date: 2026-09-23. Read-only architecture recommendation for the controller. Authority: `CONTEXT.md` Workspace/Run definitions (lines 209–215), approved `docs/specs/2026-09-23-craft-web-artifact-spec.md` (lines 57–65, 76), ADR-0004, T05/#124 brief and DAG, T05 fix-1 checkpoint and independent re-review. No production source or requirement was changed.

## Decision

Give each admitted writing Run a **fresh execution sandbox and OpenCode session** with a private filesystem view. Keep the Task's single persistent Workspace as the durable draft and version source, owned by WeKnora. At Run admission, materialize an allowlisted copy of the current draft into the fresh sandbox, and mount/copy only this Run's selected, authorized source package at `/workspace/knowledge` read-only. The sandbox must have no mount, API credential, shared work directory, or host path reaching the persistent Workspace, prior Run material, or another Run's sandbox. After execution, copy back only validated draft/output paths under the writer lease; retain the old default Artifact until build, preview, and page-load evidence permits immutable promotion.

The execution root may contain the prior **authored draft** so the user can continue the same page. It must exclude prior raw source packages, manifests, cache, hidden OpenCode session state, and arbitrary old Run files. A draft may contain facts previously incorporated from A; this design enforces isolation of raw selected material, not erasure of information already written into the Task's page. If the product intends revocation to erase those facts too, that is a separate requirement needing content provenance and redaction/rebuild policy before delegation.

## Required filesystem and authority layout

| Surface | Run B can read? | Owner / rule |
| --- | --- | --- |
| Durable Task Workspace draft and version store | No direct mount | WeKnora server; exported through an allowlist of editable project files only. |
| Run A `knowledge/runs/run-a/**`, old manifest, OpenCode history and caches | No | Stored outside Run B root; never copied or mounted. A's immutable source record stays server-side for old version citations. |
| Run B `/workspace/project/**` | Yes, writable | Fresh copy of current draft, excluding reserved `knowledge`, `inputs`, session data and symlinks; inspect canonical paths and file types. |
| Run B `/workspace/knowledge/**` | Yes, read-only | Exact sealed package for authoritative server Run ID B, with checked digest/record and currently authorized selection. No sibling Run paths. |
| Run B `/workspace/inputs/**` | Only chosen/acknowledged uploads | T01 input manifest, not every Task-associated upload. Opaque uploaded code stays read-only and unexecutable. |
| Network and service credentials | No general egress, no business API tokens | Sandbox policy; local OpenCode service must not expose a file/API escape into the host. Preview uses isolated origin. |
| Old successful Artifact | Via viewer only, outside execution sandbox | Immutable version remains visible while B runs; it is not a writable project mount. |

Use an explicit `RunExecutionView`/equivalent port: `(tenant, task/session, authoritative run ID, writer lease/fence, draft snapshot ID, selected material digest, selected input digests, sandbox binding)`. The server prepares it and the runtime consumes it. A prompt path or client-supplied `runID` is not a capability. The runtime must verify the admitted Run binding and package digest immediately before dispatch, and refuse execution if the view cannot be enforced. Bind the Run ID to the package, record, sandbox metadata, and result collection; retries reuse the sealed package and exact sandbox state or park unknown, rather than rebuild different bytes under the same ID.

## Publication and failure sequence

1. Acquire the Workspace's single writer lease; resolve selected documents and TaskWrite under the initiating member's current grant. Build the bounded source package in **server-private temporary storage**, verify each file and manifest digest, and write the immutable actual-source record with a publish state/key. An existing Run record with different selection/query/digest rejects before any visible file mutation.
2. Atomically seal the package (rename or content-addressed object plus compare-and-set pointer). A DB/file partial failure leaves no delegable package; retry either completes the same bytes or fails closed. A stale temp package is garbage collected later. Recheck source grants before sandbox creation/dispatch; loss of grant aborts B before material is exposed.
3. Create a fresh sandbox with a private writable project volume and a separate read-only Run B knowledge volume/copy. The current `RemoteVolumeMount` shape has only `Name` and `Path`, no read-only flag; Docker explicitly rejects volume mounts. Therefore this requires a new read-only mount contract/provider implementation **or** verified copy into a fresh sandbox followed by immutable permission and no host/peer access. Unix mode alone is insufficient if the sandbox user can change ownership or reach the backing volume. Provider capability absence fails closed.
4. Export only draft project files from the persistent Workspace through a server-side allowlist; reject symlink/hardlink/device/path traversal and reserved names. Dispatch OpenCode in this sandbox, not in a reused session that retains A in prompt/history/tool state. No shared local serve root, global `inputs/`, or mutable `output` symlink may bridge Run A/B.
5. On success, collect only allowlisted outputs from B and validate build, preview reachability and page load. Compare the writer fence before draft copy-back and Artifact promotion. A failed, stopped, unknown, or stale-fence Run may retain a private draft for recovery, but cannot replace the default version. Preserve old successful version and its original source record. Cleanup of Run sandbox/material is post-settlement and never the confidentiality mechanism.

## Current seams and migration cost

- `internal/container/craft_runtime.go:180–233` currently stages inputs, repoints output and delegates against one local OpenCode serve; `ensureWorkspace` reuses one OpenCode session (`269–299`). `pointWorkspaceOutput` uses a shared work-dir symlink (`336–371`); `stageWorkspaceInputs` writes all Task-associated inputs into a shared `inputs/` tree (`374–467`). This runtime cannot claim per-Run confidentiality and should fail closed for selected knowledge until replaced/bounded.
- T05 fix-1 `BuildForRun` writes `knowledge/runs/<runID>` within one Workspace and saves the record only after writes (`craft_knowledge.go:122–140`, `KnowledgeRunDir`). The re-review confirms old A remains readable and same-Run retry can mutate bytes before insert-once rejects. Keep its ACL, bounding, citation and truncation logic; move publication behind a sealed package port. Avoid copying its legacy `Build` output into Run B.
- `internal/modules/execution/sandbox/remote_client.go:104–137` exposes named mounts without read-only semantics; `docker_remote_client.go:261–269` returns unsupported for mounts. Provider-neutral read-only capability must be explicit and tested, or use a fresh isolated sandbox plus verified server upload of the sealed package. A subdirectory or prompt instruction does not enforce reads.
- This changes runtime binding/recovery: one persistent **logical** Workspace can have multiple sequential physical Run sandboxes. Store the current Run sandbox and package digest alongside the durable Run, while persistent Workspace/version identity remains stable per ADR-0004. Existing `OpenCodeSessionID` reuse cannot continue for knowledge-bearing Runs because session memory can carry A.

## Ownership and dependency recommendation

- **T05 backend correction:** own sealed package construction and insert-once record consistency in `internal/application/service/craft_knowledge.go`, its package/store port, and focused failure/retry tests. It consumes T08 Task access and authoritative Run admission. Do not mark #124 verified at this seam alone.
- **T20 runtime integration:** own the admitted Run binding, fresh sandbox/OpenCode session creation, draft export/import, selected upload + knowledge attachment, provider capability checks, and `internal/container/craft_runtime.go` integration tests. It consumes T05 sealed package, T01 chosen inputs, T08 authorization, T16 writer fence, and Artifact validation. The DAG should record these as integration prerequisites; T20 must not substitute a prompt-only path for the runtime view.
- **Sandbox module support:** backend implementer owns `RemoteCreateRequest`/provider read-only mount semantics if that route is chosen, with Docker/E2B capability tests. This is a prerequisite to T20's mount implementation. A fresh-sandbox server-copy route avoids the provider mount extension but still needs a real filesystem/credential isolation test.

## Minimum behavioral proof

At the actual delegate filesystem/API seam, run A with KB A, revoke A, then run B selecting only KB B. In B, reading `/workspace/knowledge` finds only B; attempts to open A's old absolute path, sibling path, old session history, or shared-root path fail. B can read/edit the continuing draft, but cannot read an unchosen upload. Repeat with no selected knowledge (empty mount), same-Run conflicting retry, writer/record partial failure, sandbox creation failure, stale writer fence, stop/unknown recovery, and old-version citation opening under the viewer's current grant. The test must execute or inspect from **inside B's actual sandbox identity**; map-prefix assertions in a fake writer are insufficient. Provider-specific deployment tests must verify read-only behavior and absence of host/peer mounts and egress.

Alternative: atomically replace a dedicated knowledge tree in the existing sandbox before every Run. This is smaller in code but weaker: old bytes may remain in snapshots, open handles, session memory, shared serve caches or concurrent sandboxes; replacement failure and unknown Run state complicate recovery. It should not be accepted without proving all of those paths inaccessible. Fresh per-Run execution is the defensible boundary for the approved selected-only promise.
