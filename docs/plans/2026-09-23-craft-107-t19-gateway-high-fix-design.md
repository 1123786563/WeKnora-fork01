## High 1: response body outlives the start callback

`Forward` creates a request with the caller context, then inside `StartBinding` creates another timed context and `defer cancel()` around `Do`. `StartBinding` also defers its own bounded-context cancel. Both return before `io.ReadAll(resp.Body)`. Go's transport keeps that request context attached to the response body, so a delayed/streamed body can be canceled after successful initiation. The handler also leaks `resp.Body` on a `startErr` after `Do` returned headers.

Use two lifetimes: an **initiation deadline** owned by `StartBinding`, and a **whole upstream response deadline** owned by `Forward` through body read/close. Create the latter before the callback from the inbound request with a bounded deadline, and defer its cancel only after response handling. Inside the callback, check `startCtx.Err()` immediately before `Do`, then use the whole-response context on the outbound request. The callback reports `Started` only after `Do` returns a nonnil response; it must not read body under the journal transaction or start callback. `StartBinding` still decides `unknown` if its own deadline expires around `Do`; never treat that as a definite non-start. On every non-success return after `Do`, close a nonnil body, record unknown usage if the activity may have been attempted, and preserve the journal/hold for reconciliation. On body read error or truncation, keep the activity non-replayable and usage unknown. A response-header success is **initiation evidence**, not a complete usage or model-result observation.

One nuance: `Forward` cannot simply pass `context.WithoutCancel(startCtx)` to `Do`; that would drop the caller's cancellation and deadline. The response context must be derived from the inbound request with an explicit whole-response timeout. Test headers arriving first, body arriving only after the start callback returns, slow body timeout, inbound cancellation, `Do` returning `(resp, err)`, and no-body/nil-body cases. Ensure the timer is not canceled before `Close`.

## High 2: no trustworthy activity ID in production model traffic

The gateway requires `X-Craft-Activity-ID` and hashes it with credential tenant/run/grant. That authenticates scope but **not the raw ID's relationship to an actual OpenCode model attempt**. The Go `opencode.Client` sends WeKnora→OpenCode session requests; adding a header there cannot make OpenCode forward it in OpenCode→model-provider requests. `docker/craft/runtime-config.json` says model access uses the server gateway, but neither the pinned lock nor checked-in image config proves a per-model-request header hook. Do not derive the activity ID from request body, model name, prompt hash, timestamp, TCP connection, or gateway-generated random value: those cannot distinguish a new physical model attempt from a retry after an unknown send.

Required contract: before **each physical model provider attempt**, a server-owned runtime or sidecar durably records `(tenant, run, delegation, model-call ordinal/attempt ID)` and places the same opaque ID on the outbound gateway request. A retry of that attempt reuses the ID and reconciles its journal/usage without calling the provider again; a deliberately new model attempt receives a distinct ID. The gateway validates the ID against the authenticated execution credential and a durable attempt record (or a signed, narrowly scoped attempt token issued only after that record commits); a syntactically valid caller-selected header is not sufficient authority. `StartBinding` remains the one-shot durable charge-start fence.

The narrow viable adapter, if pinned OpenCode has no hook, is a **per-Run model egress sidecar/proxy** that terminates OpenCode's configured provider endpoint, authenticates the container identity, allocates and persists an attempt ID before forwarding, and injects the gateway header. It must own provider-request retry policy: after an ambiguous forward it cannot mint a new ID and resend; it observes/reconciles or parks. A plain HTTP proxy that generates a fresh header for every inbound POST is unsafe, and a body hash is not an attempt identity. It needs private per-Run network routing, no direct provider egress, and a persistent attempt journal correlated to RunView/container generation. If OpenCode 1.18.4 does support a verified pre-request hook with durable model-call identity, use that smaller hook instead; no such capability is established by the current repository evidence. Keep the gateway fail-closed until a live pinned-image test shows the exact propagation and retry behavior.
