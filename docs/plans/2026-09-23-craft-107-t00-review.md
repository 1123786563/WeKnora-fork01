**Reviewed checkpoint:** `t00-checkpoint-01`, digest `f3f0eae50510c6094ab04c33b7aad701e7cf7862e30ebf708d8ba69984ed5d63`; BASE and HEAD are both `4bcad69baf033a1310b4dce1372c8153e66adc81`. I read the approved Craft web-artifact Spec, ADR-0004, CONTEXT.md, the #119 snapshot, T00 brief and Task 0 plan. This was a read-only code review; I did not rerun the controller's tests or OCR. The implementer reports all five required verification commands passing, but those results are not an independent execution result here.

## Verdict

- **Spec compliance: changes required.** Input recognition, four independent web checks, stop and writer outcome enums, budget/share/export record types, legacy optional DTO fields, and the ownership matrix are present. The frozen export manifest cannot represent each derived file's origin, which the approved Spec requires the owner to see before consent. The route seam also lacks the containment needed to make feature registrations safely independent.
- **Code quality: changes required.** No active unauthenticated endpoint is introduced by this checkpoint. The production router passes a Viewer+ and chat API-key guarded `sessions` group, and the slot is empty by default. However, the slot gives registrars unrestricted `GET`/`POST` access to that group, and its test substitutes a raw Gin group with a single test header guard. The parser also silently accepts a malformed recognition `reason` value. I found no direct change to Task ID / Session ID identity or historical-version restore behavior.

## Findings

### Important — Frozen export manifest omits required origin evidence

**Evidence:** `internal/modules/craft/web_contracts.go:183-203` defines each `ExportFile` as only `Path`, `SHA256`, and `Restricted`; `packages/contracts/src/craft/web-artifact.ts:19-20,72-75` freezes and parses the same shape. The approved Spec's User Story 24 and Implementation Decision on source download require a manifest of derived data files **and their origins** before owner confirmation. Task 0 calls this the public typed `ExportManifest` consumed by T12/T13; the ownership matrix reserves its public Go/TS files for T00 and T20.

**Impact:** T13 cannot present or bind the exact source origins to an export decision through the frozen public manifest. Later lanes would need an unplanned contract edit or a parallel ad hoc payload, risking a consent decision made without the required provenance.

**Smallest correction:** Add a typed, immutable origin reference list to each export file on both public contracts and parsers, and test that a derived file's origins survive manifest parsing/serialization and are included in the digest-bound consent view. Keep original-source authorization separate from this descriptive metadata.

### Important — Route slot does not confine feature paths to the Craft Task namespace

**Evidence:** `internal/handler/session/craft.go:107-110` exports the raw `GET`/`POST` route-group interface. `internal/handler/session/craft_features.go:56-70` passes that whole group to every mount callback; the name check at lines 28-53 validates only the registry key, not the paths registered by the callback. The production caller in `internal/router/routes_chat.go:197-202` passes the general `/sessions` group, whose API-key wrapper registers one chat policy per route (`internal/router/rbac.go:356-381`). Gin's group path joining cleans `..` segments. `internal/handler/session/craft_features_test.go:35-67` uses a raw group and checks only a normal `/:id/craft/<name>` path.

**Impact:** A feature can register an endpoint outside `/:id/craft/...` / `/:session_id/craft/...`, including a sibling namespace after path cleaning, while inheriting the session group's Viewer+ and chat-key policy. This undermines the promised stable Craft-only extension boundary and can give an unintended route the wrong policy. It is a construction-time risk, not an observed remote exploit in the current empty registry.

**Smallest correction:** Give callbacks a constrained Craft feature registrar that validates a canonical path under the appropriate Task Craft prefix and rejects traversal, absolute or sibling paths before calling the guarded group. Add a production-router test for an attempted escape and for inheritance of both Viewer+ and API-key policy on an allowed route.

### Minor — Recognition parser coerces a malformed field to an empty reason

**Evidence:** `packages/contracts/src/craft/web-artifact.ts:44-51` reads `reason` with `typeof v.reason === 'string' ? v.reason : ''`. An object such as `{ accepted: true, understood: true, reason: 17 }` is accepted, despite the public `CraftInputRecognition.reason: string` contract and Task 0's malformed-payload rejection requirement. `packages/contracts/src/craft/web-artifact.test.ts:20-25` covers the valid and legacy cases but no wrong-type reason.

**Impact:** A malformed new response is silently normalized, which can conceal server/client contract drift. This does not by itself authorize a Run or grant access.

**Smallest correction:** Require `reason` to be a string whenever `recognition` is present, while continuing to default the entire absent legacy `recognition` field to `null`; add a wrong-type parser test.

### Minor — Implementer report states an unreproducible aggregate checkpoint digest

**Evidence:** `docs/plans/2026-09-23-craft-107-t00-report.md` states that SHA-256 of sorted `shasum -a 256` lines for the 14 owned files is `b734861eefc61d2c13853cf125deb9060cc7ce3193bdb330465264caeedf1f9e`. Reconstructing those lines from the formal `manifest.json` in path order yields `9456e86c4d60609fb7f9762885c9c876f7e694824c844b07501608e7db9aba9d`. All 14 individual file hashes match the formal manifest, so the code under review is identifiable despite the report discrepancy.

**Impact:** The report's aggregate claim cannot be used to bind its test evidence to this checkpoint. It is an evidence and documentation defect, not evidence that the reviewed code changed.

**Smallest correction:** Correct the reported digest or document the precise alternative byte sequence and command that produced it; keep the formal per-file manifest and checkpoint as the review identity.

## Review notes and test evidence limits

- The four web outcomes are independent and `Ready()` requires all four passed (`internal/modules/craft/web_contracts.go:72-88`); `not_run` and invalid enumerants do not pass. The new Go test checks the page-load gate, but it does not vary each of the other three gates. A small table over all four fields would protect this release predicate if T15 later relies on it.
- The stop and writer records preserve `unknown` as an explicit status (`web_contracts.go:90-128`). These are facts only; later lifecycle services must retain the writer fence until authoritative resolution. This checkpoint neither implements nor claims that behavior.
- The optional `recognition` and `web_evidence` fields are omitted from legacy Go DTOs and default to `null` in TypeScript (`internal/handler/session/craft.go:305-338`; `packages/contracts/src/craft/index.ts:277-342`). The run budget pause is TypeScript-only at this stage; the T00 report explicitly leaves Go emission to T19/T20. Existing-route preservation is supported by the implementer's reported handler suite, but the route-slot test itself is a unit test with a synthetic header guard, not a production API journey test.
- The implementer reports `go test ./internal/modules/craft/...`, `go test ./internal/application/service/... -run Craft`, `go test ./internal/handler/session/... -run Craft`, `pnpm test:shared`, and `pnpm typecheck:web` all exiting 0. I did not duplicate those runs. The exact reviewed 14-file content matched the checkpoint manifest when inspected.
