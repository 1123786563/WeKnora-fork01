# CRAFT-107 T08: separate Task owner from Run actor

## Evidence and failure

`CraftSessionService.writeSession` authorizes a Collaborator with `TaskWrite`, then loads the Task's stored Session. `StartRun` deliberately derives `ownerScopeOf(session)` for workspace/version lookup, but also sends `Admission.UserID=session.UserID`. `AgentRunStore.Admit` uses this field to lock `sessions.user_id`, scope `(tenant, owner_id, request_id)` idempotency, store `agent_runs.owner_id`, and validate T01 `input_admission` claims. Thus simply changing `Admission.UserID` to the Collaborator would break the storage foreign key and T01 claim fence. On worker recovery, `Run.UserID` is read from `agent_runs.owner_id`; `ExecuteDurableRun` puts `run.Owner` (the **lease worker owner**, not either human) into `types.Principal`, and tool metadata uses `run.UserID` (Task owner). Capability assembly reads this context, so the current durable path can authorize or attribute a Collaborator Run as another principal. The same issue affects follow-up admission, which copies the prior `run.UserID`.

## Narrow invariant and interface change

Keep existing `Admission.UserID`/`Run.UserID`/`agent_runs.owner_id` as **Task storage owner** for session locking, workspace, input claims, RunView owner key and existing idempotency index. Add an immutable **`ActorUserID`** to `Admission`, `Run`, and `agent_runs.actor_user_id`; it is the authenticated user who requested this Run. The repository must require actor for newly admitted Craft Runs and atomically persist it with the Run; legacy non-Craft admissions may default actor to owner only where their existing semantics require that. A new migration (Postgres and SQLite, coordinated with migration owner) adds the column without rewriting historical Craft actor facts. Existing in-flight rows without actor must fail closed for actor-scoped capability use, or be reconciled with an independently verified admission audit record; do not infer a Collaborator from current Task membership or silently use owner credentials.

At `StartRun`, after `TaskWrite`, derive actor from authenticated `types.CallerFromContext(ctx)` and require tenant/user equality with the request scope. Preserve `ownerScopeOf(session)` for storage and `claimInputDecisions`; pass `ActorUserID=scope.UserID` separately. Bind the actor into the idempotent request: same `(tenant, Task owner, request_id)` and same payload with a different actor returns conflict, not another user's prior Run. This check must happen in `AgentRunStore.Admit` against the persisted actor; `StartRun`'s prior-run lookup can remain owner scoped for recovery but must not return a cross-actor replay. T01 claim keys and their `(tenant, Task owner, session)` rows remain unchanged; claim/replay additionally checks that the admitted Run actor equals the current caller before returning it. Do not rekey input claims to actor, which would permit two Collaborators to claim the same Task input decision.

Worker recovery uses `run.ActorUserID`, **never `run.Owner`**, to restore `types.WithCaller`, `types.WithPrincipal`, and any legacy `UserID` context before `prepareAgentCapabilities` or tool registration. `run.Owner` remains the lease fence identity only. Before capability assembly, recheck the actor's current Task role and resource grants; revoked Collaborator access fails/parks without switching to Task owner. Tool execution metadata `ToolExecContext.UserID` becomes actor ID. Storage writes and artifact/version ownership continue to use Task owner. Follow-up Run admission carries the prior actor only after checking that actor can still write the Task; a worker lease has no authority to choose a new actor. Do not put actor only in the mutable model snapshot: the Run row is the recovery authority.

## Sequential implementation ownership

1. **Schema/contracts/repository** — `internal/modules/agentruntime/agent/runtime/contracts.go`, `internal/application/repository/agent_run.go`, paired versioned/SQLite migrations and repository tests. Add immutable actor field, atomic persist/load, replay conflict, and legacy policy. Coordinate migration number with current T08/T19/RunView changes.
2. **Craft admission** — `internal/application/service/craft_session.go`, `craft_inputs.go` only if claim replay needs explicit actor query, and focused Craft service tests. Preserve owner-scoped workspace, Version, RunView and claim keys; assert owner versus Collaborator actor and foreign-key validity.
3. **Worker and tools** — `internal/application/service/agent_run_graph.go` and focused worker/capability tests. Restore Caller/Principal from durable actor, check current Task access, pass actor to tool metadata and follow-up admission. If capability assembly cannot distinguish storage owner from authorization actor, add one typed context/binding at its entrance rather than rewriting ownership of Session or Run.
4. **Assembly review** — inspect `internal/application/service/agent_capabilities.go`, tool registration and connector/MCP call paths for any remaining owner fallback, with tests for owner-only personal connector denial, collaborator-owned grant acceptance, revoked actor on retry, worker restart, and lease-owner string never appearing as web principal.

## Acceptance and migration risk

Run created by Collaborator C on owner O's Task remains keyed/stored under O and passes T01 input decision claim once; audit, capability assembly, OAuth/connector identity and tool event metadata use C. Same request ID replay by C returns exactly the same Run; replay by O or another Collaborator conflicts. Restart on a different worker restores C; changing worker lease owner does not change authorization. Removing C's access before retry prevents new capability use and does not silently substitute O. Old rows without independently proven actor cannot safely execute personal capabilities. A `TaskWrite` check alone does not grant owner personal credentials; connector-specific grants must still be checked at execution time.
