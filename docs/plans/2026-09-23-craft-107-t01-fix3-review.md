## Verdict

- **Scoped R3 Spec compliance: PASS.** Claim identity and a server Run ID are persisted before Submit. The repository checks the current token, Run and Session under the same transaction that inserts/replays the Run and marks claims admitted. Recovery rotates an expired token only with a compare-and-swap and preserves the Run ID. Cancellation contends with the same claim row. A missing claim bundle is rejected for a Craft session with pending or legacy admission fences.
- **Scoped code quality: PASS with PostgreSQL validation pending.** The typed claim stays in internal `Admission`, not an HTTP field. Fresh admission requires a live lease; stale/expired tokens fail. Existing committed Run replay is checked by request hash and Run ID. I independently reran the focused repository admission tests and T01 service tests; both passed. The implementer reports full service/repository/runtime package passes, but handler/session retains a documented preexisting acceptance-test mismatch. PostgreSQL row-lock interleavings were not exercised; `TRPC_TEST_POSTGRES_DSN` was unset in the implementation run.
- **Full #120 compliance: FAIL pending other gates.** Per-Run read isolation and read-only input mount remain unimplemented here. The product frontend decision/retry and real joined route need their own reviewed checkpoints. This R3 pass does not close the Ticket.

## Evidence and limits

`claimInputDecisions` locks each decision/admission row, requires a matching continue hash, writes a UUID token, preallocated Run ID and bounded lease (`internal/application/service/craft_inputs.go:381-450`), and on recovery checks for the exact scoped Run before rotating the expired claim via token/state/lease CAS (`:453-526`). `StartRun` passes that exact claim bundle to `Submit` (`internal/application/service/craft_session.go:771-803`) and intentionally retains claims after ambiguous Submit errors (`:804-816`). `AgentRunStore.Admit` locks the Session and claims, checks Run/key/token scope, rejects an expired lease on a new insert, inserts/replays the Run, and transitions claims to `admitted` in its transaction (`internal/application/repository/agent_run.go:125-199,273-380`). Focused tests include stale token, expired lease, no-claim bypass, restart after abandoned claim, committed replay, cancellation race and ordinary admission compatibility.

The admission migration's `admission_state` is `NOT NULL DEFAULT ''` in **both** dialects, so legacy rows have an empty state. The repository's `admission_state <> 'admitted'` predicate (`agent_run.go:219-220`) includes those rows. A SQL `NULL` bypass would require a schema outside this reviewed migration and is not a finding against this checkpoint.
