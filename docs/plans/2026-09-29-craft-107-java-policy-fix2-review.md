## Finding

### HIGH — Java `@argfile` bypasses the module path screen

- **Evidence:** Oracle's [Java 21 launcher documentation](https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html) specifies that `@argfile` contents are expanded before option processing and may contain the main class and all launcher options. In `internal/modules/craft/input_code.go:371-485`, a Java token such as `@/workspace/inputs/launch.args` is neither an option nor a specially recognized argument file. It becomes the first `scriptSeen` operand; `canonical(workingDir, arg)` receives the literal leading `@`, so it does not identify `/workspace/inputs/launch.args`. The policy allows it. An uploaded `launch.args` containing `--module-path /workspace/inputs/mod.jar -m app/main` then supplies the screened module option and uploaded modular JAR to the real launcher after policy review. The new module-path tests (`input_code_round2_ocr_test.go:264-334`) cover literal argv options but no argument-file expansion.
- **Impact:** Uploaded code can execute through the same Java module route that Fix2 intends to close, violating the approved Spec's rule that uploaded code is never directly executed. This is a policy bypass even when the module-path and patch-module parsers handle their literal argv forms correctly.
- **Smallest defensible correction:** Fail closed on Java `@argfile` tokens before treating them as a script or data operand, including wrapped Java commands; if generated argument files must be supported, resolve and parse their bounded contents under an approved trust boundary and rescreen the expanded option stream. Add a regression where `java @/workspace/inputs/launch.args` is denied, plus a generated argument-file case that demonstrates the chosen policy.
