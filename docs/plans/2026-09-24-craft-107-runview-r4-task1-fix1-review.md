## Findings

1. **Medium — message-ID adoption is not idempotent under concurrent retry or a conflicting request.** `adoptExecutorMessageID` updates `craft_delegations` by tenant/Run/tool-call/Workspace and current Run epoch, but does not condition the update on the prior `prompt_message_id` or verify the stored request (`internal/container/craft_runtime.go:407–440`). Two executions holding the same UUID can each mint a different `msg_` ID and overwrite the row; a second update after the first executor's `PrepareTask` can cause two distinct prompts. A different task with the same tool-call and Workspace can also overwrite the saved `task_json` before `PrepareTask` applies `sameDelegationRequest`. The new tests cover a stale epoch and one successful update, not this same-epoch race or request mismatch (`craft_runtime_r4_seed_execute_test.go:122–147`). **Impact:** duplicate or substituted delegated work can cross the durable request identity boundary. **Smallest correction:** compare the existing delegation request with the incoming request, then use a conditional update on the expected old message ID and current epoch; on a lost CAS reload and adopt the already persisted `msg_` ID only if the request matches. Test concurrent same-request adoption and a different-request collision.

2. **Medium — required Execute acceptance cases remain untested.** The new production-boundary fixture proves empty revision, frozen D1 with current head D2, exact completed retry, 21 MiB acceptance, >50 MiB rejection, wrong Run/Workspace/epoch, changed object bytes, and no dispatch for those rejections (`craft_runtime_r4_seed_execute_test.go:25–120`). It does not set up a partially seeded output and retry, nor create a V1/default pointer and verify it remains unchanged after a failed B. The fixture's executor simply returns `failed` and has no Version store (`:163–172`, `:186–286`). **Impact:** R4 Task 1's partial replay and unchanged-default acceptance remain unproven, including the user-facing failed/stopped continuation scenario in the approved Spec. **Smallest correction:** add a partial output replay case through `Execute` and a scoped persisted Version/default fixture (or a higher existing service seam) that proves failed B preserves V1; keep Task 2's candidate/promotion work separate.

## Verified corrections and limits

- `readRunViewDraftObject` accepts a declared size through 50 MiB, reads at most declared size plus one byte, and checks exact length and SHA-256 (`craft_runtime.go:655–681`). The 21 MiB Execute test passes; a 50 MiB + 1 declared file rejects before object fetch. The focused suite does not test the exact 50 MiB boundary, but the integer bounds are direct and consistent.
- Output inspection compares preflight `Fstatat` with opened `Fstat` for file type, mode, single link, size and device/inode; it rechecks the open descriptor and path after read. Intermediate directories receive descriptor/path identity rechecks after recursion (`craft_runtime.go:740–847`). Controlled same-byte hard-link and directory replacements reject. This closes the prior preflight/open substitution finding for the inspected output tree.
- The durable Run epoch is rechecked after seeding, on message-ID adoption entry, in the adoption SQL predicate, and after final material revalidation immediately before the inner executor (`craft_runtime.go:619–651`, `:407–440`, `:239–245`). Changed epochs during fetch and revalidation cause conflict with no inner dispatch in the focused tests. The inner production executor's `PrepareTask` also fences its durable Run transaction before prompt. The H2 fixture is not loosened and runtime assembly remains default-off.
- The reported full `go test ./internal/container -count=1` remains red in four tests. Two assembly failures (`TestCraftAccessFeatureRegistriesAreAssemblyOwned`, `TestWireCraftInteractionRegistrarRegistersPendingInteractions`) predate this delta. Two H2 knowledge tests fail earlier on zero `Fence.Epoch`; their separately owned fixture lacks the now required durable epoch/seed data. This review did not rerun the full package, so its classification is based on the Fix1 report and prior Task 1 review. These failures are not evidence of a passing package gate.
- This Task 1 review does not establish Task 2 Run-bound collection, real Linux mount isolation, or integrated A→B/C acceptance.

## Verdict

**Spec compliance: FAIL for Task 1 acceptance.** The legal draft size, exact predecessor and changed-epoch behaviors are now implemented and focused tests pass, but the specified partial retry and unchanged-default behavior lack production-boundary evidence.

**Code quality: FAIL for Task 1 acceptance.** The message adoption race/request overwrite is a substantive correctness and duplicate-dispatch risk. The full container package is still red. Correct finding 1, add the missing behavioral evidence, then obtain an independent review of the resulting checkpoint.
