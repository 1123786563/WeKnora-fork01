## Findings

1. **High — Extension replay can permanently lose the Craft call-cap increase.** `CraftBudgetService.Extend` in `internal/application/service/craft_budget.go:652-673` first commits `BudgetStore.ExtendTaskLimit`, then separately updates `craft_budget_grants.max_calls`. If the process stops or the second update fails, retry sees the commercial extension row and returns success at line 657 without raising the call cap. `ExtendAndResume` can then put the Run into `recovering`, where the next authorized call immediately pauses it again despite the paid extension. Same-key concurrent requests can also observe the row between those writes. **Smallest correction:** record the per-key Craft cap application durably and apply it in the same database transaction as the G4 extension, or make the Craft cap update independently idempotent and recoverable by key before returning replay success. Add a test that interrupts after the G4 write and retries.

2. **High — The first Run's grant deadline becomes a permanent Task deadline.** `Admit` creates the Session owner budget with the first Run's `now + GrantWindow` (`craft_budget.go:266-284`); G4 `EnsureTaskBudget` is an idempotent no-op for later Runs (`budget_task.go:16-25`). `ExtendTaskLimit` explicitly does not extend the owner deadline. Thus a valid later Run in the same long-lived Craft Task can never reserve after the first grant window expires, and a top-up cannot repair it. This conflicts with the Spec's persistent Task and follow-up Runs. **Smallest correction:** separate the durable Task budget validity policy from a per-Run grant window, with an explicit, authorized renewal rule for the Task owner deadline; test a second Run after the first window.

3. **High — Pause and charge admission are not serialized.** `requireRunChargeable` reads Run state before `AuthorizeBinding` inserts/reserves/marks dispatched (`craft_budget.go:308-344, 440-467`); `pauseOnDenial` changes the Run to `waiting_user` in another transaction (`:713-725`). A concurrent call can read `running`, then reserve and dispatch after another call persists the pause. This violates “limit prevents new chargeable calls” and “paused Run cannot cause new chargeable work” when budget remains available but the Craft call cap is exhausted. **Smallest correction:** fence the Run state and reservation/dispatch at one durable admission boundary, or use a guarded Run generation/lease token validated immediately before dispatch with compensating release for a provably unstarted reservation. Add a two-worker last-slot test.

4. **Medium — Missing Run is accepted at the production budget seam.** `Admit` permits a caller-provided Session ID when no `agent_runs` row exists (`craft_budget.go:243-257`), and `requireRunChargeable` treats a missing Run as chargeable (`:694-697`). This supports older low-level tests but bypasses the durable Task/Run association and pause authority that #138 requires. If invoked before Run persistence, a grant can be issued and charged with no Run to pause or recover. **Smallest correction:** require a tenant-scoped durable Run and matching Session for production admission/charging; give tests a persisted Run fixture or a separate explicitly test-only seam.

5. **Medium — The budget notice makes an unverified authority claim.** `CraftBudgetPauseNotice` receives `canExtend` as a boolean and says the actor may request an increase (`packages/views/src/craft/usage.tsx:169-185`), but there is no server-side action projection or mounted endpoint in this checkpoint. The test only renders two caller-chosen booleans. This is an integration gate, not evidence that permission enforcement is wrong in `ExtendAndResume`. **Smallest correction:** project an authenticated server-derived allowed action with the T00 pause fact, mount the notice and guarded extension route, and test owner/admin versus collaborator through the Craft API. Ordinary members should receive a generic pause notice without commercial fields.

## Acceptance and test evidence

- **Supported at adapter seam:** shared Task root across two Runs, stable sandbox activity key, durable pause/reload, denied collaborator extension, unknown dispatched reservation held during recovery. The T19 report records focused Go tests passing, 988 shared tests passed with one skipped, and web typecheck passing. `usage.budget.test.tsx` only checks static markup.
- **Not yet demonstrated:** budget admission before actual Lead model and sandbox effects, complete model/sandbox charge attribution and settlement, owner/admin extension through authenticated API, paused Run promotion rejection, workspace reload projection, and browser recovery. The report itself lists these integration gaps. The mandated highest available Craft API journey test is instead a direct service/database test, so it does not prove the ticket's external behavior.
- **Financial privacy:** the new notice does not render Credits, balances, credential material, or the T00 call counters. That local display choice passes review. The eventual API projection must enforce the same visibility rule server-side.

These findings are scoped to the five checkpoint files and their G4 dependency. Shared Lead/sandbox dispatch, central Run DTO/route, UI mounting, and promotion fencing should be reviewed as the integration owner’s work rather than silently credited to T19.
