# T19 normal-output Docker exec architecture

Date: 2026-09-24. Read-only architecture recommendation; no production implementation or requirement change.

## Authority and existing seams

The approved Craft spec requires budget admission before sandbox activity, once-only attribution, durable pause, and recovery without duplicate work or false success (`docs/specs/2026-09-23-craft-web-artifact-spec.md`, stories 34–35 and Implementation/Testing Decisions). T19 in `docs/plans/2026-09-23-craft-107-dag.md` maps those requirements. `CONTEXT.md` defines Task Budget as a Task-wide credit cap; ADR-0004 makes Run the execution identity. S2's reviewed coordinator commits an intent and hold, binds an immutable `(container ID, exec ID)`, and grants one exclusive send permission. The S3 outputless adapter deliberately does not route normal Craft commands; its reviews retain duration and physical-send gates.

The existing `RemoteExecRequest` requires optional stdin, live `OnOutput`, timeout, and user/workdir/env; `RemoteExecResult` presents stdout/stderr strings, exit code, duration, and killed. Legacy `DockerRemoteClient.Exec` creates an attached exec, calls `ExecAttach` once, writes stdin, half-closes the write side, demultiplexes with `stdcopy.StdCopy`, then inspects. Its measured duration is local elapsed time. `ExecAttach` in pinned Moby client v0.5.1 sends `POST /exec/{id}/start`; detached `ExecStart` followed by `ExecAttach` is two start requests. Inspect has exit state but no output replay or execution timestamps (normal-output research and S3 provider design).

## Recommended ownership and interface

Keep S2 as the only budget/Run authority. Introduce a **normal-output Docker operation** beside the restricted outputless one; do not expand the restricted result's unavailable flags into the ordinary `RemoteExecResult` without a typed completeness contract. Its provider interface should expose `CreateAttachedExec(request) -> immutable receipt`, `StartAttachedExecOnce(receipt, input, outputSink) -> stream outcome`, and `InspectExec(receipt) -> observed state`. `StartAttachedExecOnce` is the sole method allowed to issue the hijacked start POST. The application operation takes the S2 `DockerSendPermission`, consumes it immediately before this call, and never calls legacy `Exec`, detached `ExecStart`, or a second `ExecAttach` on this receipt. Only the exact bound receipt may be inspected.

Before create, validate the Docker handle and normalized command, shell/args, environment, user, workdir, timeout, stdin size, output quota, and output policy. Configure `AttachStdout=true`, `AttachStderr=true`, `AttachStdin=(input present)`, `TTY=false` at `ExecCreate`; these cannot be changed at start. Preserve the existing in-container timeout wrapper and activity marker, while preventing `ensureRunning` or any container restart inside this operation. Pre-stage an immutable, bounded stdin value in the journal or another durable operation record before create/claim; otherwise a crash after bind cannot reproduce the requested input on `ResumeBound`. For large or sensitive input, a separate encrypted/retained blob with hash and expiry is preferable to a journal column. Revalidate the hash at resume. The provider writes it once to the hijacked connection and half-closes the write side without closing stdout/stderr. A failed write after claim is unknown because the command may have consumed a prefix.

Output persistence belongs to an operation-scoped append store keyed by tenant, Task/Run/activity, exact receipt, stream, and monotonically increasing chunk sequence. Demultiplex Docker's non-TTY frames with `stdcopy` or an equivalent bounded parser; persist each stdout/stderr chunk before exposing it to `OnOutput`. A callback is a best-effort live projection; recovery reads committed chunks by cursor. Enforce byte limits and record explicit truncation, store failure, stream parse failure, and incomplete-tail markers. Limit memory independently of persisted output. Neither an empty string nor exit 0 implies output completeness. Keep the output store within the same tenant access and retention boundary as the Run, with no cross-tenant receipt lookup. Do not log stdin or raw output.

Suggested result shape: `ExecutionEvidence{receipt, startEvidence, inspectState, exitCode?, outputState: complete|partial|unavailable|truncated, stdoutRef?, stderrRef?, duration?, durationSource?, killed?}`. Convert to `RemoteExecResult` **only** when both streams are complete, terminal status is authoritative, and the caller's required duration semantics are met. If existing callers require synchronous stdout/stderr strings, reconstruct them from bounded persisted chunks after terminal inspection. `OnOutput` must use persisted sequence/cursors so reconnect does not invent, reorder, or silently duplicate events. The present provider-neutral `RemoteExecInitiator` promises a complete `WaitExec` result; advertise that capability only after these conditions and recovery are implemented. Otherwise keep a distinct typed operation and routing gate.

## State machine and failure rules

1. `prepared`: committed hold, intent, activity key, Run fence, and immutable input/output policy. No Docker create yet. A repeated inert create is allowed only while the intent is unbound.
2. `bound`: exact successful `ExecCreate` receipt persisted by S2 CAS. Bind failure forbids start. Resume uses the same receipt and input hash.
3. `claimed`: S2 exclusive claim committed. This is the irreversible application send boundary. A crash or cancellation here may mean zero physical starts, but no later claimant may send; classify unknown and retain hold/fence.
4. `starting/streaming`: consume permission and call **one** `ExecAttach`. A successful hijacked response proves accepted start and supplies the only stream. Persist chunks before callback. Connection loss, malformed stream, output-store failure, stdin error, deadline, or cancellation after claim leaves output partial/unavailable and operation unknown until observation; never reattach.
5. `observed`: inspect the same IDs. `Running=true` is positive start evidence. Terminal exit with previous positive start evidence can establish process completion. A first `Running=false, ExitCode=0` without positive start evidence, 404, mismatch, daemon loss, or inspect error remains unknown. Persist positive start evidence durably; S3's process-local `running` map cannot survive restart. Inspect cannot repair missing stream bytes.
6. `resolved`: settle/charge once against the original tenant and Task Budget activity key only after the policy has authoritative charge evidence. Distinguish command completion from output completeness. A completed process with partial output may be chargeable yet cannot be reported as a successful normal build. Unknown keeps the hold and Run fence; budget extension or reconnect must not replay it. Confirmed stop does not by itself prove command never ran.

Client deadline is looser than the in-container command timeout, as in legacy Docker exec; close the hijacked connection on cancellation and drain the copy worker within a bound. Context cancellation stops local waiting, not necessarily the command. Inspect after stream EOF to get exit code; EOF alone is not process success. Timeout wrapper exit codes must be interpreted with its actual contract; transport timeout is not `Killed=true`. Docker inspect has no authoritative duration, so mark duration unavailable unless a separately reviewed clock/evidence source meets the caller's duration requirement. Do not use poll elapsed time as execution duration.

## Decision on missing output and routing

Missing stdout/stderr may be represented as **explicit unknown or partial evidence without replay**. It must block promotion of the affected normal Craft build, because the approved spec bars false success and requires actual build, preview, and page-load proof before version promotion. It need not erase the previous successful version or block read-only viewing of it. A narrowly declared output-discard activity may use the S3 restricted path, but ordinary Craft build commands need normal output and cannot silently accept empty strings. If an individual command's output is genuinely irrelevant, the caller must opt into that policy before budget admission/create; this is a caller contract, not a recovery inference.

Route only reviewed Docker normal-output calls through the new operation; keep E2B, Cube, Docker create, and legacy unmarked paths separate. Marked `docker_coordinator` journal rows never fall back to legacy `StartBinding` or synchronous `Exec`. Gate production routing on a disposable real-Docker proof joining durable claim to exactly one hijacked start and marker side effect, plus complete stream/partial-output semantics. Existing S3 reviews do not establish this gate.

## Focused verification

- Fake engine counts HTTP-equivalent starts: one create and one `ExecAttach`, zero `ExecStart`; two claimants and all crash/replay boundaries never exceed one physical start. Lost attach response after a marker side effect never triggers reattach.
- Non-TTY multiplexed interleaving, split headers, binary bytes, stdout/stderr separation, malformed frames, quota truncation, persistence failure, and callback failure preserve explicit completeness state and committed sequence order.
- Stdin is written once, half-closed, bounded, and identical after bound-resume; a write failure after claim is unknown. No input/output appears in logs or another tenant's lookup.
- Stream EOF followed by inspect success/nonzero exit, running, first false/zero, 404, ID mismatch, cancellation, deadline, and daemon loss preserve the correct hold, fence, result state, and version gate.
- A real Docker integration test under isolated no-egress container proves the pinned client's single hijacked start, stdin/half-close, demux, timeout, marker side effect, and response-loss behavior. Run SQLite/PostgreSQL claim races on the same checkpoint. Validate normal Craft caller behavior for complete output, partial output, old-version visibility, and no false build promotion.

## Alternatives and change cost

An operation-scoped in-container output spool could recover bytes after a lost hijacked response, but requires trusted read-only retrieval, atomic completion metadata, symlink-safe ownership, quotas, cleanup, and retention across container loss. It is a larger protocol and still needs a once-only start claim. The simpler stream-persistence design preserves bytes already received and explicitly marks unrecoverable gaps; this satisfies no-replay safety but intentionally sacrifices liveness when the start response or connection is lost. If product requirements demand automatic recovery of every output byte after connection loss, the spool or another durable command-side sink is necessary before normal Docker routing.
