# T19 full-package failure: cancel then session delete event count

**Read-only triage, 2026-09-23.** Integration HEAD `a5e9195acd6500c085c85d60c852148e7bbbbf34`; moving-tree SHA-256 at inspection: `agent_run_lifecycle.go` `637bb9f132f1524024f5f525f6ede4e58191ade536f1ed82781fe55bdfd4d8d2`, test `11d12c7e2f64cad421afba2345f19b80751ecc8c710b92872bf673cc80fbd89b`. Sources: approved Craft Spec/#138 T19 cancellation and stop semantics, T19 Run-transition review, pending-cancel PASS review, current and HEAD baseline repository code. No source/test edits.

## Ruling

`TestCancelRunReleasesSlotAndDeleteFences` expects **two** `cancellation_requested` events: one from `CancelRun(reason=quote...)`, another from `DeleteSessionRuns(reason=session_deleted)`. This matched the pre-T19 `DeleteSessionRuns` implementation, which unconditionally rewrote every Run to `canceled` and appended a second event even if the Run was already canceled. Current `DeleteSessionRuns` tombstones the Session, then calls the shared `cancelRunTx`; that function returns immediately for a terminal canceled Run. The test's final `canceled` state, stale-worker fence and `execution_cleanup.tombstoned` remain satisfied; only the duplicate event assertion fails.

The changed count is an **intentional idempotence change**, not a lost cancellation request. The T19 pending-cancel PASS review specifically verifies repeated cancel produces one request/revision advance, while unresolved charge-start cancellation remains requested until reconciliation. A second `cancellation_requested` after a terminal cancel would claim a new stop request for an operation that is already complete, distort event projections, and provide no additional fence. The durable session deletion fact is the `execution_cleanup` tombstone; the existing first event retains the original cancellation reason. The approved Spec requires authoritative stop/recovery and durable facts, but does not require one Run cancellation event per cleanup caller. Thus change the obsolete test expectation, rather than alter `cancelRunTx` to append another cancel event.

## Smallest safe fix and ownership

**Test owner only:** `internal/application/repository/agent_run_lifecycle_test.go`. Assert `cancellation_requested` remains exactly one after `DeleteSessionRuns`, its payload still has the original reason, Run remains canceled with unchanged terminal revision/lease state, Session active slot is clear, and `execution_cleanup` is tombstoned. Add a second `DeleteSessionRuns` call to prove no duplicate event/revision and durable tombstone replay if the cleanup contract permits idempotent deletion. No production edit is needed for this failure.

**Separate required coverage:** in `internal/application/repository/agent_run_craft_charge_test.go`, test pause → `DeleteSessionRuns` while an `intent|unknown` charge start exists → journal resolution. Assert one pending `craft_charge_cancel_requested` and one `cancellation_requested`, final canceled, slot release only after resolution, and retained journal. This addresses the pending-cancel review's missing session-delete path; it is independent of the terminal-cancel event-count assertion.

If product/audit later requires a distinct notification that Session deletion occurred after a Run was already canceled, add a specifically named `session_delete_requested`/cleanup event from the tombstone path with its own idempotency key. Do **not** overload `cancellation_requested` or rewrite terminal Run state for that purpose. That is outside the current #138 acceptance and not needed to restore the package test.
