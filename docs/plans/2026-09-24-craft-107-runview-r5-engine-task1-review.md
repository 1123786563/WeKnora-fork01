# Craft #107 T01 RunView R5 engine Task 1 — independent review

Date: 2026-09-24. Scope: the Task 1 adapter, narrow provider ImageID change, H2 live fixture change, exact checkpoint and patch. Reviewed against the approved Craft #107 spec, `CONTEXT.md`, ADR-0003, R1 provider design and independent reviews, H2 review, and the R5 Task 1 brief. Source and tests were read only; no OCR was run.

## Findings

1. **High — container-shared PID and IPC namespaces pass the purported isolation inspection.** `hasUnsafeRunViewContainerSettings` in `internal/container/craft_runview_docker_engine.go:513-520` rejects only `PidMode.IsHost()` and `IpcMode.IsHost()`. The pinned Docker SDK also supports `PidMode.IsContainer()` and `IpcMode.IsContainer()` for `container:<id>`; both return false for `IsHost()`. `InspectContainer` projects only the host booleans (`:166`), so the provider's `validateContainerFacts` (`craft_runview_container_provider.go:569-573`) accepts these modes if the other facts match. An existing generation container with a durable marker could therefore share another container's process or IPC namespace while receiving `IdentityVerified`. This violates the R5 brief's exact privilege/namespace inspection and the R1 dedicated sandbox boundary. **Smallest correction:** reject container-shared PID/IPC modes and any other nonprivate namespace or cgroup sharing in the adapter's inspected `HostConfig`; add fake inspect/provider regression cases that reach marker-backed validation.

2. **Medium — the live knowledge write-denial assertion probes the wrong path.** `TestCraftRunViewDockerEngineRealPinnedProviderIsolation` creates a host file at `layout.knowledge/r5-write-challenge`, then passes that host absolute path to `ExecCreate` inside the container (`internal/container/craft_runview_docker_engine_test.go:330-347`). The actual container destination is `spec.Directory/knowledge` (`:321-329`). A nonzero exit can therefore mean the host path does not exist in the container; unchanged host bytes do not prove the actual bind rejects a write. The report's “root write through the knowledge mount was denied” claim is unsupported by this test, leaving a required H2/R5 live acceptance check open. **Smallest correction:** exec against `path.Join(spec.Directory, "knowledge", "r5-write-challenge")`; assert the preexisting bytes are readable through that exact container path, the root write fails with a read-only-filesystem error, and the host bytes remain unchanged. Keep the existing container/network cleanup checks.

## Verdict

- **Scoped Spec compliance: FAIL.** The real adapter enforces pinned create settings and reports inspected image ID, repository digest, mounts, networks, published ports, caps, limits, labels, user and runtime hashes through the provider. The container-shared namespace gap means it can still certify an isolation-violating existing container. The live knowledge mount denial required by the R5 brief remains unproven.
- **Scoped code quality: FAIL.** The adapter's definitive 404 handling, one-call create/start paths, durable provider marker, bounded exec stream/hash probe and explicit cleanup are sound in the reviewed paths. The missing namespace cases and misaddressed live probe require correction and behavioral tests.
- **Production T01/RunView acceptance: NOT VERIFIED.** `docker/craft/opencode.lock.json` still has `container_digest: null`; no server-owned production assembly or A→B handoff is in this Task. The local image's reported RepoDigest cannot substitute for a verified deployable registry pin.
