# T64 Task8 architecture plan review, round 2 — 2026-09-29

Read-only review of the revised detailed plan, `plan-t64.md` Task8 amendment, proposed ADR-0015, earlier review, approved Marketplace spec, `CONTEXT.md`, and current Run/AgentQA/revocation code. No implementation or requirements changed.

**Decision: do not dispatch 8A–8E yet; keep ADR-0015 proposed.** The revised design now states a coherent high-level direction: exact Version binding, source-tenant-first serialization, durable request identity, assistant placeholder in the claim transaction, generation fencing, and revocation cancellation in the ledger transaction (`plan-t64-task8-atomic-admission.md:52-76`; ADR-0015:14-16). The executable checkpoint contracts still contradict that direction:

1. **8B's schema cannot implement its public interface or ADR.** The shared contract requires `(session_tenant_id, session_id, owner_id, request_id)` uniqueness, canonical request hash, local Agent Version, lease owner and monotonic generation (`plan-t64-task8-atomic-admission.md:62-72`; ADR-0015:16). The 8B table list instead omits `owner_id`, `request_hash`, `local_agent_version_id`, `lease_owner`, and `generation`; its only unique key is `(source_tenant_id, session_id, assistant_message_id)` (`plan-t64-task8-atomic-admission.md:153`). It cannot identify a retry before generating a new assistant ID, reject a changed payload, bind the selected Version, or CAS a generation. Specify columns, types, nullability, both tenant-scoped uniqueness constraints, and the input/replay contract before an 8B Brief. Keep `(id, source_tenant_id)` on every claim lookup/update if that composite primary key remains.

2. **Claim lock order differs between the shared contract and 8B implementation steps.** The shared contract and ADR require both source and session tenant guards in ascending ID order before session/share/Variant/claim rows (`plan-t64-task8-atomic-admission.md:76`; ADR-0015:14). Step 8B says acquire `withTenantSecurityGuard(sourceTenantID)` first and session row second (`plan-t64-task8-atomic-admission.md:176`), while 8D says it will lock both tenants through the claim service (`:192`). If the source ID is greater than the session ID, 8B would reverse the global order. Put the two-guard transaction and share authorization recheck in the 8B repository contract; 8D should supply the server-resolved identity, not independently choose lock order. Test both numeric orderings and a share grant revoked between `resolveAgent` and claim admission. Current `resolveAgent` authorizes before this new transaction (`internal/handler/session/qa.go:552-601`).

3. **Lease ownership and fencing are not yet executable.** `Renew` accepts generation and lease owner, but the schema omits both (`plan-t64-task8-atomic-admission.md:68-72,153`). `Expire` has no explicit owner, schedule, or transaction order; 8B mentions expiry recovery (`:175-177`), while failure handling depends on a later explicit request (`:200`). Define whether each new admission sweeps expired claims in that session, whether a bounded background sweeper also runs, and how an expired handler is prevented from doing the next model step and every message write. A database CAS can fence durable writes, but cannot revoke already issued external model/tool work unless the handler checks/renews at defined boundaries and cancels on renewal failure. Define terminal placeholder update on expiry and the Stop-versus-Finish-versus-Expire winner. ADR-0015:33 can remain the intended no-restart policy after the contract is made precise.

4. **Assistant placeholder ordering is internally inconsistent.** The shared contract correctly requires claim plus assistant placeholder in one transaction (`plan-t64-task8-atomic-admission.md:62`; ADR-0015:16), solving the current Stop route's message lookup prerequisite (`internal/handler/session/stream.go:250-257`). Step 8D then says to create the placeholder “before ... messages” and tests assert “no ... messages before rejection” (`plan-t64-task8-atomic-admission.md:190-191`). Clarify that blocked admission writes zero messages, while successful admission atomically writes its assistant placeholder before attachment processing and any user message. Specify how existing `createTurnMessages` avoids creating a second assistant row (`internal/handler/session/qa.go:1004-1020`), and how placeholder terminalization retains auditable history after failure/cancel.

5. **Version binding is stated but not routed into either caller.** The shared helper requires a server-derived immutable `localAgentVersionID` (`plan-t64-task8-atomic-admission.md:53-56`), yet 8C's consumed input is the unchanged `agentruntime.Admission` signature and its steps say only to call 8A (`:104-115`); 8B's table omits Version (`:153`). Current `AgentRunStore.Admit` validates a snapshot and separate `AgentID` but its current transaction does not show a Version field or binding (`internal/application/repository/agent_run.go:153-168,223-244`). Name the authoritative field/path used by Run and QA, verify it is server-derived and equals the published Variant Version under the guard, and specify where the pinned value is persisted for later audit. A test should change the published Version/Release after handler resolution and assert fail-closed new admission. This preserves the approved spec's Task Version pin (`docs/specs/2026-09-20-agent-marketplace-domain-model.md:52-57`).

6. **Atomic cancellation needs a named repository boundary for both revocation forms.** The revised plan correctly requires audit append plus matching claim cancellation in one source-tenant transaction (`plan-t64-task8-atomic-admission.md:76,177`; ADR-0015:16). Current service calls `AppendReleaseRevocationWithAudit` / `AppendDependencyRevocationWithAudit`, then performs Run cancellation after commit (`internal/application/service/agent_security.go:189-203,229-246`); those store methods currently only append and audit (`internal/application/repository/agent_security.go:84-115`). 8B must define which existing store methods gain claim cancellation, how dependency affected Releases are selected with exact tuple under the same transaction, how a cancellation-store error rolls back both ledger and audit, and whether existing Run cancellation remains post-commit. Add crash-after-commit and rollback tests for each revocation form. Preserve the stated rule that later applicable `cancel` wins over earlier `allow` (`plan-t64-task8-atomic-admission.md:76`).

7. **Ownership/schedule: parent amendment is now aligned, but the file map is incomplete.** `plan-t64.md:1409` now explicitly permits parallel 8C/8D after integrated 8B, matching the detailed plan `:46,216`. Their listed production files do not overlap. However, 8D's Container registration file is still undiscovered (`:43,184,232`); identify it in the Brief and reserve it against other streams. `:235` says 8D owns schema tests, while the ownership table and 8B steps assign `internal/database/migration_sqlite_versioned_schema_test.go` to 8B (`:41,161,174`). `:31-32` assign QA rejection/cancel tests to 8E, while `:190-194,234` assign them to 8D. Correct these references. Separate worktrees also need a shared integrated 8B base for both streams and serial integration/affected package validation as already required by `:216`; an isolated SQLite file removes test database conflict, not all integration conflict.

**Recommendation:** reconcile the shared claim interface with 8B migration and repository steps first; state the two-tenant guard and Version input path; define expiry owner/fence boundaries and transactional cancellation methods; then correct checkpoint ownership and review-focus references. ADR-0015 should remain **proposed** until these are reflected in its implementation contract and the plan is independently rechecked. Its high-level decision need not be rejected or replaced.
