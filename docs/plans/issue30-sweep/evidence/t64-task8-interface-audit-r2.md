# Task8 interface audit R2 — 2026-09-29

Scope: read-only review of `plan-t64-task8-atomic-admission.md`, ADR-0015, current Run/Variant models and migrations, and the parent Task9 plan. No production code or tests were changed or run.

## Findings

1. **Blocker — four-field Run pin invariant is underspecified.** The plan calls `security_agent_id`, `security_local_agent_version_id`, `security_release_id`, and `security_pin_source` immutable, but its stated database check only pairs Version and Release nullability (plan lines 62, 171–172). Cancellation assumes all four identify one adopted Agent, while ordinary non-Marketplace Runs have no target. Require one database check on both engines: either all four are NULL, or all four are non-NULL and `security_pin_source IN ('admission','legacy_backfill')`. Reject partial pin inserts, not just Version/Release mismatch. Add insert and update cases to the migration tests. Existing `agentRunRow` has no such columns, so 8C must write all four in its owned repository file.

2. **Deployment gate remains operational, as documented.** The plan now correctly says SQL cannot attest human review of unmatched active Runs. It requires a signed per-tenant report before startup migration (plan line 62), with the preflight SQL owned by 8B. The report location is inside the source repository and may contain live tenant/Run identifiers. Keep operational reports in an access-controlled deployment evidence store, or redact identifiers and retain an authorized mapping outside Git. The plan must identify who checks every required report before applying migration; a repository test cannot establish that a production data owner signed it. This is a deployment blocker if unmatched rows exist, not a reason to change the approved security behavior.

3. **Migration order is sound if executed atomically.** Adding nullable columns, checking/backfilling attributable active Runs, then installing the four-field immutable UPDATE trigger permits the one-time backfill while preserving original JSON snapshot bytes. Add the old-writer INSERT guard before application traffic can resume. Paired SQLite/PostgreSQL migration execution must prevent an old writer from inserting between backfill and guard installation; document transactional/exclusive-lock behavior and test a concurrent writer boundary. The current plan lists operations in that order but does not explicitly state this cutover barrier.

4. **Exact target and recovery ownership are coherent.** `PublishVariant` creates a new local Agent and Version; Upgrade creates a fresh Variant. New Run pins are produced by 8C and supplied by 8E; 8B owns legacy sidecars, exact cancellation, revocation state, and reconciliation. Reconciliation takes tenant guard, locks/rechecks pending revocation, then atomically updates Run/event/session/count/state. Task7 is an integrated prerequisite; 8B owns subsequent Container registration edits. Task9 starts after 8C–8E and owns only its two end-to-end test files, so production ownership does not overlap. Exact targets must include retired Variants and compare all three identity fields plus tenant; the plan states this.

## Recommendation

Resolve finding 1 before approving an implementation Brief. Make the operational review gate and migration cutover condition in findings 2–3 explicit before applying migration to existing tenant data. No additional product decision is needed for the normal supported-writer path; unmatched legacy data still requires the named data owner's disposition.
