# T64 Task8 architecture plan review — 2026-09-29

Read-only review at coordination HEAD `726a6513d1c0b8b2b4ef11876ae2ab05d1ca9eff`. Reviewed `CONTEXT.md`, approved Marketplace spec §10–11, ADR-0015 (proposed), Task7/8 preflight, original `plan-t64.md` Task8 amendment, the proposed detailed plan, and relevant repository/handler code. No production code or requirements changed.

**Conclusion: revisions required before accepting ADR-0015 or dispatching Task8.** The tenant-first transaction and exact dependency predicate are sound directions. The following contract and recovery gaps are blocking.

1. **The proposed parallel schedule conflicts with the governing amendment.** `plan-t64-task8-atomic-admission.md:42-45,201` permits 8B/8C/8D concurrently, while `plan-t64.md:1409` requires serial, independently reviewed checkpoints before the next consumes them. More substantively, 8C's tests and wiring consume 8B's new authoritative `AgentRunStore.Admit` behavior (`plan-t64-task8-atomic-admission.md:57-59,135-142`), and 8D consumes the Task7 container provider file whose exact name/ownership remains undiscovered (`:43,162`). Thus disjoint listed edits do not establish independent validation or a fixed file set. Either retain the serial schedule or formally amend the parent plan with an explicit integration/test baseline and discovered 8D file; do not dispatch on the current claim of independent parallel streams.

2. **The shared Variant predicate does not yet define an exact published Version decision.** `plan-t64-task8-atomic-admission.md:52-55,72,177` looks up by tenant/local Agent and returns `releaseID, adopted`, but the spec says Task pins a local Agent Version (`docs/specs/2026-09-20-agent-marketplace-domain-model.md:52-57,135`). `AgentAdoptionVariantEntity` has `LocalAgentVersionID`; the helper contract neither accepts nor checks it. A local Agent's active/version selection can change between the handler's `resolveAgent` and guarded claim, and Run admission receives `AgentID` separately from its immutable snapshot. Require both callers to pass or transactionally derive the exact intended local Version and verify its published Variant maps to the fixed Release; reject a mismatch/ambiguous association. Add a test where the same local Agent gets a different published Version/Release between resolution and admission. Also make zero mappings an explicit non-Marketplace result only after verifying that the intended Version truly has no adoption association, so a stale/retired mapping cannot silently fall through to unrestricted execution.

3. **AgentQA claim identity is specified before its message exists.** The plan's key `(source_tenant_id, session_id, assistant_message_id)` and `Admit` before message writes (`plan-t64-task8-atomic-admission.md:72,149,175-178`) need a concrete server-generated ID and replay contract. In current `qa.go:391-396,1004-1021`, the assistant ID is populated by `createAssistantMessage` after parsing, and `requestID` comes from request context (`qa.go:130`). The plan never says how an ID is allocated without a message write, how a retry obtains the same ID, or whether `request_id` is unique per session/owner. Specify the identity generator, durable request-to-claim lookup/uniqueness, hash or payload equivalence check, and terminal retry behavior before implementation. Otherwise retries can mint new IDs and claims, or the claim can be created with an empty ID and fail to bind the later message.

4. **Lease and orphan recovery contradict the proposed ADR and leave live turns unfenced.** ADR-0015:33 permits an expired incomplete message to be reclaimed, while the plan's storage contract `:149` and recovery `:186` forbid restart, requiring a new assistant ID after terminalization. Pick one policy and record it in the ADR. Define who expires/fails orphaned active claims after handler crash, how a live handler renews its lease, and the exact CAS/fencing check before any later message write/model step. `context.WithoutCancel` on early returns (`:178`) and polling (`:180`) do not guarantee terminalization after process death. A finite lease alone cannot both stop an old generator and admit a new one safely.

5. **Revocation cancellation is only best effort after the ledger commit.** `plan-t64-task8-atomic-admission.md:179-180,186` and ADR-0015:16 call for a post-commit `CancelByReleases`; current `agent_security.go:154-246` already separates ledger append from Run cancellation. If claim lookup/update fails or the process exits after append, an active claim remains runnable; polling only sees its unchanged `active` state. Persist a recoverable revocation disposition/claim cancellation obligation in the guarded transaction, or make the watcher independently derive cancellation from the committed revocation ledger under a documented recovery scan. Include crash-after-ledger and cancellation-store-error tests. Also state how repeated revocation rows with different `allow`/`cancel` dispositions affect an earlier claim; release-blocking alone does not determine in-flight disposition.

6. **The source/session tenant contract is incomplete for shared Agents.** `plan-t64-task8-atomic-admission.md:72,166-177` requires a source-tenant guard and then a session-row lock in a different tenant. It does not say whether another operation locks the session tenant first and then source tenant, nor how the repository verifies the share authorization held by `resolveAgent` while both records may change. Current `resolveAgent` uses a selected source tenant for shared lookup (`qa.go:552-605`); the claim must bind the resolved Agent, source tenant, session tenant, owner, and share grant to one authorized observation or fail closed if they changed. State a global cross-tenant lock order and add tests for revoked share and concurrent source/session operations. The suggested check `customAgent.TenantID == effectiveTenantID` only proves consistency of two handler values, not continuing authorization.

7. **Stop and failure cleanup need one terminal owner and explicit ordering.** `plan-t64-task8-atomic-admission.md:178-180` says stop marks the claim cancelled and uploaded resources are cleaned on failure, but current `StopSession` first requires an already persisted assistant message and only appends a StreamManager event (`stream.go:219-320`); claim creation precedes that message. Define behavior when Stop arrives between claim commit and message creation, and when stop-event append fails after claim cancellation. Define whether `cancelled`/`failed` leaves the user and assistant messages as auditable terminal rows and which uploaded objects are removed. Add race tests for completion vs stop vs revocation, and for cleanup failure. The existing deletion APIs may not cover all image/file storage side effects; identify each resource type before promising cleanup.

8. **Migration and file details are partly conditional.** Proposed IDs `000126`/`000205` are free at this HEAD (the old `000126_craft_versions` text is only a comment in SQLite `000046`), and rechecking is appropriate. `plan-t64-task8-atomic-admission.md:149,153-162` still needs explicit SQLite/PostgreSQL column types and constraints for `state`, lease time and tenant key; the composite `(id, source_tenant_id)` primary key allows the same claim ID across tenants, so every FK/query must carry both parts. The plan should name the exact Task7 DI file after integration and reconcile its file list before briefs. These are resolvable plan details, but not safe to leave to a parallel implementer.

**Recommended revision order:** settle the claim identity/version contract and cross-tenant lock order; choose one lease/recovery policy; make `cancel` durable across post-commit failure; then update ADR status/decision, tests, owned files and the parent Task8 schedule. Preserve the current preflight's request replay and tenant-first locking conclusions. ADR-0015 should remain `proposed` until those points are explicit and independently reviewed.
