# Issue #65 research: adopter-level error-category source

## Verified facts

- The approved marketplace spec defines Marketplace Metrics as de-identified aggregates of adoption, upgrade, and error-category metrics; publisher output must exclude tenant/member identity, task content, local mappings, knowledge, connections, and tool parameters. See `docs/specs/2026-09-20-agent-marketplace-domain-model.md` §12, §15 (especially acceptance scenario 10), and `CONTEXT.md` (`Marketplace Metrics`).
- Adoption persistence is governance metadata only. `agent_adoptions` stores `(tenant_id, listing_id, accepted_release_id, state, created/ended metadata)` and `agent_adoption_variants` stores release pin, lifecycle state, local agent/version references, and actor/timestamps. Source: `migrations/sqlite/000113_agent_adoption_variants.up.sql`; entities: `internal/types/agent_adoption_persistence.go`. There is no error field, run count, or metrics/event ledger.
- Upgrade persistence stores proposal identity, from/to releases, diff JSON, state, accepted variant, resolver and timestamps. Source: `migrations/sqlite/000120_agent_upgrade_proposals.up.sql`; entity: `internal/types/agent_upgrade_persistence.go`. It has no execution/error outcome fields. Upgrade service errors are transient Go errors (`ErrAgentUpgrade...`) and are not persisted as categorized events: `internal/application/service/agent_upgrade.go`.
- Durable execution rows do retain tenant-scoped run status and raw execution material: `agent_runs` has `(tenant_id, run_id, session_id, owner_id, status, snapshot, timestamps)`, while `agent_tool_attempts` has `error_message`; events and tool rows retain payload/result/args. Source: `migrations/sqlite/000014_agent_runs.up.sql`. These are task/run content-bearing surfaces and are not marketplace metric records.
- `agent_runs` does not carry `adoption_id`, `variant_id`, `release_id`, or `local_agent_version_id`. The only apparent runtime linkage is admission-time checking of `agent_adoption_variants` in `internal/application/repository/agent_run.go` (around the variant retirement/runnability guard); it does not persist a marketplace attribution on the run row. The run table therefore cannot safely provide a direct adopter-to-error join.
- Existing structured error fields elsewhere are unrelated: `knowledge_spans.error_code` is parser/retrieval data (`internal/types/knowledge_span.go`), `semantic_outbox.error_code` is outbox delivery state, and `craft_scheduled_task_runs.error_class/error_detail` is scheduled-task execution. None is a marketplace adoption/release error source, and some contain detail that must not cross the privacy boundary.

## Join/filtering implications

No current query can produce a defensible distinct-tenant error-category aggregate. A hypothetical future event must carry server-derived tenant scope and a stable release/listing attribution at emission time; aggregate with `COUNT(DISTINCT tenant_id)` after filtering to approved marketplace releases/listings and a fixed time window. Never join through task/session/message/tool tables, and never export tenant IDs, run IDs, adoption/variant IDs, local agent/version IDs, prompt/output, mappings, or error text. If counting events, deduplicate by a server-generated event key before distinct-tenant aggregation so retries cannot inflate adoption counts. Cross-tenant sharing should be suppressed or thresholded before publisher output (the spec requires de-identification but gives no numeric threshold).

## Query safety

The existing adoption/upgrade repositories are tenant-scoped (`internal/application/repository/agent_adoption.go`, `agent_upgrade.go`) and safe for administrative reads when the caller supplies the tenant. They cannot safely answer publisher-facing metrics because they expose tenant-local rows and no error category. `agent_runs`/tool attempts are queryable only inside tenant/task authorization paths and should be treated as unsafe for a publisher metrics query due to content-bearing columns and missing release attribution.

## Recommendation

Conservative Issue #65 behavior: report error-category metrics as unavailable/`not_collected` and do not infer them from run status or raw error messages. Implementing a future source requires a new append-only, privacy-reviewed marketplace metric/event projection emitted at adoption/variant/upgrade/run boundaries, with a closed allow-list of coarse error categories, immutable release/listing attribution, tenant-scoped ingestion, retry idempotency, retention, and aggregate-only publisher reads. Until that source exists, expose only verified adoption/upgrade counts from their own tables (with `COUNT(DISTINCT tenant_id)` and no IDs) and omit error-category breakdowns rather than joining task/run content.
