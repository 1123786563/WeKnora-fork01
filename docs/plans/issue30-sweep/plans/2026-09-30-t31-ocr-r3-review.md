## Findings

### F1 — Medium — unrecognized non-system dylib loads still pass silently

**Evidence / affected symbol:** `apps/mobile/scripts/verify-ios-framework-closure.py:88-96`. The new `UNSUPPORTED_DYNAMIC_LIBRARY_LOAD` branch fires only when `load` begins with `@rpath/`, `@loader_path/`, `@executable_path/`, or `/`. A load such as `@unknown_path/libMissing.dylib` or a bare `libMissing.dylib` has no `.framework` component, matches neither branch, and reaches `continue` at line 96. The repair plan's produced interface says any non-system load not proven to be an embedded framework dependency must fail closed. The new fixtures at `apps/mobile/src/ios-framework-closure.test.ts:162-189` cover three recognized tokens and an absolute path, but not an unrecognized token or relative dylib.

**Impact:** The Release closure gate can still report success for an unclassified dependency that dyld may fail to load, so the Medium OCR issue is only partially closed.

**Smallest correction:** After handling the two explicit system roots and successfully resolved embedded framework paths, reject every other load form in this branch with a stable failure code. Add an unrecognized-token and bare-relative load fixture. Retain the existing `/System/Library/` and `/usr/lib/` positive coverage.

### F2 — Low — provider conformance regression fixture drops its own markers

**Evidence / affected symbol:** `apps/mobile/src/scripts/verify-ios-scene-project.test.ts:50-53`. The first replacement places `ExpoReactNativeFactoryProvider` in a Swift comment and string. The second replacement replaces the whole resulting sequence with `ExpoAppDelegate {`, deleting both markers. The resulting negative fixture has no provider token anywhere, so it would pass even with the previous raw `appDelegate.includes(...)` implementation. The production change at `verify-ios-scene-project.ts:26-29` correctly checks masked text, but the test does not demonstrate that behavior.

**Impact:** The named OCR false-pass scenario can regress without this test failing.

**Smallest correction:** Remove the real conformance from the declaration while retaining a provider token in a separate comment or string elsewhere in the fixture; assert the checker rejects it. Keep the valid conformance fixture.

### F3 — Medium — repair report understates the complete OCR result

**Evidence / affected symbol:** `.superpowers/sdd/plan-t31-ios27/ocr-r3-repair-report.md:7` in the current uncommitted report says the complete review covered eight items and reported three comments. `docs/plans/issue30-sweep/ocr/ocr-t31-r3-resumed.md:1` says **six findings across eight selected items**: the three checker/documentation findings plus three Low `_layout.tsx` findings (safe-area background/placement, nested provider, and initial metrics). The original `ocr-t31-r3-final.md:1` was only partially complete, with three findings and one failed selected item. Neither report assigns stable finding IDs; the plan's Step 7 request to record IDs cannot be fulfilled from these text artifacts alone. The report does not give a ruling or follow-up for the three additional findings.

**Impact:** The repair record can be mistaken for disposition of the entire completed OCR run and can hide unresolved layout findings from the controller's release decision.

**Smallest correction:** State that the partial run had three comments and the resumed complete run had six, identify the three additional layout findings, and record each disposition or its separate tracking reference. If OCR has no IDs, use stable file/line anchors and explicitly say no IDs were supplied. Commit the corrected evidence report with the source SHA and final verification results.
