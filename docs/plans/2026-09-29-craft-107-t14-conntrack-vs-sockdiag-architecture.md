# T14 exact WebDriver flow: conntrack versus socket diagnostic

Read-only architecture audit, 2026-09-29. Scope: T14 worktree source and the integration evidence at `docs/testing/craft/t14/2026-09-29-ctnetlink-exact-flow-fix3-retry1/`. No Docker run or production edit.

## Decision

**The present design is blocked, but the approved product Spec is not necessarily blocked.** `NETLINK_SOCK_DIAG` can give a kernel-authoritative proof of a live TCP socket, exact tuple, TCP `ESTABLISHED` state, and socket inode. Together with the host-issued PID 1 FD and unique ChromeDriver listener ownership checks, it can strengthen the seven-field attestation without a new privilege. It **cannot** prove that Netfilter has a matching conntrack entry or that `ct state established` will match the next packet. Replacing ctnetlink with sock_diag while retaining that nft predicate would claim a guarantee it has not established. Removing the predicate would change an explicit implementation invariant and requires a reviewed architecture ruling/plan update, even though the approved Craft Spec itself requires no external egress and does not prescribe conntrack.

The current ctnetlink result is a successful, empty dump, not a parser failure: the saved raw-header diagnostic contains one 20-byte `NLMSG_DONE`, zero status, no `CT_NEW`. The provided `/proc/net/tcp` observation of `127.0.0.1:49152 -> 127.0.0.1:9515 ESTABLISHED` proves a socket exists in the renderer namespace, not that this socket has an established conntrack record. The separate saved host flow attestation has the same seven-field shape but a different sample port (`39186`); do not join those samples as one transaction. The source currently fails closed on zero/ambiguous ctnetlink matches before policy mutation, which is correct for the current invariant.

## Existing ownership and interfaces

- Host controller `capture_webdriver_flow` initiates `docker exec` as renderer UID 10001, inventories PID 1 FDs and TCP tables, checks the same renderer ID/PID before and after, and selects one client socket owned by PID 1 and one ChromeDriver `LISTEN` socket. The seven fields are `{family, client_addr, client_port, driver_addr, driver_port, state, client_socket_inode}`. `barrier_adapter.validate_webdriver_flow` checks exact field set, loopback family/addresses, ports, state and inode.
- Controller starts a one-shot helper with `--network container:<exact renderer ID>`, `--cap-drop ALL --cap-add NET_ADMIN`, `no-new-privileges`, read-only root, and the seven-field JSON. The helper has the renderer **network** namespace, but not its PID namespace or process FDs. Its independent cross-check can compare sock_diag's `idiag_inode` with the host-provided inode; process ownership remains the host controller's responsibility.
- Helper `require_tracked_webdriver_flow` currently queries `NETLINK_NETFILTER`; `webdriver_rules` emits two direction-specific tuple rules with `ct state established`; output chain priority is `-150`, followed by loopback drop. The inode constrains admission, but nft cannot bind its packet rule to that inode. The exact tuple is therefore the enforcement interface.

## Candidate comparison

| Candidate | What it establishes | Main gap / risk | Recommendation |
| --- | --- | --- | --- |
| ctnetlink exact bidirectional CT tuple | A conntrack record and TCP CT state in the exact network namespace | Observed empty successful dump; repeating AF_INET or NFPROTO_UNSPEC does not create a record. Cannot infer that an established TCP socket was tracked. | Retain fail-closed behavior; only retry after evidence of a concrete tracking prerequisite and an exact CT record. |
| `NETLINK_SOCK_DIAG` / `INET_DIAG` | Kernel TCP socket tuple, `idiag_state`, `idiag_inode`, socket cookie and namespace context | TCP socket state is distinct from conntrack state. Inode ownership is observed across two steps; namespace/FD/inode reuse and reconnect races remain. | Best diagnostic and potential socket-based admission seam, conditional on an explicit change to the nft exception semantics. |
| `/proc/net/tcp{,6}` plus `/proc/<pid>/fd` | Socket table and process-FD ownership | Same socket-versus-CT gap; proc parsing and PID/FD races; source already uses this for host discovery. | Retain as ownership evidence, not as proof of `ct state established`. |
| nft counters / successful marker | Packets hit rules and the existing connection still works | Outcome evidence is post-install, not a safe pre-install admission proof; a counter does not identify the socket owner. | Required independent acceptance proof, not an attestation source. |

The Linux `inet_diag_req_v2` request and `inet_diag_msg` response expose TCP state, tuple, inode and cookie; the kernel's exact-query path is separate from dump handling ([UAPI](https://github.com/torvalds/linux/blob/master/include/uapi/linux/inet_diag.h), [implementation](https://github.com/torvalds/linux/blob/master/net/ipv4/inet_diag.c)). Conntrack has its own tuple and TCP state data model ([kernel conntrack netlink specification](https://kernel.org/doc/html/latest/netlink/specs/conntrack.html)). This distinction is the reason sock_diag cannot silently satisfy the existing CT predicate.

## Narrow socket diagnostic seam, if approved

Keep the external seven-field JSON and host ownership selection stable. Inside the helper, make one bounded, read-only `SOCK_DIAG_BY_FAMILY` exact query for `AF_INET`/`AF_INET6`, TCP and the four address/port fields in the joined renderer network namespace. Validate sender PID, sequence, message type/length, family, protocol, state `TCP_ESTABLISHED`, exact tuple, and `idiag_inode == client_socket_inode`; reject no result, duplicates/ambiguous results, malformed data, truncation, errors and deadline breaches. A bounded diagnostic dump may be used only if exact query behavior on the target kernel is established; it must filter to exactly one socket and remain fail closed. Do not accept the listener or server-side accepted socket as the client socket. The host should recheck renderer identity and PID 1 FD ownership near installation, and record tuple/inode/cookie and timing; a cookie helps detect reuse but is not carried in the current seven-field interface.

The unresolved enforcement choice is explicit: (1) retain `ct state established`, in which case socket diagnostic is supplemental and installation still blocks without CT proof; or (2) authorize **only** the two exact address/port directions independent of CT state, after exact socket plus ownership proof, with no listener-wide or generic established allowance. Option 2 permits a new socket that somehow reuses the same four-tuple after the old socket closes; it must be bounded by renderer lifetime, fail on reconnect, immediate post-install reuse proof, and negative fresh-connection canary. This residual race and change to the existing implementation contract need an explicit architecture/spec ruling. A process owner check alone cannot remove it because nft packet matching has no persistent binding to the Python FD. If that risk is unacceptable, stop at the current fail-closed blocker rather than silently weakening the rule.

## Required proof before T14 acceptance

1. Target-kernel diagnostic exercise in the exact renderer namespace: response with the seven-field tuple, `TCP_ESTABLISHED`, matching client inode, and verified helper capability/namespace; negative exact-query cases for absent socket, wrong inode, wrong tuple/state, response framing and timeout. Capture raw bounded headers and source hashes.
2. If retaining CT: show one matching CT original/reply tuple and state before install. An empty successful dump is a failing result. If changing to socket-based exact rules: record the approved ruling and audit the generated nft rules to show precisely two full-tuple exceptions before loopback drops, with no broad established or port-only path.
3. One disposable integration run on the immutable image/helper build: existing socket returns `reuse-ok` after installation, a fresh connection to the same ChromeDriver listener from another source port fails and increments the exact loopback-drop counter, preview still works, external egress remains denied, and failure/cleanup receipts are complete. Then run the prescribed T14 matrix. Evidence must tie image ID, source hashes, netns inode, flow inode/tuple, rule set, counters, and marker to the same run.

## Updated probe ruling (2026-09-29)

The bounded dump is now empirically proven from an unprivileged `docker exec` in a running disposable renderer namespace on the pinned target kernel (this probe did not invoke the privileged policy helper). `docs/testing/craft/t14/2026-09-29-sockdiag-dump-probe/query.json` records the raw response. It includes the client `127.0.0.1:47630 -> 127.0.0.1:9515`, state 1 (`TCP_ESTABLISHED`), inode `5717721`; `/proc/1/fd/3` pointed to the same inode. The accepted server-side peer and listening socket have different inodes. Exact `SOCK_DIAG_BY_FAMILY` (non-dump) returned `NLMSG_ERROR -ENOENT` in this environment; the implementation plan should use a bounded dump and require exactly one tuple+state+inode match, rejecting malformed, interrupted, truncated, duplicate, absent and out-of-budget results.

This is a valid supplemental socket/inode verification seam. It does not change the ruling on nft enforcement: retaining `ct state established` still requires a matching conntrack record and current ctnetlink cannot provide it here. A socketdiag-only replacement would require a separate plan/ruling and proof addressing ACK-only two-direction tuple exceptions, tuple reuse, renderer lifetime/reconnect, existing-flow continuation, and a fresh-connection counter canary. Until that separate reviewed decision, current installation should continue to fail closed at the conntrack requirement.

## ACK-guarded stateless exception ruling (2026-09-29)

The saved `docs/testing/craft/t14/2026-09-29-sockdiag-dump-probe/query.json` is a successful **bounded dump issued by an unprivileged process directly in the renderer container** (not by the one-shot policy helper), with a kernel-sender response for the client `127.0.0.1:47630 -> 127.0.0.1:9515`, TCP state 1, inode `5717721`, and distinct server peer/listener inodes. It supports a read-only exact tuple/state/inode helper check. The previously proposed non-dump exact lookup is not viable on this target (`-ENOENT`); use the bounded dump with exact-one matching and all framing, sequence, sender, timeout, truncation, interruption and resource-limit checks. The JSON alone does not prove the nft policy works.

**Conditional recommendation:** A stateless nft exception limited to the two full four-tuples and requiring `ACK=1, SYN=0` is a plausible narrow replacement for the missing conntrack predicate. This is an explicit change to the existing implementation invariant, so it needs a reviewed plan/ruling and live acceptance before T14 is verified. The nft expression should be `tcp flags & (syn | ack) == ack` on **each** direction-specific rule, alongside matching family, source/destination addresses and source/destination ports. The mask tests exactly those two bits: ACK must be set and SYN clear; PSH, FIN, RST, ECE and other flags are deliberately ignored. Do not write `tcp flags ack` or a set expression as a substitute: nft's bitmask and set semantics differ ([nftables man page](https://netfilter.org/projects/nftables/manpage.html), [nftables packet-header examples](https://wiki.nftables.org/wiki-nftables/index.php/Matching_packet_header_fields)). Keep the rules before the loopback drop and require the resulting ruleset text/packet trace to confirm the parsed expression and counters.

Why this can preserve the old socket: ordinary established TCP data, data retransmissions and pure ACKs carry ACK without SYN; FIN+ACK and RST+ACK can pass too. A new ordinary `connect()` starts with SYN without ACK, so its first packet cannot pass either exception. A retransmitted SYN is still excluded, and SYN+ACK is excluded in the reverse direction. ACK is **not** a proof of an established connection: it is only a packet-header guard. Thus the admission proof remains the near-install SOCK_DIAG socket/inode plus PID 1 FD ownership, while the flag guard prevents an ordinary fresh TCP handshake from exploiting the static tuple exception. Linux's TCP flag definitions and input path distinguish ACK and SYN ([Linux TCP header](https://github.com/torvalds/linux/blob/master/include/net/tcp.h), [TCP input implementation](https://github.com/torvalds/linux/blob/master/net/ipv4/tcp_input.c)).

Residual risk: the nft rule is not bound to an inode, socket cookie, PID or TCP sequence window. A process with packet injection capability could forge matching ACK-bearing packets; the renderer's `CAP_DROP ALL`, lack of `CAP_NET_RAW`, `no-new-privileges`, read-only filesystem and isolated network namespace reduce that path, but the one-shot NET_ADMIN helper is a separate trusted actor. The exact four-tuple could be reused after the attested socket closes; a normal new TCP connection still needs a blocked SYN, but a previously existing or injected matching connection could use the stale rule. Netns lifetime must remain tied to the renderer, and loss/reconnect of the attested socket must fail the run or remove policy. A same-process user with access to the established FD can send on it; packet filtering cannot distinguish that from the intended WebDriver control traffic. Avoid claiming the ACK guard is equivalent to `ct state established`.

**Required live negative test:** On the pinned renderer/helper pair, attest the exact client socket via bounded SOCK_DIAG and PID 1 FD/inode, install only the two ACK-guarded full-tuple rules, then (1) send a marker on that *same* FD and prove `reuse-ok` with positive exception-counter delta; (2) attempt a fresh connection to the same ChromeDriver listener from a different source port and prove failure plus positive loopback-drop delta; and (3) preferably force-bind the previously attested source port after closing the old FD and prove its new SYN also fails, or record why the port cannot be safely reused in the fixture. Record nft ruleset, per-rule and drop counters, tuple/inode, namespace, image/source hashes, and verified cleanup in one run. A separate synthetic ACK packet test is useful only if performed in an isolated privileged test actor; it cannot substitute for the ordinary fresh-connection denial. If the marker or canary fails, restore fail-closed status and do not run the browser matrix.
