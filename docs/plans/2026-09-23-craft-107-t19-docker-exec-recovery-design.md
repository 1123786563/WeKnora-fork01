# T19 Docker exec recovery design challenge

Read-only assessment, 2026-09-24. Sources: approved Craft spec (`docs/specs/2026-09-23-craft-web-artifact-spec.md`, budget and recovery acceptance), `CONTEXT.md` Task Budget and Run definitions, ADR-0004, T19 durable-start and Task 4b plans, Task 4b Task 2 report, SDK research, Docker v28.5.2 client and daemon code, current Docker adapter and `craft_charge_start_journal` schema/service. No provider was enabled by this assessment.

## Decision

**The proposed split is a useful prerequisite, but does not by itself satisfy the Task 4b recovery contract.** `ExecCreate` is inert with respect to command execution; a lost create response can leave an orphan exec configuration, but a retry may create a different inert ID without running the command. Once an ID is returned, persisting `(tenant, Run, operation key, container ID, exec ID)` before `ExecStart` removes the *lost create receipt* window. It does not make `ExecStart` idempotent, nor does `ExecInspect` prove that an unstarted-looking ID can safely be started after an ambiguous send.

Concrete counterexample: worker A commits the exec ID, sends `ExecStart`, and loses its response while the daemon is processing it. Worker B obtains the same journal row and inspects that ID before A's start has crossed the daemon's `Running=true` point. Inspect reports `Running=false`, `ExitCode=0` (the public API represents the daemon's nil exit code as zero). B interprets this as unstarted and sends a second `ExecStart`. Both start requests may race; Docker's daemon lock rejects the second once the first sets `Running`, but this behavior is a Docker implementation detail, not an idempotency-key protocol or proof from Inspect. More importantly, after A's client context is cancelled, the daemon may kill the process; B cannot infer from a later `Running=false, ExitCode=0` whether the command never ran or ran and exited successfully. Retrying with a *new* exec ID would duplicate side effects. Retrying with the *same* ID after an ambiguous start can also encounter daemon disappearance/GC and cannot recover output or effects. Thus `Inspect` cannot convert an ambiguous start into `definitely_unstarted`; it can only provide positive running/completed evidence while the ID remains inspectable.

The safe restricted policy is **at most one application `ExecStart` invocation per operation key**, durably claimed before the call. After a crash or ambiguous response, inspect the exact ID for positive evidence only; otherwise keep `unknown` and its hold/fence, with no automatic second start. This is safe against duplicate chargeable initiation but can park an operation indefinitely and cannot meet an expectation of automatic recovery to a confirmed final outcome. A fresh request after a definitely pre-send failure can use the same prepared ID only if the journal records that no worker crossed the durable send claim; never infer this from Inspect alone.

## Evidence and boundaries

- Pinned Docker client has distinct `ContainerExecCreate`, `ContainerExecStart`, `ContainerExecInspect`; Start accepts only an exec ID and options, no application key (`github.com/docker/docker@v28.5.2+incompatible/client/container_exec.go`). The current `DockerRemoteClient.Exec` calls create, then `streamExec`/attach, then inspect, all inside a synchronous operation (`internal/modules/execution/sandbox/docker_remote_client.go:668-734`). `ContainerExecStart` with `Detach=false` is not a bounded acceptance receipt: it waits for execution/response. A bounded start needs detached mode or equivalent protocol and separate wait/output design; switching to detached mode loses the current attached stdout/stderr/stdin behavior unless designed separately.
- Public `ExecInspect` contains `ExecID`, `ContainerID`, `Running`, `ExitCode`, `Pid`, but no `StartedAt`, never-started flag, application key, or durable acceptance marker (`api/types/container/exec.go`). The daemon keeps exec configurations in `daemon.execCommands` and inspect returns not-found when absent (`daemon/inspect.go:199-229`); daemon restart/container removal/GC can erase the receipt. Not-found is not proof of no prior side effects.
- Docker daemon's `ContainerExecStart` checks `ExitCode` and `Running` under the exec lock, then sets `Running=true`; it rejects already-running/already-run starts (`daemon/exec.go:162-188`). This makes a duplicate request for the *same extant ID* unlikely to execute twice in this pinned daemon, but does not solve lost or expired IDs, durable application-key mapping, final output, or the question whether a completed external effect occurred.
- The journal currently has unique `(tenant_id, run_id, activity_key)` and unique reservation key, with `intent|started|unknown|definitely_unstarted` state and no provider receipt/send-claim fields (SQLite `000112_craft_charge_start_journal.up.sql`; PostgreSQL `000191` counterpart; `CraftChargeStartJournalRow`). `StartBinding` prepares an intent/hold transaction, then runs a bounded callback and CAS-resolves outcome (`internal/application/service/craft_budget.go:267-408`). Reusing it unchanged around `ExecStart` gives no place to persist the exec ID between create and start, nor a durable exclusive send claim. The existing unique key rejects replay, but a separately designed recovery path needs a clear ownership/CAS protocol.

## Minimal viable restricted design, if parked unknown is acceptable

1. **Journal persistence task (service/schema owner):** add nullable provider, sandbox/container ID, exec ID, and a distinct send state or attempt-claim marker to the existing `craft_charge_start_journal` in both SQLite and PostgreSQL migrations/models. This is an additive migration of the existing journal, not a new table. Require immutable `(operation key, provider, container, exec ID)` after binding, a uniqueness constraint on provider/container/exec ID where supported, and CAS from prepared to `send_claimed` with one owner. Do not overload `started`: it currently means resolved start and releases the unresolved Run fence. Preserve `intent|unknown` fencing until positive resolution. No SQL transaction may surround the Docker call.
2. **Coordinator task (budget service owner):** expose prepare/bind/claim/resolve as a reviewed narrow seam. Prepare commits the G4 hold before `ExecCreate`; bind commits the returned ID; claim commits *before* invoking `ExecStart`. On replay, load the same row and ID. A claimed or unknown row is observation-only, never invokes Start again. A crash after claim but before actual send conservatively remains unknown. Make the claim atomic across workers and fence stale Run epochs. Keep the old `StartBinding` contract for existing callers until migration is reviewed.
3. **Docker adapter task (sandbox owner):** separate inert prepare from chargeable start and observation, without advertising the existing synchronous `Exec` as charge-safe. Validate the inspect ID belongs to the persisted container. Use a bounded start mode and define how stdin/output/wait are preserved; otherwise restrict supported requests explicitly. Tests must count physical Start calls under concurrent replay, lost response, crash at each journal boundary, inspect false/zero/404, and daemon restart. A 404 or `Running=false` alone stays unknown.
4. **Production wiring/recovery task (runtime owner):** supply the stable ToolPlan call/attempt operation key, route every approved chargeable Docker exec through the coordinator, and keep Cube/E2B/create paths fail-closed until separately proven. Reconciliation can promote positive same-ID evidence; unresolved ambiguity remains visible to Run/Task recovery and Budget, never silently retried or marked success. Verify real Docker behavior plus SQLite/PostgreSQL race/failure cases and independent review before claiming T19 acceptance.

This design deliberately favors safety over liveness. If T19 requires unattended recovery from every unknown Docker start, the pinned Docker exec API is insufficient: a daemon-lost ID or a `Running=false, ExitCode=0` observation cannot distinguish no send from completed side effects. A provider-side idempotency key with durable lookup, or an application command protocol with durable per-operation acknowledgement inside the sandbox, is needed for that stronger guarantee.
