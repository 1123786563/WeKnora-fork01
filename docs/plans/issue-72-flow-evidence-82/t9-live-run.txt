## §D BLOCKED analysis — "customer wallets missing" (A5)
Verbatim failing assertion (t9LagoSnapshot, lago_settlement_integration_test.go:398-399):
    if len(wallets) == 0 {
        return nil, fmt.Errorf("customer wallets missing")
    }
  (surfacing as: settle_drives_the_rails_and_the_webhook_finalizes:
   "capture complete pre-replay Lago snapshot: customer wallets missing")

Chain up to that point PASSED on the live stack: subscription active, invoice
finalized + payment_status succeeded, exactly one succeeded Lago payment.
The assertion then requires an ACTIVE wallet named "<extPurchase>-<period>".
Facts established:
  - Neither the test nor the LagoAdapter ever grants a wallet in this chain
    (grep: zero CommandKindGrantIncludedCredits / createWallet calls in the test;
    settle is spec'd to perform NO Lago state write).
  - Wallets are granted ONLY by the application service layer
    (service/commercial/purchase_fulfillment.go:302, benefits.go:431), which the
    tagged test does not invoke.
  - The fresh stack's wallets table is EMPTY after the run (psql count=0) — the
    wallet is not created-and-missed; it is never created.
  - No deploy/lago-lab fixture seeds it (fixtures.py/phases.py: zero wallet refs).
=> The wallet expectation depends on state the test cannot produce on a fresh
stack; historical greens (settle-evidence, r4-flow*) rode a long-lived lab stack
where application-level flows had granted wallets. NOT an env-assembly knob I may
turn: hand-seeding the wallet via API would fabricate the very fact under test.
NOT a product defect either (the settle chain itself is green). Classification:
BLOCKED — harness-state dependency in the tagged test's wallet snapshot. Fix
belongs to the test (drive the application fulfiller or drop/seed the wallet
expectation explicitly) — outside this task's authority to change assertions.
