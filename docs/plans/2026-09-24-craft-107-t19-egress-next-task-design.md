## First task: E0 pinned provider-route and bypass feasibility probe

**Goal:** establish, on the exact built Linux ARM64 image, whether OpenCode can be forced through a private per-Run OpenAI-compatible adapter endpoint and whether a container network policy can deny direct gateway/provider egress. This is the smallest independent, reviewable prerequisite to implementing durable physical-attempt identity. It may conclude `blocked` with exact evidence; it must not claim T19 complete.

- **Dependencies:** T01 pinned ARM64 image build evidence above; a disposable local Docker network, mock OpenAI-compatible endpoint, and mock gateway/provider listener. No real provider key, paid call, persistent service, production gateway or shared test DB.
- **Owner:** runtime researcher (read-only protocol task). **Owned output:** one new report under `docs/testing/craft/` plus bounded, disposable probe script/fixtures under `docs/testing/craft/egress-probe/` if needed. Do not change `docker/craft/*`, gateway, RunView, migrations, or application tests. Record image ID, exact command, endpoint/config path, observed HTTP route/headers/body, retry/redirect behavior, network inspection and listener counts. Coordinate output filename with the integration owner before dispatch.
- **Consumes:** OpenCode 1.18.4 image and documented configuration/plugin contract; existing RunView/container network expectations. **Produces:** a measured provider baseURL/configuration recipe and a network-enforcement recipe with evidence, or a precise blocker. Treat a route demonstrated only by a mutable OpenCode HOME setting as unsafe until creation and recovery can verify or seal it.
- **Probe:** launch the image with no upstream credential, configure one test model to a loopback/private mock adapter by the actual supported mechanism, issue one OpenCode session/model turn, and capture the outbound request at the adapter listener. Separately attempt direct gateway, provider IP, provider DNS name, redirected target, custom baseURL and proxy-env routes from the OpenCode container under the proposed Docker policy. Inspect effective network attachment, DNS, proxy env and route configuration; repeat after container restart with the same HOME. Prove the adapter can be the only reachable model endpoint without placing a gateway credential or upstream API key in OpenCode's writable HOME/workspace. Record any OpenCode automatic retry count and whether it can be disabled; do not infer retry identity from equal bodies.
- **RED checks / exit evidence:** before testing the policy, demonstrate that the unprotected baseline can reach the mock direct listener or state why that control is unavailable. With policy applied, the intended adapter receives exactly the observed model request; every direct/bypass listener receives zero requests, including after restart and custom route/proxy attempts. A missing route, unexpected direct connection, mutable setting that OpenCode can override, or inability to enforce/inspect the policy is a failed probe with precise command and output. A nonzero provider invocation count during budget denial is never acceptable in later integration tests.
- **Review:** independent reviewer checks the report against command/output artifacts, image digest, baseline control, and bypass attempts. The probe does not modify production code, so no gateway/adapter behavior is represented as verified.

## Follow-on implementation seam after E0 passes

Dispatch E1 as a backend implementer task owning only new model-attempt SQL migrations and a dedicated `internal/modules/craft/modelattempt` repository/API/tests. Its public contract should atomically allocate `(tenant, run, delegation, RunView generation, model-call ordinal, physical-attempt ordinal)` and opaque attempt ID; CAS transition `prepared → forwarding` **before** network `Do`; persist completed/definitely-unstarted/unknown/reconciled/parked outcomes; enforce unique ordinals and fenced leases; and validate a proof against the authoritative committed row. No request body, provider key or uncommitted sidecar file is identity authority. RED tests must cover duplicate allocation/nonce, two-worker race, crash at every send boundary, unknown restart without reforward, stale generation/grant, changed model/body, DB outage and key rotation. Keep the handler, runtime provider and Docker files with their current owners; only after E1's reviewed checkpoint is integrated should E2 adapter and E3 gateway validation be assigned, then E4 RunView/network assembly, then E5 live acceptance. Gateway verification must precede `BeginBinding`; repeated proof can only retrieve/reconcile its existing attempt and never create another provider send. Paid egress stays disabled until E5 proves the no-bypass route and once-only accounting on the pinned image.

## Decision and blocker rule

**Dispatch E0 now.** The prior lack of a Linux image is resolved for ARM64, so the probe is feasible without touching concurrent production edits. The pinned `chat.headers` hook alone cannot meet the identity invariant: it has no proven durable pre-physical-attempt record or retry decision, and equal HTTP bodies can be a retry or a deliberate next call. That is a verified limitation of the documented hook, **not** proof that the adapter route is impossible. If E0 cannot force and seal the provider endpoint or deny every direct path on the exact image, record that specific observed failure as the blocker, keep model egress default-off, and do not start E1 as though a route exists. If E0 passes, E1 can be implemented and reviewed independently of the currently active gateway/RunView owners; the eventual end-to-end route remains gated on E2–E5.
