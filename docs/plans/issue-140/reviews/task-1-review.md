# Task 1 independent spec and quality review

Reviewed `38d2d1d037ab9b15470f4f7f15bc84de3f138d83..95fe03c4865dfb5b5b59810e380763ecf9f7421f` in the Task 1 worktree. Implementation commit is `75b6343583fb91f15c165877d7d3f6fa24935fc6`; the later commit records its report. Sources: approved main-port design, approved job-search spec, ADRs 0017–0018, `CONTEXT.md`, current implementation plan, Task 1 brief, and `docs/plans/issue-140/reviews/task-1-contracts-api-desk.md`. The latter is the available Review Package; no separate diff package was found, so I reviewed the exact Git range.

## Verdict

- **Spec compliance: FAIL.** This is an initial seam, but the required strict and complete versioned contract/API plus cross-client Desk interface are not frozen. The approved port design requires every external response to be decoded before state changes; the plan requires all Career DTO variants and same-ID recovery.
- **Code quality: FAIL.** Valid malformed data and failed response envelopes pass the decoders, write inputs are unchecked, and the Desk cannot directly consume the exported `CareerApi`. These defects affect data consistency and the security boundary for downstream clients.

## Findings

1. **High — failed/malformed response envelopes can become authoritative data.** `packages/api-client/src/career/index.ts:9-16` accepts `listOpportunities` whenever `data` exists and lets `getEvaluation`/`getApplication` unwrap `data` or parse the raw result without checking `success`, a request receipt, or envelope keys. `decodeCareerProfile` in `decode.ts:4-12` checks a request ID only when a caller supplies one and allows unrecognized envelope keys. Reproduction at reviewed HEAD: `createCareerApi(async () => ({success:false,data:validApplication})).getApplication('x')` resolves as an application. A failure/forbidden/unknown outcome can appear as success. **Correction:** define one explicit versioned response envelope and strict endpoint decoders, reject `success !== true`, malformed/unknown fields and mismatched/missing write receipts, and test every endpoint with failure and malformed fixtures.

2. **High — application snapshot decoder accepts invalid revision, empty ID, and nested authority fields.** `packages/api-client/src/career/decode.ts:19-28` validates top-level revision but checks nested `opportunitySnapshot.revision` only with `Number.isSafeInteger`, never requires positivity; it validates neither application ID nor snapshot opportunity ID as non-empty and never rejects extra nested fields. Reproduction: an application with `id: ''`, snapshot revision `-1`, and `opportunitySnapshot.tenantId: 'other'` is returned unchanged. This violates strict snapshot and untrusted-authority decoding and can bind an application to an invalid evidence version. **Correction:** move application and snapshot-ref parsers into canonical contracts, validate positive revision/non-empty IDs/exact nested keys/digest, and test hostile nested fields and zero/negative revisions.

3. **High — required Career API surface and Desk port do not meet at an interface.** `packages/api-client/src/career/types.ts:4-10` exports only profile read/write, opportunity list, evaluation read and application read. It omits search, creation, materials, submission, timeline, reminders, privacy/export/delete, and request lookup needed by the approved three-client workflow. `packages/career-core/src/index.ts:2-5` instead requires `api.act` and `api.list`, which `CareerApi` does not expose, and its reads carry no scope/revision request input. Downstream clients cannot use the shared Desk with the canonical API without implementing a second, unreviewed business/transport adapter. **Correction:** freeze an endpoint/command and lookup interface covering the planned DTO variants, provide the adapter from `CareerApi` to Desk, and compile-test a representative Web/Mini/Expo assembly against it before forks.

4. **High — Desk has no revision/conflict and unknown-outcome protocol despite its ownership claim.** `packages/career-core/src/index.ts:12-24,35-57` saves and resends an intent, but ignores receipt revision, does not validate positive `expectedRevision`, has no request-status lookup, and treats every thrown response (including a definite 409/403) as a pending unknown outcome. `reconcilePending` blindly calls `api.act` again; `rebase` saves a modified intent under the original request ID, which can reinterpret an already executed idempotent request. The test at `test/desk.test.ts:5-17` only checks that a mock sees one ID; it does not check a lookup or conflict. This can leave permanent retry loops or alter the meaning of an idempotency key. **Correction:** model acknowledged/unknown/conflict/forbidden outcomes explicitly; look up unknown requests by the same ID before any permitted retry; accept and expose validated server revision; require an explicit new intent/key for a revised write after conflict; add behavioral tests for these branches.

5. **Medium — write request trust boundary is not encoded.** `packages/api-client/src/career/types.ts:9` defines `updateProfile.body: unknown`, `requestId: string`, and `expectedRevision: number` without runtime checks; `index.ts:16` forwards the body and headers verbatim. Empty request IDs, revision `0`/`NaN`, and client-provided `tenantId`/`ownerId` reach the server, while the decoder's authority protection applies only to responses. Server authorization is still required later, but the Task 1 strict client request contract is absent. **Correction:** define a request DTO that excludes actor/tenant/owner authority, validate non-empty ID and positive safe revision before transport, and add no-send tests for invalid inputs.

6. **Medium — profile fact and remaining DTO variants are not strict.** `packages/contracts/src/career/profile.ts:1` leaves fact `value` as arbitrary `unknown` and `source` as any non-empty string; `index.ts:31-40` admits any nested object, including authority-looking fields, as a confirmed fact. `search.ts` and `privacy.ts` export types only; no decoder covers search, export or delete receipt variants. The only fixture is `test/career/material-version.json`, and `index.test.ts` exercises four parser families in one test. The Task 1 plan asks for failing fixture tests for all Career DTO variants and receipt mismatch. **Correction:** specify and parse every wire variant and fact provenance/value schema needed by the approved spec, reject unknown nested fields, and add per-variant valid/invalid fixtures including privacy receipts.

7. **Medium — scope invalidation depends on untyped adapter behavior.** `packages/career-core/src/index.ts:3,25-29,48-52` calls parameterless `api.list()` and `api.act(intent)` while `initialScope` is a bare string. The Desk only checks generation after results return; it cannot ensure a request was sent under the intended deployment/tenant/actor or prevent a late request from being sent after scope changes inside an adapter. The existing late-write test checks discard after a single switch, not identity binding or pending-store cleanup. **Correction:** use an explicit structured scope/lease carried into every remote and store operation, invalidate it on switch, and test a switch during persistence, dispatch, lookup, and read. The server must still enforce authorization.

8. **Low — ADR 0019 authority is not traceable in this checkout.** The plan names ADR 0019 as the Desk interface authority (`docs/superpowers/plans/2026-09-28-issue-140-main-port.md:7,50,125`), but `docs/adr/0019*` is absent. The Task 1 report acknowledges this. This matters because the Desk API is being frozen for three client implementations without the decision record that defines it. **Correction:** recover the approved ADR or record an explicit ruling identifying the authoritative Desk interface before downstream tasks consume it.
