## Finding

### R2R2-C1 — Medium — A `resource://` artifact is opened through the tenant's current default backend

**Evidence:** `internal/handler/session/career_artifacts.go:215-230` parses `resource://` as no backend and no provider, then calls `StorageBackendService.ResolveFileService` with empty selectors. `internal/application/service/storagebackend.go:300-317` chooses `tenant.DefaultStorageBackendID` in that case. Only afterward, `resourceCatalogFileService.PrepareGetFile` resolves the resource's persisted physical path (`internal/application/service/file/resource_catalog.go:141-151`). A stored resource retains its own `StorageBackendID` and `PhysicalPath` (`internal/types/resource.go:44-53`); a backend-scoped physical path from an older backend is rejected by `backendScopedFileService.unwrap` when its ID differs from the newly selected default (`internal/application/service/file/backend_scoped.go:24-32,67-76`). The new single-connection regression covers only a resource on the current default local backend.

**Impact:** Changing the tenant's default backend, or storing an artifact on a nondefault backend, makes a still-ready and authorized immutable Career artifact return 404 even while its original backend remains active. This violates the approved expectation that an old material version remains viewable and the #142 exact-version download contract.

**Smallest correction:** Before constructing the file service, resolve a `resource://` reference outside `WithResolved`, verify that the stored resource belongs to the grant tenant, and use its persisted backend ID/provider to select the storage service. Keep the already prepared physical object and version object-key consistency check before opening under the session lock. Add a regression with two active backends: publish on A, switch the tenant default to B, then redeem the same signed version and verify its digest.
