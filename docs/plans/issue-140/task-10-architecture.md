# T10/#150 architecture recommendation (read-only, 2026-09-24)

## Evidence and decision

Read `CONTEXT.md`, approved `docs/specs/2026-09-23-weknora-job-search-design.md` (§§2–4, 6.1, 8), ADR-0015 and ADR-0017, #150 snapshot, T10 plan, and integrated `internal/modules/career/{office,opportunity,model_input}.go`. The approved behavior is a three-valued hard-qualification judgment before any softer match explanation. An explicit failure remains visible regardless of softer fit; a missing graduation date is unknown. Each conclusion must reopen the exact job snapshot and confirmed-profile version used when it was made. The current Opportunity importer preserves immutable raw JD, SHA-256, source and acquisition time but defaults extracted fields to unknown; its `requirements` string alone is not validated hard-condition evidence. Career profile uses an aggregate revision and append-only `career_fact_versions`, while `Open` returns latest facts. No evaluation record exists yet.

**Recommendation:** Career Office owns a distinct immutable Evaluation aggregate. It consumes a scoped immutable Opportunity snapshot and a consistent snapshot of confirmed facts; it does not mutate profile or Opportunity. Keep hard-condition evaluation deterministic and narrowly evidenced. Put any model-generated match narrative behind structured validation; if it cannot be validated, persist `needs_review` and explicit unknowns rather than favorable qualification. The plan sketch `CareerRemote.act(..., expectedRevision)` must not reuse profile mutation semantics for this read-derived aggregate.

## Contract and invariants

- Command: `Evaluate(ctx, {requestId, opportunityId, snapshotId, profileRevision?})`. Server derives Tenant/User; caller may pin a known profile revision or omit it to evaluate the current confirmed revision. No client-supplied facts, qualification values, or score. Return a stable receipt `{kind:'evaluation_created', requestId, evaluationId, opportunityId, snapshotId, profileRevision, status}`. Same scoped request ID and same canonical intent returns identical IDs/body; changed intent is 409. For an omitted profile revision, resolve and freeze it **before** fingerprinting/persistence, and handle replay using the stored original intent so a later profile change does not turn an exact retry into a new evaluation or conflict. A fresh evaluation after a profile change uses a fresh request ID (and may pin the new revision).
- Read: `GET /api/v1/career/evaluations/{evaluationId}` returns the immutable assessment plus fixed references; scoped `GET /api/v1/career/evaluations/receipt?requestId=...` supports ambiguous write reconciliation. Optionally list evaluations by `(opportunityId,snapshotId)` for history, ordered by creation. Never resolve an old evaluation through latest profile facts or latest Opportunity observation. Cross-user/Tenant IDs return not found/forbidden without private payload.
- Per hard rule: `{ruleId, criterion, outcome:'eligible'|'ineligible'|'unknown', jobEvidence:{snapshotId, observationId, acquiredAt, rawSha256, spanStart, spanEnd, quotedText}, profileEvidence:{revision, factKey?, factRevision?, confirmedAt?, source?}, reasonCode}`. A source span is a byte/rune range into the immutable raw JD and is validated against exact quoted text. An absent explicit job requirement or absent confirmed fact carries an explicit missing-side reason and no invented citation; every rule still pins the snapshot and profile revision. Rule provenance distinguishes source text, a deterministic rule, and any model inference. Never label model inference as a source fact.
- Overall hard result is `ineligible` if **any** hard rule is ineligible; otherwise `unknown` if any applicable rule is unknown or relevant hard requirements could not be interpreted; otherwise `eligible` only when all identified applicable hard rules are eligible and extraction completeness is established. A 2026 confirmed graduation year against an unambiguous “仅限 2027 届” yields ineligible; an absent confirmed year yields unknown. A bare year, ambiguous range, conflicting dates, partial URL/JD, or unreviewed extraction yields unknown. Do not treat a missing requirement as a positive match.
- Soft match is a separate list of evidence-backed strengths/gaps/unknowns for skills, projects, location and intent. Keep any ordinal fit indicator clearly named and explained as **matching evidence**, never a hiring probability; the UI and downstream application gate use the hard result independently. The safest T10 minimum has no aggregate numeric score. Any model output must cite both pinned inputs and pass schema/source-span validation; invalid output becomes `needs_review`, with no fabricated strengths. User override of advice is a separate later action/event and never edits this evaluation.
- Persist algorithm/ruleset version, extractor/model version or `none`, creation time, input digests, fixed profile revision and its confirmed-fact evidence, and complete output. Later parser/rule changes create a new evaluation; historical reads return the stored result. No Task, grant, URL fetch, application, model tool call or external side effect is implied by Evaluate.

## Persistence and consistency seam

Add `career_evaluations` plus scoped request receipts and, if not stored as an immutable validated JSON document, immutable rule rows. Unique `(tenant_id,user_id,request_id)` and opaque evaluation IDs; foreign references to immutable Opportunity snapshot and observation. A transaction reads the Opportunity snapshot and profile revision, reconstructs **only confirmed facts as of that revision** from `career_fact_versions` (latest revision `<= pinned` per key), evaluates, and inserts evaluation plus receipt atomically. Guard the profile read against a concurrent confirm: either lock the profile row in a supported way or verify the revision at the end of the transaction and retry with a fresh snapshot. A historical pinned revision must be checked against that user's profile history. Storing a compact confirmed-facts evidence copy/digest in the evaluation makes old reads and auditing independent of later projection changes; do not copy unrelated sensitive facts. Database migration must be additive for SQLite and PostgreSQL, with up/down/up coverage and current Career AutoMigrate registration.

The existing `BuildModelInput('qualification_evaluation')` reads latest `Open`, and intentionally drops source/confirmation metadata. It is **not** an adequate evaluation input seam: add a version-aware, purpose-limited input builder from the pinned confirmed-fact set if model explanation is introduced. Raw JD is untrusted data and must never supply instructions, tools, URLs to fetch, or authority. Exact source spans and user confirmation metadata stay on the server and in typed read contracts; Web renders text escaped.

## Open implementation ambiguity

The Spec does not define a complete source taxonomy/parser or numeric match formula. T08 currently has no authoritative hard-requirement extraction. T10 can deliver the specified 2027-only graduation case with a deliberately narrow, source-span-preserving deterministic rule and mark all unsupported/ambiguous conditions unknown. A broader hard-condition parser or model-assisted extraction requires its own provenance/validation contract and review before it can yield `eligible` or `ineligible`. The exact policy for a JD with *no* stated hard requirements is not explicit; recommend `unknown`/`needs_review` until extraction completeness can be established, rather than a vacuous eligible result. The graduate-date representation also varies (`graduation_year` and `education.graduation_year` exist); normalize only confirmed, unambiguous year/date values and reject conflicts as unknown.
