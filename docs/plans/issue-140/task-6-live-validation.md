## Defects found (recorded only; no production code changed)

- **D1 — official build cannot boot in real DevTools.** `dist/subpackages/execution/artifact/index.json` (from `src/subpackages/execution/artifact/index.config.ts` `usingComponents: {'t-button': 'tdesign-miniprogram/button/button'}`) emits `"t-button": "/npm/.pnpm/tdesign-miniprogram@1.17.0/node_modules/tdesign-miniprogram/button/button"`, and no `dist/npm` is ever produced. DevTools aborts app.json compilation: `[BackendInitEnv] getAppJSON error … 路径下未找到组件` and `[appservice] simulator launch catch error`, so the whole mini program white-screens. Placing the component files at the exact referenced path still fails (paths containing a `node_modules` segment are not accepted), which is why the local unblock copied `node_modules/tdesign-miniprogram/miniprogram_dist` to `dist/npm/tdesign/…` and retargeted the page JSON reference — a gitignored build-output patch, not a source fix. The 53/53 unit tests and the webpack build never load the page JSON in a real runtime, so this was invisible to them.
- **D2 — the artifact page's only action button is inert in the real runtime.** In `dist/base.wxml` every `<t-button id data-sid>` template branch carries no `bindtap`/`bind:tap`, i.e. the `onTap` prop passed via `createElement('t-button', {onTap})` is dropped for string-tag custom components by this Taro build (the native `button` template by contrast binds `bindtap="eh"` etc.). A template-level dist patch adding `bindtap="eh"` still did not deliver the event to the React handler (a console error object appeared, no signed-url POST reached the server), so the compiled runtime lacks the event registration entirely. Positive control on the same page: tapping 重新读取 (native button) reliably produced a fresh artifacts GET on the server, proving taps and handlers work and the inertness is specific to the t-button. Consequence: users cannot trigger the protected download from the mini program UI in this build.
- **D3 — “受控删除临时文件” fails silently in DevTools.** `openProtectedDocument`'s finally-block calls `unlinkSync(tempFilePath)`; in the real DevTools runtime this throws `unlinkSync:fail permission denied, open http://tmp/…pdf` and the 403-byte temp file still exists afterwards (`getFileInfo` returns it). The catch swallows the error, so the UI notice "文件在本机临时打开后立即清理，不会写入持久缓存" does not hold in this runtime. Real-device behavior was not verified (no device). Unit tests mock the file system, so this divergence was invisible to them.

## Not verified / limits

- No real phone (真机): simulator only, per the brief's fallback for missing devices.
- The app's own React `openProtectedDocument` path was not exercised by a real GUI tap (blocked by D2); it was exercised at the declared request-layer seam with the identical `wx.request`/`wx.downloadFile`/`wx.getFileInfo`/`wx.openDocument`/`unlinkSync` sequence and the app's own stored credential (its own successful GUI login), the strongest level available in this build.
- Cross-tenant denial was verified at the HTTP layer (B list/mint → 404). A second GUI login as user B was not run; the app's list is owner-scoped by construction.
- The `wx.openDocument` preview screenshot is blank (the fixture is a hand-crafted minimal PDF); the API returned success. Content rendering of real PDF/DOCX previews was not visually confirmed.
- GUI-level expiry handling (the app mapping 401 `artifact_grant_expired` to the "重新获取" notice) was not exercised in the GUI because D2 blocks triggering downloads; the server-side 401 semantics are verified above and the client mapping is covered by the 53/53 unit suite.
- Pre-existing baseline: `pnpm --filter @weknora/miniprogram typecheck` still reports 13 `CommercialSummary` errors in `account/pages.tsx` (documented in the brief as pre-existing; untouched).
