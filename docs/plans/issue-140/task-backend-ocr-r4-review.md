## Finding

**Medium — reminder race reconciliation can leave a receipt after a completed Career deletion.** `internal/modules/career/reminder.go:300-335`, `reconcileReminderSource`, reads an existing reminder and inserts a new `career_reminder_receipts` row in a transaction without locking the profile head. The normal `attemptReminderWrite` path now acquires that lock before its dedupe check (`:370-394`). `DeleteCareer` explicitly takes the same profile lock and re-purges all Career rows in its final transaction (`career_export.go:816-880`, `careerPurgeTables` at `:703-733`) so a `deleted` receipt is truthful. A failed same-source reminder request can enter reconciliation, read a reminder, then let deletion's final purge commit, and only afterward insert its deduplicated receipt. PostgreSQL's ordinary `SELECT` does not serialize against the profile lock; the receipt has no source existence check at insert. This leaves private Career data after a successful deletion receipt and breaks the documented deletion invariant. **Smallest correction:** acquire the profile row lock in `reconcileReminderSource` before reading the source reminder or writing a receipt, in the same ordering as the normal path; recheck that the source/reminder still exists under that lock. Add a behavioral concurrency test that pauses reconciliation between source lookup and receipt insertion while deletion finalizes, then asserts no Career reminder receipt remains after a `deleted` outcome.
