# T07 / #147 architecture ruling — profile intake

Date: 2026-09-24. Read-only decision support for T07. Sources: approved `docs/specs/2026-09-23-weknora-job-search-design.md` §§2, 3, 7, 9; `CONTEXT.md` 求职档案; ADR-0015–0018; `issues/issue-147.md`; `task-7-research.md`; integrated T03 Career Office and temporary-document code. This is an implementation recommendation, not a Spec change.

## Boundary and interface

**Career owns a durable source revision.** Add a tenant+owner-scoped Career intake/source record with server-issued ID, monotonically increasing source revision (per profile), upload digest, filename/MIME/size, state (`processing`, `ready`, `failed`), timestamps, parser failure category, and private resource reference. A completed revision and its provenance cannot be overwritten. A failed upload/parser attempt remains an intake attempt; it must not alter `career_facts`, `career_fact_versions`, or prior proposals. Manual entry uses `Source{kind:"manual"}` and a server-issued edit/confirmation reference; resume proposals use `Source{kind:"resume_extraction",referenceId:<source revision ID>}`. Never accept a client-chosen source ID as authority.

**Do not use `TemporaryDocumentService` as the Career source.** Its `Create/Get/OpenFile` interface requires `sessionID`, stores a 24-hour temporary document, and its cleanup removes expired content (`internal/types/interfaces/temporary_document.go`, `internal/application/service/temporary_document.go`). Directly referencing that ID would make provenance and retry depend on a chat session and expiry. Extract a narrow reusable upload/parse adapter below both services, backed by existing `FileService`, `ResourceCatalog`, `docparser`/`DocumentReader`, and existing file validation/byte limits. Career receives only a scoped stored-file handle plus extracted text or a typed failure; it does not copy the broad temporary-document prompt, OCR, lifecycle, or session API. If factoring the parser is too large for T07, a bounded bridge may parse a temporary document and immediately promote its bytes/result into a Career-owned resource before expiry; the Career record must never retain the temporary ID as its only source. This bridge has higher race and cleanup cost.

**Per-field proposals, one extraction batch.** Represent each atomic fact with stable `key` (category + item ID + field, not an array-position key), string value, source revision ID and status. Categories are education, experience, project, skill, quantified achievement, certificate, preference; omitted/unknown values are absence or explicit review metadata, never invented facts. For a conflict, retain separate pending alternatives and show the existing confirmed value; do not silently replace it. One upload creates one immutable source revision and one proposal batch, with each field pointing to that revision. User confirmation remains per proposal through T03 `confirm_proposal`; dismissal remains per proposal. T03's `Fact` collection, not all proposals, is the only read seam later evaluation/material generation may consume. Do not add a second confirmed-profile table.

**Batch atomicity and replay.** A server-side `CompleteIntake(sourceID, extractionBatch, requestID, expectedRevision)` should atomically insert all proposals and a receipt/change record, or none. The request ID is scoped to tenant+owner; replay with identical canonical batch returns the stored receipt, while changed input returns idempotency conflict. Check replay before expected-revision CAS so a successful retry still returns the original result after profile revision advances. A stale new batch returns current revision and leaves no partial proposals. Source completion and batch insertion need a recoverable transaction/outbox boundary because blob storage, parser, and DB do not share a transaction; retry processing the same source must not duplicate proposals. User confirmations use T03's existing per-action expected revision and idempotency behavior.

**Raw data and model boundary.** Keep raw resume bytes and unredacted extracted text in private Career source storage with tenant+owner checks, separate from normal profile/proposal list payloads. Store the digest and minimal provenance for confirmed facts even if raw bytes are later purged. Apply the product's actual retention/delete policy through the Career deletion path in T22; do not silently impose a new duration here. T07 should support explicit source deletion/retention state and avoid permanent backup copies in temporary storage. For model calls, construct a purpose-specific payload from confirmed facts only, allowlist relevant categories, and strip government ID/passport/identity-document numbers before serialization. Raw source text is accessible to extraction only; any later raw-source model use requires the Spec's purpose notice to the user. Redaction belongs at the server model-input builder, with assertions on the final serialized request, not merely in UI display.

## Ownership and verification map

| Owner | Files/seam | Focused checks |
| --- | --- | --- |
| Career backend | `internal/modules/career/office.go`, new intake/source and model-input files in that module, `handler.go`, Career migrations through `NewOffice` | scope, immutable source revisions, batch CAS/replay, no partial proposals, failed upload preserves confirmed facts/history, confirmed-only consumer, redacted final model payload |
| Shared parser/storage adapter | `internal/application/service/temporary_document.go` only for narrow extraction if necessary; new shared adapter under `internal/modules/knowledge/docparser/` or `internal/application/service/`; `internal/types/interfaces/` only for its narrow interface; `internal/types/resource.go` for Career resource owner if catalog requires it; `internal/container/container.go` for wiring | same MIME/size/sniffing controls; parser failure and expiration race; scoped resource retrieval/cleanup |
| Wire contract | `packages/career-core/src/contracts.ts` and contract tests | source/batch status, category/key/proposal metadata, revision and error decoding; no resource ref or raw text in normal view |
| Web client | Career route/API adapter and intake/review UI in `apps/web/src/` after T03 Web route is frozen | missing/conflicting fixture, per-item confirm/dismiss, stale refresh, failed replacement, upload status |

The shared adapter is a prerequisite for the Career upload handler. Backend contract should freeze before Web implementation and before T08 changes shared Career files. Existing Career `office_test.go`, `handler_test.go`, `contracts_test.go` are the natural Go test owners; add focused adapter tests beside its implementation and Web behavior tests beside its new UI. Use a deterministic parser fixture containing missing graduation date, conflicting employment dates, quantified outcome, certificate, and ID-like value.

## Conflict check

No direct Spec/ADR conflict found. The approved Spec requires confirmed facts as model input, provenance and revisions, purpose-limited raw evidence, and deletion by retention rules, but does **not** specify a raw-file retention duration. Choosing a fixed duration or irrevocable raw deletion at T07 would be a new product policy; defer that value to T22/privacy policy while implementing deletion capability. ADR-0017's immutable evidence applies to jobs/applications; Career fact/source revisions follow the Spec and T03 history model without claiming that raw resume bytes must be retained forever. T03 Web is still underway, so avoid freezing its route shape by assumption.
