# T14/#155 architecture recommendation

Read-only assessment at `2eba6c141` (2026-09-24). Sources: [issue snapshot](issues/issue-155.md), [approved Spec](../../specs/2026-09-23-weknora-job-search-design.md), [ADR-0015](../../adr/0015-job-search-as-weknora-specialist-agent.md), [ADR-0017](../../adr/0017-immutable-job-and-application-evidence.md), `CONTEXT.md`, and [Task 14 plan](../2026-09-24-issue-140-implementation.md).

## Boundary and ownership

Career owns the Application, immutable evidence references, qualification warning, receipt, and link state. Workbench owns Task identity, ownership, lifecycle, and its durable creation receipt. A Career Application references one Workbench Task; it does not copy or mutate Workbench task state. The HTTP layer authenticates and supplies scope; neither client-provided tenant/owner nor a returned Task ID is authority. A single-member Career space is checked by `Office.requireSpace` (`internal/modules/career/office.go`); Workbench must independently fence tenant and owner. Workbench read/archive ownership currently derives from `agent_runs(tenant_id, owner_id, session_id)` (`internal/application/repository/workbench_task_state.go`), and `task_id = session_id` is its existing convention. A bare `sessions` insert would therefore create an invisible/unowned Task. The existing `AdmissionCoordinator.Start` requires session, text, budget, and starts an execution (`internal/modules/workbench/service/workbench/admission.go`); it is not an appropriate implicit Task creation API. Introduce a small Workbench-owned `EnsureApplicationTask` adapter that establishes the Task and its ownership projection without starting a run, or explicitly define a distinct Workbench-owned session/Task lifecycle. Do not have Career write Workbench tables directly.

Career can atomically validate scoped evidence and persist Application + immutable pin set + idempotency receipt + `linking` intent in its own transaction. It cannot claim atomic Application-plus-Task creation across module APIs. After Career commit, invoke the Workbench adapter with a **stable key derived from the original Career create request ID** and the authenticated scope. Workbench must make that key unique and return the same Task ID on replay; a changed intent under the same key conflicts. Then Career conditionally changes `linking` to `ready` with the returned Task ID. A retry or recovery worker reads the persisted intent and uses that same key; it never allocates a replacement key after a timeout. A response with unknown Workbench outcome leaves `linking`, exposes reconciliation, and blocks Task-dependent actions. If Workbench has definitively rejected creation, retain a visible recoverable failure state and retry only under the same key after the cause is addressed. This is a two-step durable workflow, with local atomic writes at each owner, not a distributed transaction.

## Stable interface proposal

- Career command: `CreateApplication(ctx, {requestId, opportunityId, snapshotId, evaluationId, batchIdentity, continueDespiteHardFailure, expectedRevision}) -> {applicationId, linkState, taskId?, pinnedEvidence, warning}`. The request ID and canonical intent fingerprint are immutable per `(tenant, owner)`; same ID/same intent returns the same Application, same ID/different intent conflicts. A separate `GetApplication`/`FindApplicationReceipt(requestId)` gives an owner-scoped recovery read. Avoid making `expectedRevision` a moving requirement on exact replay.
- Workbench port: `EnsureApplicationTask(ctx, {tenant, owner, origin:"career_application", originRequestId, applicationId, title}) -> {taskId}` and `FindApplicationTask(ctx, tenant, owner, originRequestId) -> {taskId | absent | unknown}`. Implement and name the port in Workbench; Career depends on this narrow interface, not on Workbench repositories. Enforce unique `(tenant, owner, origin, originRequestId)` and unique Task association to one Application. The Task title is display metadata, never identity. If the Task has been created but Career link commit is unknown, reconcile by the original key before retrying.
- Receipt exposes `linking | ready | link_failed` and a stable application ID; `taskId` only with `ready`. The Web client retains the original `requestId` through retry and receipt lookup. Never call `EnsureApplicationTask` again with a new ID after a 504.

The exact batch identity must be persisted separately from opportunity ID and JD snapshot ID. Use a canonical, evidence-backed recruitment batch key where known (source job identifier/company/role/location/batch), with `unknown` represented explicitly; never merge uncertain source records by title alone. Same job in distinct **known** batches is allowed; same `(tenant, owner, canonical job identity, canonical batch)` should have a uniqueness guard to prevent duplicate applications from distinct request IDs. Unknown-batch identity needs a conservative key tied to the selected opportunity/source record; do not collapse unrelated unknown batches. This follows the Spec's evidence-based deduplication and separate-batch applications (`docs/specs/2026-09-23-weknora-job-search-design.md`, sections 3–4). A stricter product decision on multiple applications within one unknown batch should be recorded before broad cross-source merging.

Pin the existing evaluation **ID**, its `snapshotId`, `opportunityId`, `profileRevision`, ruleset, and hard outcome as immutable Application evidence. `evaluationRecord` already stores scoped immutable evaluation JSON and profile revision; its receipt carries IDs and status (`internal/modules/career/office.go`, `evaluation.go`). Resolve all IDs under `(tenant, owner)` and require the evaluation's opportunity/snapshot to match the selected Job. Do not recalculate against the current profile or latest JD during create/replay. `opportunitySnapshot` stores raw text/hash/extracted fields and batch (`internal/modules/career/opportunity.go`); the pinned reference is authoritative even after source changes (ADR-0017). A hard `ineligible` outcome requires a separate explicit continuation value in the immutable intent; preserve the warning on every Application read and exclude it from qualified-application metrics regardless of later matching scores. `unknown` stays unknown and must not be advertised as eligible. Later reevaluation may create new evidence but cannot silently rewrite the Application's original pin set.

## Failure matrix

| Boundary/result | Durable state and response | Recovery invariant |
| --- | --- | --- |
| Invalid scope, missing/mismatched evaluation or snapshot, hard failure without explicit continuation | No Application or Workbench call; scoped error | No side effects; do not disclose another owner's existence. |
| Career transaction known rollback | No Application; error | Same request ID can retry. |
| Career commit acknowledgement unknown | Lookup Career receipt by original request ID; if unresolved return outcome unknown | No Workbench call until Application intent is found durably. |
| Career committed, Workbench not called or definitely failed | Application `linking` or `link_failed`; no Task ID | Resume with persisted original key; never display ready. |
| Workbench timeout/unknown | Application `linking`; no asserted Task ID | Scoped Workbench lookup/retry with same key, then conditional Career link. |
| Workbench Task exists, Career link update fails/unknown | Application remains `linking`; Workbench has one Task | Reconcile by original key and bind same Task ID. |
| Concurrent exact replay | One Application, one Workbench Task | Database uniqueness and fingerprint checks, not process mutexes. |
| Same request ID, changed payload or changed explicit override | Conflict, original receipt unchanged | No second Task and no evidence drift. |
| Same job, distinct confirmed batch | Separate Application and Task | Batch key participates in business identity. |
| Cross-owner/tenant read, create, or reconcile | Denied or not found | Every Career and Workbench query includes tenant and owner; origin key alone is never sufficient. |

## Integration risk

The principal migration risk is defining a Task that Workbench can actually list and authorize: current task ownership is tied to an owned run. Freeze that Workbench contract before backend implementation and test the real read/archive path, not just returned `taskId`. Add schema uniqueness and a recovery scan without modifying existing sessions or agent runs in place. Existing Career evidence APIs already implement scoped request receipts and bounded unknown-result reconciliation (`internal/modules/career/evaluation.go`, `opportunity.go`); reuse their semantics while keeping the new Application/Task receipt separate. No production code or tests were changed in this assessment.
