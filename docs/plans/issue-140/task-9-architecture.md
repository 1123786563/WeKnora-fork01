# T09/#149 architecture recommendation: URL evidence and paste fallback

Date: 2026-09-24. Read-only design against `CONTEXT.md`, the approved job-search Spec §§3–4/8, ADR-0015/0017/0009/0018, Issue #149, T09 research, and the integrated T08 Career Opportunity implementation. No production source domain has been vetted yet.

## Ownership and contract

Career Office owns URL intent, source policy, observation, immutable snapshot and scoped receipt. A narrow `CareerSourceAdapter` may consume an HTTP-only fetch transport; neither the chat `PluginWebFetch` nor Web owns persistence or source authorization. Web sends a typed intent and renders a typed result. The URL/page body remains untrusted data, never a tool instruction or Task Grant.

Proposed additive endpoints (names can be frozen in contract tests):

- `POST /career/opportunities/import-url` with `{requestId,url}`. Server policy determines whether any fetch is allowed. Return a durable receipt with `opportunityId,observationId,snapshotId,sourceStatus,completeness,failureCode?,acquiredAt,needsUserJD`. Keep T08's scoped `GET /opportunities/receipt?requestId=` recovery. A failed attempt is a successful *recording* operation, not a successful source read.
- Extend `POST /career/opportunities/import` with optional `{opportunityId,priorObservationId}` for a user paste following an URL attempt. Verify both IDs belong to the same Tenant/user and refer to each other; append a `manual_paste` observation and new snapshot to that opportunity. The response returns new fixed IDs, and the original URL observation/snapshot remain readable. Omission retains T08 create-new behavior. Do not infer the same opportunity merely from URL or title.
- Existing `GET /career/opportunities/{opportunityId}?snapshotId=...` should expose source status, completeness, sanitized failure code, original URL, acquired time and all snapshot IDs (or a separate scoped observation-list endpoint) so the old failed observation is openable after paste. Render raw text as inert text. Do not put raw upstream error bodies, credentials, cookies, arbitrary redirect chains or private network details in API errors.

Stable enums: `sourceStatus = complete | partial | login_required | blocked | not_found | timed_out | fetch_failed | policy_unverified`; `completeness = complete | incomplete | unknown`; `failureCode` is a bounded machine code (`login_required`, `access_blocked`, `not_found`, `timeout`, `source_unverified`, `unsupported_content`, `empty_content`, `response_too_large`, `network_error`, `redirect_disallowed`). Map unknown fetch errors to `fetch_failed/network_error`. `complete` requires an adapter-specific positive completeness check, not HTTP 200 or nonempty extraction. `partial` includes summaries/truncation. For anything except `complete`, all hard-condition fields remain `unknown`, status `needs_review`, and `needsUserJD=true`. Even on complete, T08 currently has no approved extraction authority, so extracted fields still remain unknown/needs_review until independently supported.

## Persistence and failure flow

Extend `career_opportunity_observations` additively with `source_status`, `completeness`, `failure_code`, `submitted_url`, optional `final_url`, `adapter_id/version`, and perhaps `observed_http_status` if useful; extend the API read model. T08's `source_ref` alone cannot explain a failed read. Keep snapshot text non-null: failed/blocked observation may have empty raw text and SHA-256 of empty bytes, with an explicit unavailable status; partial observations may preserve bounded fetched text but must not promote extracted hard conditions. A separate immutable observation row and fixed snapshot row should be created atomically with its receipt, also for policy rejection/timeouts. `acquiredAt` means attempt time for failure and content acquisition time for success; expose this distinction in the UI label. Use new forward-only SQLite and PostgreSQL migrations; include GORM AutoMigrate additions, up/down/up tests, and old T08 snapshot compatibility. Avoid modifying T08's released migration files.

Canonicalize only for validation/policy evaluation; preserve the submitted URL byte string as evidence. Resolve redirects through policy at **every** hop and through SSRF guards. Disallow user cookies/credentials and browser fallback. Source policy belongs in server configuration with vetted host/path and allowed access method, never client input. With zero vetted production entries, production must return durable `policy_unverified` evidence and request paste; a local fixture policy can exercise full/partial/login/404/timeout in tests. This is intentionally a real product limitation, not a claim of a shipped source integration.

The existing `web_fetch.NewPipelineFetcher` is useful only as a lower-level HTTP-only SSRF/timeout/body-limit transport after policy checks. Its `Fetch` return is just extracted text: it hides final URL, HTTP status and raw page signals needed for a trustworthy completeness/login classification, and redirect targets are SSRF checked but not Career-policy checked. Introduce a narrow transport/result interface or extend a safe HTTP-only method that reports those facts and invokes a per-redirect Career policy callback. Do not use `NewFetcher` because it can render through Chromium fallback; do not call chat `PluginWebFetch` because it has no Career authority or durable receipt. Browser-like headers in `web_fetch` should also be reviewed against each source's approved access method.

Use T08's `(tenant_id,user_id,request_id)` receipt namespace for URL and paste intents with a kind-inclusive fingerprint. Identical replay returns the same observation/snapshot; changed kind, URL, or linked opportunity under the same request ID returns 409. Never hold a DB transaction across network I/O. A persisted request claim/state, or equivalent per-scope serialization plus unique receipt reconciliation, must prevent concurrent identical calls from appending two observations; an in-progress call can return a typed pending/unknown result for recovery. After a network attempt, atomically insert observation, snapshot and terminal receipt. If acknowledgment is lost after commit, recover through the scoped receipt; if durable outcome cannot be established, return outcome-unknown rather than retrying as a fresh intent. Paste append requires a transaction that verifies ownership and linkage immediately before insert; competing distinct paste requests append separate snapshots and do not rewrite the URL record.

## Web seam and verification

The chat result card uses only typed Career receipt data. For `needsUserJD`, show the submitted link, attempt time, explicit reason and “需用户补充 JD”; keep a paste input with the same `opportunityId/priorObservationId`, a new request ID, and a link to the original snapshot. After paste, open the **new** fixed `snapshotId` and let the user revisit the URL observation. Fence late responses after Tenant/logout changes, and resolve an unknown POST outcome through receipt lookup before offering a fresh intent.

Contract tests: fixture policy + controlled HTTP server for full JD, summary, login page, explicit block, 404, timeout, redirect to unapproved host, SSRF target, oversized/empty content; assert exact statuses, no hard-condition inference from incomplete text, no browser/session bypass, no fetch for unverified source, and sanitized errors. Persistence tests: failed observation survives paste append, old and new snapshot IDs open independently, same-request replay and changed-intent conflict, concurrent requests, tenant/user isolation, cancellation/acknowledgment loss, migration up/down/up. Web browser test: URL failure → paste JD → new snapshot open → old URL trace still open. Fixed fixture results do not establish permission for any real recruiting domain.

## Outstanding release decision

No vetted source domains, path patterns, access methods or use-condition records were supplied. The source allowlist must remain empty in production until an authorized owner records that review and the initial published source list. Thus the safe T09 code can deliver truthful URL failure trace and paste fallback now, but cannot claim the Issue's “接入经核验允许读取的来源” acceptance complete for a live source. The parent should keep that acceptance blocked, with evidence, until a real source is vetted and end-to-end verified.
