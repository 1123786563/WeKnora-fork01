# T01 / Issue #120 independent Spec and quality review

**Reviewed artifact:** T01 seven-file full-content checkpoint `t01-checkpoint-01/manifest.json`, SHA-256 `5dfe2bfbd39c46415dd5d3a65d757836dab9f75a564f8286320ecdffc31327ef`. I matched each of its seven file hashes against the T01 Worktree. Source HEAD `43dcff3454d8f7ec70a37a8c06ba3087b7947b98` was externally committed after the checkpoint; the verdict is about the checkpoint, not an empty or later Git diff. I read the T01 brief and implementer report, approved web-artifact Spec and scope design, #120 issue snapshot, CONTEXT.md, ADR-0004/0009, the T00 rereview, and the reviewed recognition migration. No OCR or test suite was rerun.

## Verdict

- **Spec compliance: FAIL for T01.** The new multipart path enforces the stated shape, byte, digest and quota checks, persists separate recognition fields, and prevents a selected unrecognized input from starting a Run without a recorded continue decision. But the still-live existing association route can create recognition-null inputs that bypass that gate, and the runtime stages every workspace input regardless of the Run's selected refs. Thus the member's decision to continue *without* an unrecognized file does not constrain the material actually supplied to the Run.
- **Code quality: FAIL.** Multi-file persistence is not atomic: rollback deletes blobs after a later row-write error without removing rows already inserted. Decision checking and Run submission also have a cancel/admission race. The reported focused Go, shared frontend, and typecheck commands passed, but their tests do not cover these behavior paths.

## Findings

### F1 — High: selected-input admission does not control runtime materialization

**Evidence / affected symbols:** `CraftSessionService.StartRun` resolves and checks only `req.InputRefs` (`internal/application/service/craft_session.go:721-727`) and snapshots that selected set. `localCraftRuntime.stageWorkspaceInputs` instead calls `workspaceInputManifest`, which queries every row of `craft_workspace_inputs` for the workspace (`internal/container/craft_runtime.go:380-389, 430-455`). An unrecognized input can therefore be omitted from `input_refs`, pass admission, and still be staged under `inputs/<digest>/<name>`. Accumulated uploads can also exceed the runtime's per-round manifest caps even though each acceptance round passed.

**Impact:** The user cannot reliably continue with other material while excluding an unreadable input. The Run may see an input never chosen or acknowledged and may fail later on accumulated quota rather than at upload or admission. This violates #120's continue choice and the approved Spec's chosen-input boundary.

**Smallest correction:** Make runtime staging consume the immutable admitted Run snapshot's selected input manifest, with scope and digest verification, instead of querying the workspace-wide manifest. Add a journey test that accepts two inputs, excludes the unknown one from the Run, and verifies the runtime stages only the selected ref; cover multiple individually valid rounds.

### F2 — High: existing association route bypasses recognition and decision

**Evidence / affected symbols:** `POST /:session_id/craft/inputs` remains registered (`internal/handler/session/craft.go:132, 454-476`). Its `AssociateInput` writes `craftWorkspaceInputRow` without recognition columns (`internal/application/service/craft_session.go:611-616`). `craftWorkspaceInputRow.input` projects all-NULL columns as `Recognition=nil` (`craft_session.go:196-202`), and `requireInputDecisions` skips nil recognition (`internal/application/service/craft_inputs.go:255-259`). The nullable migration intentionally preserves legacy rows, but a newly associated opaque or executable file can take this path today.

**Impact:** A caller can associate an unknown file through the existing API and start a Run with it without the accepted-versus-understood disclosure or a continue decision. The new endpoint alone does not enforce the required server authority.

**Smallest correction:** Apply recognition and the decision requirement to every new association path, or retire the old write route when the new route is mounted. Keep a deliberate policy for pre-migration legacy rows, but do not let newly created null rows bypass the gate. Test both HTTP paths against the same admission rule.

### F3 — High: failed multi-file persistence leaves dangling accepted inputs

**Evidence / affected symbols:** `AcceptInputRound` saves all objects, then inserts input rows one at a time without a transaction (`internal/application/service/craft_inputs.go:165-196`). On an error inserting row N, `rollback` deletes *all* saved blobs but does not delete the rows inserted for files 1..N-1. `OnConflict DoNothing` is also treated as success without checking that the existing row represents the returned input.

**Impact:** `WorkspaceInputs` may advertise and Run admission may accept a ref whose bytes have been deleted; subsequent staging fails. A retry can return a new ref that was not durably associated. This breaks input immutability and recovery after ordinary database failure.

**Smallest correction:** Commit all input rows in one DB transaction and distinguish newly inserted rows from existing ones. On failure, delete only blobs that have no committed reference; handle cleanup failure with reconciliation. Add an injected second-row DB failure and duplicate/ref-collision test that checks both database rows and blobs.

### F4 — Medium: cancel acknowledgement can race with Run admission

**Evidence / affected symbols:** `requireInputDecisions` reads the latest `continue` row (`internal/application/service/craft_inputs.go:255-267`), `StartRun` performs other work, then calls `s.runs.Submit` (`craft_session.go:726-789`). `DecideInput` may upsert `cancel` at any point (`craft_inputs.go:248-252`). No shared transaction, decision revision, or compare-and-swap binds the observed continue decision to admission.

**Impact:** A concurrent cancel request can return success before a Run is submitted, yet that Run can still be admitted on the earlier continue read. The member sees a durable cancellation that did not prevent the Run.

**Smallest correction:** Bind the decision revision/hash to admission in one serialized transaction or reject cancel once admission has taken the decision. Test a controlled interleaving where cancel completes between gate read and Submit.

### F5 — Medium: `understood=true` is inferred from extension and UTF-8, without content understanding

**Evidence / affected symbols:** `recognizeCraftInput` marks `.json`, `.xml`, `.yaml`, `.csv`, `.txt` and related names understood whenever bytes are UTF-8 and contain no NUL (`internal/application/service/craft_inputs.go:199-212`). It invokes no parser, so malformed JSON, XML or CSV and arbitrary prose renamed to one of those suffixes get `understood=true`. The Spec requires accepted and understood to be distinct, and its test guidance distinguishes accepted-but-unrecognized from parsed-and-used.

**Impact:** The UI can tell the member content was understood when no parser or consumer has confirmed it. This can silently admit misleading material without the unrecognized warning.

**Smallest correction:** Report `understood=true` only after the relevant bounded parser or consumer succeeds; until then project accepted but not yet understood. Add malformed known-extension and valid parsed-content cases at the API seam.

## Scope and evidence notes

The new handler is not mounted in the production router and `CraftInputDecisionPanel` is not composed into the workbench in this T01 checkpoint. The T01 brief and implementer report assign these central route/UI hooks to controller integration; I have **not** counted their current absence as a T01-owned finding. Integration must still verify guarded HTTP authority and the browser decision journey before the overall feature is marked complete.

The T01 tests do demonstrate one unknown extension passing quota, executable magic remaining unrecognized, digest and hostile-name rejection, a selected-input gate, one idempotent Run after continue, and zero Runs after cancel in a sequential service test. The HTTP test uses a fake service and the frontend test renders static markup, so neither exercises old-route bypass, selected runtime staging, storage failure recovery, concurrent cancel, or an actual decision callback. This review changed only this report; it did not edit requirements, source, or remote issues.
