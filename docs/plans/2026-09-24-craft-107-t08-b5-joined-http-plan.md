## Global Constraints

- Add the smallest new **test-only** journey at the production router/auth assembly seam using migrated SQLite, the real persistent `CraftAccessService`, real `SessionService.GetSession`, Craft session/version services, and the configured preview service. Do not reuse the `newCraftHTTPEnv` identity-header engine as proof: it hand-builds identity, omits production RBAC/API-key route guards, and uses `craftHTTPSessions` rather than B2's real direct-read service. Existing `TestCraftAccessProductionSessionAssemblyAuthAndAudit` is a useful route/auth fixture pattern but creates ad hoc tables and mounts only access routes; extend through a new fixture/test, not by changing its claims.
- Test identity may be provisioned with test credentials/claims, but requests must cross the actual `NewRouter`/`registerSessionRoutes` guard and handler chain. A test-only principal adapter is acceptable only at the credential-verification edge; it must preserve production tenant/user/API-key middleware behavior. Confirm registration lifetime and avoid global registered-handler leakage between tests.
- Preserve the production fail-closed preview gate. B3 injects current access authority but leaves `BrowserNavigationProtected=false` and no production `NetworkChecker`. Never set either in production or substitute a no-op network checker to make a green integration test. A separately named test-gated preview exercise may prove access/revocation mechanics; label it non-production evidence.
- Do not change production source under this plan. A RED failure identifying a real code defect goes to a narrowly owned follow-up fix plan and independent review. Existing B1/B2/B3 tests remain owned by their lanes.

## Review Focus

The same authenticated actor and tenant must flow through list, generic direct Session, version metadata, file download and preview issue. Denials must not leak Session/version metadata, open storage readers, or write response file bytes. Cross-tenant and stale membership must remain denied even with a remembered grant/capability. Grant/revoke audit must be durable and attributed to the owner and target. Keep public `/p/` capability traffic on the isolated origin without main-site credentials.

## Task 1 — current-production joined denial journey

**Depends on:** B1 access/list integrated; B2 independently reviewed; B3 constructor wiring validated; SQLite migrations through `000115` plus their versioned counterparts available. **Owner:** backend implementer for one new `internal/router/craft_b5_joined_test.go` (or an equivalent single new router test file). **Validator:** backend validator, then independent reviewer. **Consumes:** `RegisterCraftSessionRoutes`, generic `GET /api/v1/sessions/:id`, production Craft access provider/checker, version store, preview registration, migrated member/grant tables. **Produces:** test evidence for the currently executable B5 subset; no new public interface.

1. Build a fresh migrated DB with tenant A owner, Viewer, Collaborator, ordinary Admin and tenant B actor; seed one registered Craft Task/Session and one immutable published version with known `index.html` bytes. Use the real container/router registration or the nearest production assembly entry that retains its auth/RBAC/API-key middleware. Arrange an instrumented file opener to count opens while retaining the real version metadata and access service. Do not rely on client-side filtering.
2. RED: issue an authenticated owner grant to Viewer and Collaborator through `POST /api/v1/sessions/:id/craft/access`. For each granted actor, traverse `GET /api/v1/craft/sessions` → `GET /api/v1/sessions/:id` → `GET /api/v1/sessions/:id/craft/versions` → `GET /api/v1/sessions/:id/craft/versions/:version_id` → `GET /api/v1/sessions/:id/craft/versions/:version_id/files/index.html`; assert the same Task/version, exact pinned bytes, and appropriate read-only boundaries. The generic direct read specifically exercises B2 rather than only `/:id/craft`.
3. Before grant and after owner revoke, repeat list and each direct route as Viewer; assert private Task absent from list, direct metadata/version/file requests denied with the route's actual 403/404 contract, no identifying body fields, zero file bytes and no new opener call. Repeat for ungranted ordinary Admin, same-tenant nonmember and tenant B actor. Remove the Viewer's active membership and recreate it with a new membership ID; the old grant must not revive access until an explicit fresh grant. Verify the version remains readable by owner throughout.
4. Exercise anonymous and API-key traffic through production guards, including a key without required chat capability and any explicitly allowed key path. Assert the expected 401/403 policy and no private content/bytes; do not assume a chat-capable API key carries a Task grant. Compare non-Craft direct Session behavior to the existing owner/Admin policy so B2 has not changed it.
5. On the production preview issue route `POST /api/v1/sessions/:session_id/craft/versions/:version_id/preview`, assert all actors receive no ticket while browser/network gates are disabled, and no `/p/` file bytes are obtainable. This is a **disabled-state assertion**, not evidence that authorized preview works. Keep separate focused B3 persistent-access tests for revoke-after-capability and current checker behavior.
6. Query durable `audit_logs`: owner grant and revoke success rows must carry tenant, actor, target, Session scope and outcome, with no duplicate side effects on denied attempts. For denied content requests, first pin the actual approved audit contract: #126 says authorization is audited, while current `CraftAccessService` visibly persists grant/revoke success only. Record missing denial rows as an acceptance gap; do not invent expected action names or claim full audit coverage. If denial audit is required, route the smallest production change through a separate owner/fix review and rerun this test.
