## Evidence and findings

### Scoped authority and immutable recovery

`BuildForRun` validates the resumed package (`internal/application/service/craft_knowledge.go:192-202`), then calls `reauthorizeKnowledgePackage` before `Publish` and `MarkPublished` (`:203-211`). The helper parses every recorded source ref, rejects incomplete or conflicting coordinates, deduplicates accepted documents, calls the shared-aware `Access` port, and requires exact document ID, KB ID and owner tenant matches (`:353-402`). It then checks each distinct owning KB using `Search` with the manifest query and accepted document IDs (`:404-423`). Returned search rows are discarded, so changed live retrieval cannot replace the accepted excerpt. For production binding, `BindCraftKnowledgeSearch` calls `knowledgeBaseService.HybridSearch` (`:61-67`); that implementation loads the requested KB, calls `authorizeKBAccess` before retrieval (`knowledgebase_search.go:143-170`), and verifies the requested primary exists. `authorizeKBAccess` checks API-key scope and `KBPermissions.Check(..., OrgRoleViewer)` for every loaded KB (`knowledgebase_search_storegroup.go:199-237`). Therefore this guarded search does prove current KB access when the production binding is used; a successful result set itself is not the authority signal.

The document and KB revocation tests (`craft_knowledge_t05_test.go:237-328`) assert a denied same-Run retry makes no second `Publish` call, exposes no files, preserves the private candidate and prepared record, and leaves `Sources` unavailable. The authorized retry test (`:154-198`) changes live retrieval after an initial publication failure and proves that the original sealed excerpt is published while a second search call rechecks KB authority.

### Low — multi-source partial revocation lacks a direct behavioral test

**Evidence / affected symbol:** Both new revocation tests use one accepted source (`craft_knowledge_t05_test.go:237-328`), whereas `reauthorizeKnowledgePackage` loops over a map of accepted document IDs and per-KB groups (`craft_knowledge.go:353-423`). **Impact:** The code appears to reject a missing row for any document and a denied KB in any group, but the focused tests would not catch a later accidental early return after checking only one source or one KB. **Smallest correction:** Add one prepared package with at least two accepted sources (ideally from distinct KBs), revoke only the latter grant, and assert zero additional publication and unchanged prepared state. This is a coverage improvement, not a present implementation failure.

### High, central integration gates — durable publication, per-Run isolation and final authority

**Evidence / affected symbols:** `internal/container/container.go:2639-2644` still does not assemble production `Publisher`, `Records` and Task authority for this service; the exercised publisher is the in-memory `t05Publisher` fake. `craft.KnowledgeRunDir` names a sibling directory under the persistent Workspace (`internal/modules/craft/knowledge.go:38-49`), with no delegate mount/read restriction in this lane. `BuildForRun` checks authority immediately before service publication, but no central dispatch call-site repeats it at the moment the delegate receives material. **Impact:** Production cannot yet rely on this recovered package, and a later Run could potentially read a previous Run's raw material or observe a grant revoked after this check. **Smallest correction:** Wire a durable atomic publisher/resumer and record store; create a Run-scoped delegate view containing only its authorized sealed files; at dispatch recheck the initiating Task grant and current material grants, then test denied reads and the revoke race at that boundary.

This review does not attribute the separately documented preexisting full-service `TestCraftSourceGuardDocumentContentCannotWidenPermissions` JSON-shape failure to fix4. The focused pass does not clear that package-wide gate.
