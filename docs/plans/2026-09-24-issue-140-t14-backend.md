# Issue 140 T14 Backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the server-side #155 application record and its independently authorized Workbench Task link without pretending an unknown cross-module result succeeded.

**Architecture:** Workbench owns a durable application-task projection keyed by Career's original request ID and exposes an idempotent ensure/find port. Career owns the application, immutable evidence pins, explicit hard-fail continuation, request receipts, and `linking | ready | link_failed`. The two modules communicate only through a narrow interface assembled in the container; Career never writes Workbench tables.

**Tech Stack:** Go/Gin/GORM, PostgreSQL and SQLite paired migrations, existing Workbench list/archive/read projections.

**Spec:** `docs/plans/issue-140/issues/issue-155.md`; `docs/specs/2026-09-23-weknora-job-search-design.md`; `docs/adr/0016-one-task-per-job-application.md`; `docs/adr/0017-immutable-job-and-application-evidence.md`; research and boundary assessment in `docs/plans/issue-140/task-14-research.md` and `task-14-architecture.md`.

## Global Constraints

- Work from the isolated T14 backend Worktree at BASE `04f29cc8cf4a8c41c7b95c9a32f0c1d64b3cac63c`; do not edit the integration Worktree or other task Worktrees.

- The Workbench projection must not enqueue or publish an Agent execution. It creates an owned, visible `waiting_user` task projection with `wait_reason = career_application_linking`; only a later explicit user action may start a real execution.

- Exact replay returns the original application/task. Same request ID with changed canonical intent conflicts. Same job plus canonical batch has one application and one Task; distinct known or user-confirmed batches are distinct.
- A hard-ineligible evaluation can only create an application when `continueDespiteHardFailure=true`; the original status and warning remain immutable and `qualified=false`.
- Unknown Workbench result remains `linking` and reconciliation uses the original request ID. Never allocate a replacement request ID after a timeout.

## Review Focus

- Changed payload under the same Career or Workbench request key must conflict without mutating the first receipt.
- A timeout between Workbench creation and Career's link update must reconcile to the same Task, never a second Task.
- Cross-tenant/owner reads, finds, archives, and reconciles must return not found or forbidden without leaking existence.
- A `waiting_user` application Task projection must be listable, readable, archivable, and restorable but must never be enqueued for worker execution.
- Same job and same batch under a new request ID must return the existing application; distinct batch identity must create a separate application and Task.

- [ ] **Step 3: Implement migrations and Office workflow**

Create `career_applications` with tenant/user scope; UUID ID; request ID and SHA-256 fingerprint; immutable opportunity/snapshot/evaluation IDs; profile revision and evidence body; canonical batch identity; explicit continuation flag; evaluation status; qualified boolean; warning body; link state; TaskID/RunID; receipt body; created/updated timestamps. `CreateApplication` must:

1. derive scope from context and call `requireSpace`;
2. validate IDs, normalized nonempty batch identity, and expected revision;
3. replay the request receipt before evidence lookup when the ID already exists, requiring an exact fingerprint and returning the stored state;
4. load opportunity and evaluation in the same tenant/user scope and verify evaluation opportunity/snapshot IDs match;
5. require current profile revision to equal `ExpectedRevision` except exact replay;
6. reject hard `ineligible` without `ContinueDespiteHardFailure`; when explicitly continued, persist warning and `Qualified=false`;
7. in one Career transaction, enforce the same job/batch uniqueness, persist immutable pin/evidence, and store `link_state=linking` with receipt before any external call;
8. invoke the Workbench linker with the original request ID after commit;
9. on success conditionally update link state and receipt to `ready` with TaskID/RunID;
10. on unknown/timeout return typed `OutcomeUnknownError` while retaining `linking`;
11. on definite linker rejection set `link_failed`, preserve the application, and return a typed invalid/link error.

`ReconcileApplicationLink` reads the scoped application by request ID and never changes its pinned intent. It calls `FindCareerApplicationTask` with the original ID, updates the same row/receipt on found, keeps `linking` on unknown, and returns the receipt.
