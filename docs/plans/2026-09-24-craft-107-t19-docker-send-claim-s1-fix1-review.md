This is behavioral PostgreSQL evidence, not a mock or migration-only check.
- **S1-R2 closed:** A per-engine `BEFORE UPDATE OF provider, container_id, exec_id` trigger/function aborts the bind write (`craft_docker_send_claim_test.go:52–73, 212–218`). The test then confirms the receipt and claim remain null, `state='intent'`, the prepared Run revision and dispatched reservation remain, and `ClaimDockerExecSend` returns no permission. A separate injected claim-write failure makes the same hold/claim assertions after a receipt is bound (`:226–235`).

### S1-F1 — Low — reservation fence preservation is implicit in the failure assertion

- **Evidence / affected symbol:** `assertCraftDockerSendPreparedAndHeld` at `craft_docker_send_claim_test.go:75–104` counts a reservation by tenant, key, Run, and `state='dispatched'`, but does not read or compare its `fence` value (`'fixture'` in `craftDockerSendFixture`). The S1 plan's failure case explicitly asks that the original `intent`/hold **and fence** remain.
- **Impact:** The test proves the dispatched hold remains and no send claim is granted. It would not catch a future bind/claim path that changed only the reservation fence while preserving state. Current S1 repository methods touch only the journal, so this is a narrow regression-test gap, not evidence of a production defect or a reason to reopen S1-R1/R2.
- **Smallest correction:** Select `fence` with the reservation row in the shared assertion and require the fixture's original value after both injected failures. This may be addressed with the next focused test edit; it does not block this Fix1 persistence gate.

**Spec compliance: PASS for S1/Fix1 persistence scope.** Both engines reject partial receipt and claim-without-receipt, enforce receipt uniqueness, preserve exact bind idempotence, reject divergent/stale/wrong-identity operations, and grant `claimed=true` to exactly one of two separately opened connection owners. The production repository and four SQL migration files retain their S1 checkpoint hashes.

The test uses isolated PostgreSQL schemas and a disposable database according to the report; the worker recorded cleanup of the generated database/role and no residual default-database extension. I did not independently repeat that administrative cleanup inspection. Trigger drop errors are ignored in the helper, but per-test schema/database cleanup also removes them; no shared production table is used.
