# Craft #107 T05 ↔ RunView R3 handoff plan

> **For Codex:** Execute as sequential SDD tasks with RED → GREEN → REFACTOR, exact uncommitted checkpoints, independent Spec and quality review, and no commit. This is an architecture handoff, not authorization to enable production execution.

**Goal:** Remove the circular wait between T05 knowledge snapshot Task 3 and RunView R3 material Task 3. Build one immutable, authorized Run package against a verified generation; then prove its exact read-only mount and recheck authority at delegate dispatch.

**Sources:** `CONTEXT.md`; approved `docs/specs/2026-09-23-craft-web-artifact-spec.md` (selected authorized sources, immutable evidence and Run isolation); ADR-0004, ADR-0008, ADR-0009; `2026-09-23-craft-107-t05-knowledge-snapshot-plan.md`; `2026-09-24-craft-107-runview-r3-material-plan.md`; `2026-09-24-craft-107-runview-r3r4-design.md`; current integration source inspected 2026-09-24. This plan refines implementation order only; the approved Spec governs behavior.

## Existing contracts and the cycle

- `CraftKnowledgeSelectionSnapshot{Query, KnowledgeBaseIDs}` is in the durable Run snapshot (`agent_run_graph.go`); `craft_session.go` records the authenticated original prompt as retrieval `Query`, which may differ from the server-composed model query. Empty selection means no KB. T05 snapshot Tasks 1–2 have independent PASS.
- `CraftKnowledgeService.BuildForKnowledgeBases(ctx, scope, runID, query, selectedKBIDs)` already checks current Task access and KB/document ACL, accepts a digest-bound `KnowledgeRecord`, and publishes through `CraftKnowledgePackagePublisher`; replay uses `CraftKnowledgePackageResumer` without new search. `RevalidateForDispatch(ctx, scope, runID)` is a separate read-only current-authority gate. `CraftKnowledgeMaterialPackage` carries RunID, directory, digest and exact files.
- `NewCraftKnowledgePackagePublisher(root, runID)` seals and atomically publishes, but its root must come from a verified RunView generation. Current `newCraftKnowledgeService` in `container.go` still writes through `localCraftRuntime.workDir` and omits TaskAccess, Records and Publisher; it is not a releasable T05 assembly.
- R3 Task 1's `CraftRunViewContainerProvider.MaterialHandle` returns an opaque generation-bound handle with private host paths after persisted binding, engine and OpenCode session reinspection. R3 Task 2 stages exact inputs under that generation. Provider expects `inputs/` and `knowledge/` read-only bind mounts. The current `localCraftRuntime.Execute` resolves the handle and stages inputs but has no T05 knowledge preparation gate.
- The two original Task 3 prerequisites refer to each other's *complete* result. The actual acyclic dependency is: accepted snapshot + reviewed T05 service/publisher + reviewed R3 material/input handle → package preparation under that handle → mount proof → read-only dispatch recheck. No T05 source builder needs a mounted container; no R3 mount proof needs a dispatched delegate.

## Global constraints and ownership

The server derives `(tenant, owner, session, Run, generation)` and all paths. The model, request body and prompt cannot choose a root, package digest, document ID, or extra KB. The retrieval query is the snapshot's authenticated `CraftKnowledgeSelection.Query`. Build and mount must finish before the first prompt. A missing record, unpublished package, stale generation, changed seal, failed ACL, unexpected directory entry or unverified mount fails closed. Retry resumes accepted bytes and never re-searches. No shared `workDir` writer or sibling Run package is a fallback. Old Version evidence remains immutable when current access is revoked.

Reserve shared files serially. T05 owns `internal/application/service/craft_knowledge.go` and focused tests; R3 owns `internal/container/craft_runview_material.go`, `craft_runview_container_provider.go`, `craft_runtime.go` and focused tests; the central assembly owner alone edits `internal/container/container.go`. The publisher owner owns `craft_knowledge_publisher.go` and its tests. Do not let T05 and R3 independently edit `craft_runtime.go` or `container.go`. R3 Task 2 fix2 must finish independent review and its exact checkpoint must be integrated before this plan dispatches a writer.

## Task H1 — T05 accepted package from the durable snapshot

**Depends on:** T05 snapshot Tasks 1–2 PASS, Publisher fix PASS, T05 dispatch-recheck service PASS, R3 Task 1 PASS and R3 Task 2 fix3 PASS/integrated (fix3 supersedes the earlier fix2 prerequisite). **Role:** backend_implementer; **validator:** backend_validator. **Owned files:** a new narrow container-side adapter and its tests (for example `internal/container/craft_knowledge_runview.go`, `_test.go`); `internal/application/service/craft_knowledge.go` and focused `craft_knowledge_t05_test.go` only for the explicit empty-selection path discovered during H1; publisher file only for a demonstrated defect, under its owner's release. No `craft_runtime.go` or `container.go` ownership in this step. **Consumes:** immutable parsed snapshot selection and actor scope from admitted Run, `CraftRunViewMaterialHandle` for the same persisted Run/generation, T05 service ports. **Produces:** accepted RunID + package digest and sealed package confined to `material.knowledge`.

1. RED: one selected KB uses the original retrieval query; explicit empty selection yields an empty but published package and a durable accepted record without search; Run A package cannot enter B's handle; changed selection/query on replay conflicts; revoked Task/KB/document access denies; publisher rejects wrong root, sibling package, partial candidate, changed seal and extra files. Assert no model-provided selection is used and replay does not search.
2. GREEN: make the publisher factory consume the verified handle internally, never an arbitrary caller string. Supply the *same* publisher instance to `BuildForKnowledgeBases` and exact RunID/digest resume. Bind `craft.Scope` to durable actor and Run identity. Preserve the immutable accepted record and expose only a server-side acceptance token or lookup; do not add host paths to API DTOs.
3. Focused service/container tests, `go test` for touched packages, `gofmt`, `git diff --check`; save pre/post file hashes, task delta and independent two-part review. A PASS releases the accepted-package interface to R3, not production execution.

**Interface decision:** If application service cannot receive a per-Run publisher without mutating a shared singleton, use a small per-Run service/factory in `internal/container`. Do not put container host paths or RunView types in `internal/application/service` and do not use `WorkspaceFileWriter` as a second material writer. Record the exact accepted digest in durable Run facts or prove that the existing immutable `KnowledgeRecord` can be loaded by authenticated scope + RunID before R3 consumes it.

## Task H2 — R3 exact read-only knowledge mount

**Depends on:** H1 independent PASS and R3 Task 2 fix2 PASS/integrated. **Role:** backend_implementer; **validator:** backend_validator. **Owned files:** `internal/container/craft_runview_material.go`, `craft_runview_container_provider.go`, `craft_runtime.go` and focused container tests; no T05 service or central assembly file. **Consumes:** the same verified generation handle and exact accepted RunID/digest/record. **Produces:** a verified `knowledge/` view containing only `craft.KnowledgeRunDir(runID)` with sealed files, mounted read-only before prompt.

1. RED: missing/unpublished/foreign digest, candidate-only package, modified bytes/seal, symlink or extra sibling entry, stale/recreated container, changed inspected mount source/read-only flag, and Run A→B carryover all deny before `inner.Execute`. Identical retry and process restart accept only the same sealed bytes. Include an actual Linux engine test that read succeeds and write fails inside the container; fake-engine tests alone do not prove OS isolation.
2. GREEN: resolve the accepted package through `CraftKnowledgePackageResumer` by exact RunID/digest and revalidate its seal/path set against the handle's `knowledge/` root. Reinspect engine mounts immediately before dispatch; the expected source is the handle's canonical knowledge path and `ReadOnly=true`. Use one preparation path for first execution and retry. No copying into `workDir` and no mount of the prior Run's directory.
3. Run focused container/race checks and actual engine mount test; save exact checkpoint and independent review. If the real engine adapter or pinned image is unavailable, mark this task blocked at the live mount proof; a fake engine PASS is only a unit-level checkpoint.

## Task H3 — current authority at final delegate dispatch and assembly

**Depends on:** H2 independent PASS and R2 RunView executor binding integrated. **Role:** backend_implementer; **validator:** backend_validator. **Owned files:** central owner serially owns `internal/container/container.go`; delegate owner serially owns the narrow dispatch file (`internal/application/service/agent_run_graph.go` or actual Craft dispatch entry after inspection) and focused tests. Do not merge these into concurrent writers. **Consumes:** durable actor/snapshot, published `KnowledgeRecord`, verified material view. **Produces:** a final pre-prompt `RevalidateForDispatch(ctx, actorScope, runID)` gate and fail-closed production assembly.

1. RED: revoke TaskWrite, selected KB or a recorded document after H2 but before delegate call; assert zero prompt/tool dispatch. Forged actor, changed Run, missing ports/record, prepared-only publication, changed snapshot or empty selection with lost TaskWrite deny. No new search, publish or record mutation occurs at dispatch.
2. GREEN: call the existing read-only service recheck at the last delegate boundary, after material preparation and immediately before prompt. Wire `TaskAccess`, durable `Records`, per-Run Publisher/Resumer and verified-handle resolver in `container.go`; remove shared `workDir` knowledge writer from the released path. If the current service constructor cannot safely accept per-Run ports, use the H1 factory rather than a mutable global publisher.
3. Review the exact wiring and dispatch checkpoints independently. Validate a real Run A→B journey: each Run sees only its selected inputs/knowledge, B continues from the durably frozen current Workspace draft (which may differ from the last promoted Version), neither Run can write read-only mounts, and failed B does not replace V1 as the default preview. Gate production enablement on live engine inspection, pinned image and joined acceptance, not on compilation or mocks. This follows the approved Spec's first-release current-Workspace continuation rule; arbitrary historical Version restoration is deferred.

## Dispatch now and review gates

After R3 Task 2 fix2 receives independent PASS and its checkpoint is integrated, **dispatch H1 now**. It depends on the already reviewed T05 snapshot, publisher and authority ports plus the reviewed R3 handle; it does **not** wait for R3 Task 3 or a mounted RunView. Reserve H1's new adapter files and leave `craft_runtime.go`/`container.go` to their current owners. H2 starts only after H1's exact package checkpoint and two-part review PASS. H3 starts only after H2's exact material checkpoint and review PASS. Each downstream worker must read the integrated predecessor checkpoint, not an empty BASE..HEAD diff; any post-review content change triggers relevant verification and review again.

**Failure handling:** If the accepted digest cannot be retrieved durably, add that smallest server-owned record interface in H1 before H2. If actor scope cannot be reconstructed from the admitted Run, stop H1/H3 rather than use Task owner as actor. If engine inspection cannot establish the actual read-only source and generation, keep the production dial disabled. Any ACL revocation denies a new dispatch while preserving already promoted historical evidence.
