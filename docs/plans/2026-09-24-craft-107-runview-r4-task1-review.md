# T01 RunView R4 Task 1 — independent Spec and quality review

## Scope and evidence

Read the approved Craft web-artifact Spec, `CONTEXT.md`, ADR-0004/0008/0009, R4 plan Task 1 and its current-Workspace ruling, S2 seed and exact-revision reviews, the Task 1 report/checkpoint and isolated patch, and the live owned runtime/test files. This review concerns Task 1 seeding only; Task 2 collection, T15 promotion, real Docker mount isolation, and end-to-end A→B acceptance remain separate gates. No OCR, source/test edits, commits, or child agents were used.

The live runtime, new focused test, and task-local patch SHA-256 values match the checkpoint exactly (`49b2650f…`, `491a277d…`, `fb4d0b9b…`). The patch contains the Task 1 `Execute` call replacement and seed helpers plus one focused test file. `go test ./internal/container -run '^TestCraftRunViewR4' -count=1` passed. `go test ./internal/container -count=1` failed; exact failures are classified below.

## Findings

1. **High — legal draft files over 20 MiB cannot seed a follow-up Run.** `seedRunViewWorkspaceOutput` permits a selected file up to the runtime artifact cap of 50 MiB (`internal/container/craft_runtime.go:548–550`) but calls `readRunViewInputObject` (`:598`). That helper reads at most `craftLocalStagedReadBudget`, defined as `craft.MaxInputBytes + 1` = 20 MiB + 1 (`:81–85`, `:1056–1067`). A sealed 21 MiB output file is valid under the draft manifest and 50 MiB artifact cap, yet the helper returns a byte-count mismatch. **Impact:** an otherwise valid retained Workspace draft cannot be continued, violating the approved failed/stopped repair flow; the focused tests use only a tiny in-memory file and never call this loader. **Smallest correction:** use a draft-object reader with an explicit 50 MiB + 1 (or declared-size + 1 within that cap) bound and the same exact byte-count/SHA-256 checks; add a >20 MiB, ≤50 MiB seed test through the real seed method.

2. **Medium — file identity can change between output preflight and read.** `inspectRunViewDraftOutput` checks `Fstatat(..., AT_SYMLINK_NOFOLLOW)` and link count at `internal/container/craft_runtime.go:675–682`, then separately `Openat`/reads at `:683–695` without `Fstat` on the opened descriptor or comparing its device/inode to the directory entry. A concurrent same-directory replacement after `Fstatat` can supply another regular file with the same bytes, including a hard link to an immutable object. The byte digest passes and the untrusted replacement is marked as an exact retry; later writes to that hard link can mutate the purported immutable object. **Impact:** the no-hard-link and immutable-predecessor guarantees do not hold under an output-directory race. **Smallest correction:** verify type, mode, single-link count, size and device/inode on the opened descriptor against the preflight entry, and recheck identity/content stability after read; use a controlled replacement test. The same discipline is needed for intermediate directory entries opened after `Fstatat` at `:710–725`.

3. **Medium — the writer epoch is checked before potentially long seeding, but not when it finishes.** `seedRunViewWorkspaceOutput` loads and compares `agent_runs.epoch` at `internal/container/craft_runtime.go:510–520`. It may then fetch and write an 8 GiB manifest, revalidate only the material layout at `:619–622`, and return to `Execute`, which can dispatch after `adoptExecutorMessageID` (`:218–240`). That adoption writes `craft_delegations` without an epoch predicate (`:404–426`). **Impact:** if the durable writer fence changes during materialization, stale work can still prepare output and reach dispatch under its old task fence; the brief requires the admitted writer authority for the seeded generation. **Smallest correction:** recheck the durable Run epoch at the seed completion/dispatch boundary and make the message-ID adoption conditional on the current fence, rejecting a lost fence before prompt. Add a fixture that advances the epoch during object retrieval and asserts no dispatch.

4. **Medium — the focused suite does not exercise the actual seed boundary.** All six new tests in `internal/container/craft_runtime_r4_seed_test.go:14–125` call validators, directory inspection or the inherited atomic writer directly. None calls `seedRunViewWorkspaceOutput` or `Execute` with a durable Craft Run, exact historical `ReadRevision`, pinned `FileService`, and verified material handle. Thus the suite cannot catch finding 1, a wrong Run/Workspace/epoch lookup, failure to call seeding before prompt, partial replay, or the unchanged Version default. **Impact:** the Task 1 RED acceptance cases in the R4 plan are largely unverified despite the focused green result. **Smallest correction:** add a narrow container integration fixture for initial empty, D1→D2 frozen seed, failed/stopped draft continuation, wrong-scope/fence, object mismatch, partial retry, and no dispatch on rejection; retain helper tests for filesystem edge cases.

## Verified behavior and limits

- The implementation loads the server-only typed `craft_workspace_seed` through `ParseDurableRunSnapshot`, rejects missing/invalid seeds, compares admitted Workspace/Run/epoch, and calls scoped `ReadRevision` for the exact frozen revision. It does not read a promoted Version or a previous Run directory. The exact-revision seam now has a persisted revision-zero origin marker; the earlier review's missing-provenance finding is addressed in the live repository code.
- It stages only manifest paths under the verified generation's private `output/`, checks canonical paths, digest, declared sizes, duplicate paths, file/directory collisions and total draft quota, uses no-follow descriptor-relative opens and no-replace atomic file publication, rejects pre-existing extras, and verifies the complete output tree. These checks are meaningful but do not close the race and size findings above.
- This Task 1 patch does not change the Version store or default preview pointer. No integration test here proves V1 remains the default after a failed B, and the current `Execute` success path still uses the legacy collector pending R4 Task 2. Runtime assembly remains default-off; no release-ready promotion claim follows from this review.
- The independent full container run failed in exactly four tests: `TestCraftAccessFeatureRegistriesAreAssemblyOwned` (missing `craft.TaskAccessChecker`), `TestWireCraftInteractionRegistrarRegistersPendingInteractions` (`agent runtime conflict`), `TestLocalCraftRuntimeRejectsKnowledgeMutationAfterResolver/changed_published_bytes_after_resolver` (`agent_runs.epoch` absent from its H2 fixture), and `TestLocalCraftRuntimeAcceptsIdenticalKnowledgeRetryAndRestart` (same missing column). The latter two H2 tests are directly impacted by the new seed step and must receive valid epoch and `craft_workspace_seed` fixture data in a separately owned correction. The two assembly failures precede this Task 1 delta. This package is **red**, not a passing gate.

## Verdict

**Spec compliance: FAIL for Task 1 acceptance.** The current-Workspace and exact-revision architecture follows the approved ruling, but a legal draft size cannot be continued, and the epoch/replacement guarantees lack a sound dispatch boundary.

**Code quality: FAIL for Task 1 acceptance.** The focused helper tests pass, yet no test exercises the production seed path and the full container package fails. Repair the findings and H2 fixtures, then repeat focused and package verification; real Linux mount and A→B behavior remain later release gates.
