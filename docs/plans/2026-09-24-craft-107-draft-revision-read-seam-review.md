## Scope and evidence

Reviewed the approved Craft web artifact Spec (current Workspace continuation, failed/stopped draft retention, immutable Version boundary), `CONTEXT.md` Workspace and Run terms, ADR-0004/0008/0009, the R4 plan, this prerequisite plan/report/checkpoint/patch, and S1/S2 reviews. Independently ran the focused draft-head selector tests and `ReadRevision` race test; both passed on SQLite. No OCR or child agent was used.

## Findings

**Medium — revision zero has no persisted provenance once the head advances.** `ReadRevision` returns an empty revision zero for any syntactically valid selected head at `internal/application/repository/craft_draft_head.go:227-229`. The S1 schema has no revision-zero row or immutable initial-state marker; the head row is overwritten by `Advance`. Thus the read cannot establish the prerequisite plan's requirement that the empty seed *match persisted empty head lineage*. For example, a selected head with missing/corrupt earlier revision history still yields a successful empty predecessor. This can let a Run seeded at revision zero proceed as if an empty origin were proven when persisted history is incomplete. **Smallest defensible correction:** record a durable revision-zero provenance marker or establish an equivalent invariant that survives head updates, and require it in this branch. If the existing schema cannot prove it, report that schema gap and keep R4 revision-zero seeding gated rather than treating a valid current head as proof. Add a corruption/lineage test after D1/D2 advancement.

**Low — the new tests do not exercise historical corruption or owner-transfer interleaving.** `internal/application/repository/craft_draft_head_revision_test.go` corrupts revision 1 only while it is current, then corrupts its head. It never corrupts D1 after D2 becomes current, deletes a historical file/revision, changes a historical source Run, or transfers owner during the read. The D1-after-D2 success test establishes selection but not those fail-closed paths. **Impact:** regressions in historical validation and snapshot authorization could pass the focused suite. **Smallest correction:** add D1-after-D2 tampering cases and a controlled owner-transfer/read interleaving; retain the one-joined-statement design.

## Verified boundaries and limits

- `ReadRevision` authorizes the Workspace and selects immutable revision metadata, source Run, and file rows in one SQL statement. The requested revision, rather than the mutable current revision, selects files. The result checks source Run owner/session/terminal state, canonical paths, duplicate paths, SHA-256 format, byte bounds, and a recomputed manifest digest. The D1-after-D2 SQLite test passes. Current-head mismatch for a requested current revision fails closed.
- A foreign owner is denied; foreign session/tenant and future revision return not found; a missing positive revision below the head and malformed selected files fail closed in the implementation. The test directly covers wrong scope, future revision, invalid path, file digest, revision digest, and current-head digest. These conclusions concern database metadata, not object bytes; R4 materialization still must verify sealed object content.
- PostgreSQL 17 and PostgreSQL race coverage are **not verified**: `TRPC_TEST_POSTGRES_DSN` was unset in the implementation report and in this review. The focused tests use `openCraftDB`'s SQLite path. The reported package-wide run failed in unrelated excerpt and Craft admission tests, with truncated output; it is not a green package-wide gate and was not rerun here.
- Independent commands: `go test ./internal/application/repository -run '^TestCraftDraftHead(ReadRevision|SelectedRead|EmptyRead|LegacyRead)' -count=1` PASS (3.039s); `go test -race ./internal/application/repository -run '^TestCraftDraftHeadReadRevision' -count=1 -timeout=120s` PASS (3.457s).

## Verdict

**Spec compliance: FAIL for release of the R4 prerequisite** until revision-zero provenance is established or the schema gap is resolved. Positive immutable revision selection and SQLite authorization behavior align with the approved current Workspace continuation, with no promotion or historical Version fallback in this delta.

**Code quality: conditional PASS for the positive-revision implementation; overall gate remains open.** The focused SQLite checks and exact checkpoint pass. Historical corruption/interleaving coverage is thin, and required PostgreSQL parity remains unverified. R4 Task 1 should remain gated on correction and PostgreSQL verification.
