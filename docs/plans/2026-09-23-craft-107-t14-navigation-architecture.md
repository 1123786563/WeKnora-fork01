# T14 / #129 browser navigation boundary — architecture recommendation

Read-only analysis, 2026-09-23. Sources: `CONTEXT.md` (Task Artifact), ADR-0004 (`taskId = sessionId`), approved `docs/specs/2026-09-23-craft-web-artifact-spec.md` (interactive local page, no external build/preview egress, isolated origin, actual page-load gate), T14 brief, independent `docs/plans/2026-09-23-craft-107-t14-review.md` (R1/R2), and T14 fix-1 plan/report in the T14 worktree. The actual Chromium 153 probe result is `/tmp/craft107/t14/browser.json`; it is local evidence, not a proposed policy.

## Decision

Keep `BrowserNavigationProtected` false until an **isolated remote browser** renders the generated page in a network namespace with a measured deny-by-default outbound boundary. Deliver only pixels and narrowly defined input events to the member's ordinary browser. The remote browser may reach the immutable preview handler through one fixed internal destination; it must not reach internet, enterprise/private ranges, metadata endpoints, Docker gateway, DNS resolvers, or arbitrary internal services. In particular, the render browser must have no general outbound route, even if a page script changes `window.location`, submits a form, opens a frame, or tries a new window. Denial must occur before any request reaches the target, including URL query exfiltration. Browser automation interception is a test observer, not the production boundary.

The remote browser is an additional execution boundary, distinct from the existing **build sandbox** and the Go **preview handler**. It must run with untrusted code permissions and resource limits, no host-mounted credentials, no cloud metadata access, no app cookies or Authorization header, no browser extensions, and a fresh context per viewing grant. The fixed internal preview path should retain the present one-time ticket and short-lived, manifest-scoped capability. The display/input gateway authenticates the member against the Task on creation and on each reconnect, binds a viewing session to one Task and immutable Version, and terminates it on expiry/revocation. It sends no DOM, original URL, arbitrary link target, browser devtools/CDP endpoint, proxy capability, clipboard contents, file downloads, or browser network API to the end-user browser. Any explicit download continues through the separate authorized artifact export path. Remote browser crashes, gateway failures, binding mismatch, exhausted capacity, or failed network attestation return unavailable/incomplete; they never fall back to direct page rendering.

This is the smallest **supported architecture that can meet the invariant**, not a claim that the current deployment already does. A minimal first implementation can offer a read-only screenshot stream and fixed click/key/scroll input. Interactive JS remains inside the remote browser. A richer bidirectional protocol is optional and expands the security surface. The external display channel's own request to the authenticated WeKnora app is expected; no untrusted page script receives its URL or controls its destinations.

## Why the alternatives do not establish the requirement

| Option | Assessment |
| --- | --- |
| `connect-src 'none'`, `navigate-to 'self'`, response CSP `sandbox` | Current probe loaded HTML/CSS/JS/SVG while observing seven external requests, including `window.location`, self-anchor and child-frame navigations. The fix-1 report records a CSP sandbox/`navigate-to` trial that still emitted direct and embedded navigation requests. No supported GREEN browser policy was demonstrated. |
| Main-app sandboxed iframe | `sandbox="allow-scripts"` blocks some powers, including top navigation, but the iframe can navigate itself or create a child-frame request. Probe captured embedded public and private document requests. Direct-open remains another path. |
| Same-origin or isolated-origin proxy | A proxy can constrain its own upstream, but cannot prevent a user browser from navigating to another host. Rewriting all relative resources through a proxy retains the same browser navigation channel. |
| Script/HTML rewrite or selective API monkeypatch | Generated scripts can use multiple navigation forms, forms, frames, popups, `location`, encoded URLs, and parser-created markup. An incomplete rewrite silently weakens the invariant and conflicts with local JS support. No finite rewrite proof exists in this repo. |
| Remote isolated browser | Provides an infrastructure-level network choke point around **the browser that executes untrusted JS**. It still needs a fixed handler ingress and an authenticated, destination-constrained display/input channel. Its effectiveness is subject to real deployment and browser probes below. |
| Fail closed | Present fix-1 behavior is the correct interim state. It meets no-egress by serving nothing, but cannot satisfy the approved interactive-preview/page-load acceptance or unlock T15 promotion. |

## Boundaries and interfaces

1. **T14 preview domain/application**: retain `internal/modules/craft/preview.go`, `internal/application/service/craft_preview.go` and `internal/handler/session/craft_preview.go` as the authority for immutable Version, allowed file set, one-time ticket, 5-minute read grant, per-read Task access, and selected running build sandbox check. `CraftPreviewConfig.BrowserNavigationProtected` must be set only by a deployment attestor for an actually configured render-browser boundary; a static environment flag alone is not attestation. Prefer replacing the boolean with a narrow `PreviewBrowserBoundary` dependency whose `Check(ctx, scope, versionID)` checks a live render-pool policy and returns a bound viewing-session identity. The existing boolean may remain false during migration. Avoid making the Go handler a general arbitrary-URL fetch proxy.
2. **T20 central assembly**: `internal/container/container.go:newCraftPreviewService` owns injection of T08 `craft.TaskAccessChecker`, `CraftPreviewDockerNetworkChecker` (Task's selected binding/config and live container inspect), and the browser-boundary attestor. T20 owns central routes and the authenticated member-facing viewing-session endpoint. New render-broker service/interface should be a separately owned module, not hidden in the file server or client UI. Suggested narrow calls: `Start(ctx, authenticatedScope, versionID) -> {sessionID, expiresAt, displayEndpoint}`; `Input(ctx, sessionID, event)`; `Stop(ctx, sessionID)`; `Attest(ctx, sessionID) -> {containerID, networkPolicyDigest, previewIngress}`. The broker, not a browser-supplied URL, chooses the version's preview ticket. All methods recheck scope, expiry and active session state.
3. **Deployment**: `deploy/craft/preview.conf` still serves only `/p/` on a separate registrable site, strips credentials, disables bearer URL logging and arbitrary upstreams. Add a dedicated render-browser image/policy under `deploy/craft/` with no default/bridge egress, a single fixed preview-handler route, blocked DNS or a fixed resolver that cannot resolve arbitrary hosts, no host network, and explicit dropped privileges/resource limits. Be careful that a network namespace with `network_mode=none` also cannot reach the handler: provide the fixed ingress through a controlled one-way IPC/sidecar path or equivalent endpoint-specific firewall route and prove it does not become a general network proxy. Keep the existing build-sandbox policy separate; its `NetworkMode=none` does not protect the end-user browser.
4. **Presentation**: the React Craft workbench under `packages/views/src/craft/` displays only the broker's rendered stream and sends bounded input events. Never put the raw preview capability or generated DOM in an ordinary browser tab/iframe. A direct visit to the preview origin should 404/unavailable outside the broker's controlled path. Existing older direct-open/iframe paths need a compatibility check before any gate opens.

The direction is workbench -> authenticated viewing API -> render broker -> narrow T14 preview handler -> immutable Version/file storage. Task authority is checked server-side. The preview handler must not call the broker as a generic URL loader; the broker must not mint its own authority or select a tenant/Version from page content. The display gateway must not expose a general remote-control API to page scripts.

## Verification required before enabling the gate

1. Keep `deploy/craft/browser_probe.py` as the red regression probe; extend it to run **inside the actual render-browser namespace** against the same selected Task/Version and deployed preview host. Record attempts before test interception, plus network-level packet/connection evidence. Attempt public HTTPS/HTTP, DNS-host, WebSocket, private IP, loopback, link-local/metadata, Docker gateway, direct `location`, anchor, form, popup, self/child-frame and embedded navigation. All forbidden destination requests must be absent at the network boundary, even if browser APIs report a failed load. Do not call a Playwright `route.abort()` result infrastructure denial.
2. Prove local HTML, CSS, JS, image/SVG, relative navigation and permitted same-preview files still render in Chromium through the viewing stream. Verify no app Cookie/Authorization or `Set-Cookie`, no bearer URL in browser-visible DOM, history, referrer or logs. Verify direct preview URLs in an ordinary end-user browser cannot redeem/read.
3. Inspect the **actual bound running** build container and remote render container, their effective network modes/firewall and ingress rules; test from inside each. The existing `probe-preview-network.sh` self-created container is useful but not evidence of a tenant's selected live binding. Fail closed on inspection error or changed configuration; do not trust a stale boolean.
4. Test Task permission revocation, ticket replay, expired grants, cross-tenant/Version/file access, render-session fixation/reconnect, browser crash, broker loss and pool capacity. No condition may fall back to direct browser rendering. Run the focused Go journey, real browser journey, deployment policy checks, and independent Spec/quality review on the exact checkpoint. T15 promotion consumes the successful page-load and no-egress evidence for that same Version only; T20 final verification must repeat it on the assembled deployment.

Until this evidence exists, T14-R1 remains unresolved for the interactive feature, T14-R2 remains a central integration gate, and `BrowserNavigationProtected` remains false. The current fix-1 report's expected RED result (`external_requests=7`, `credential_leaks=0`) is the baseline to defeat, not a passing assertion.
