# Craft #107 T05 ↔ R3 H2 independent review

Date: 2026-09-24. Scope: H2 task-local checkpoint and current owned postimages, H1 Fix 1 review, handoff plan, approved Craft web-artifact Spec, CONTEXT.md and ADR-0004/0008/0009. Read-only review of implementation; no OCR or source/test edits. H3 production assembly and final authorization recheck are separate gates.

## Findings

1. **High — The mounted knowledge tree is not constrained to the accepted Run package.** `expectedCraftRunViewMounts` in `internal/container/craft_runview_container_provider.go:597-604` binds the whole generation `layout.knowledge` directory. `localCraftRuntime.Execute` in `internal/container/craft_runtime.go:205-229` checks only the returned Run ID and digest syntax before dispatch; `RevalidateMaterialHandle` in `internal/container/craft_runview_material.go:140-159` checks layout identity and engine mount configuration, not children of `knowledge/`. The H1 publisher's `Resume` checks its target `KnowledgeRunDir(runID)` but `checkRootAndTarget` does not enumerate siblings of that path. A sibling package or other entry under the bind source is therefore readable by the delegate, violating the handoff's exact-view requirement and the Spec's selected-only knowledge rule. **Smallest correction:** immediately before dispatch, enumerate the mounted knowledge root without following links and require exactly the expected Run directory, whose exact published file set is verified against the accepted digest; reject siblings, symlinks and extra files. Add observable deny-before-`inner.Execute` tests for each case and Run A→B carryover.

2. **High — Accepted bytes are not rechecked at the last dispatch boundary.** The H1 `BuildForRun` path resumes and verifies the package when the resolver runs, but H2 then performs `ensureWorkspace`, `pointWorkspaceOutput` and `adoptExecutorMessageID` before `inner.Execute` (`craft_runtime.go:205-229`). The final `RevalidateMaterialHandle` call does not call `CraftKnowledgePackageResumer` or compare the accepted digest to the files currently under the mount. Modification, removal or replacement after acceptance can therefore cross the prompt boundary despite a valid generation mount. **Smallest correction:** carry the accepted Run ID/digest into a final package verification directly before `inner.Execute`, using the same provider-issued handle and exact published path. Reject missing, candidate-only, changed-seal and changed-byte packages. Test tampering after the knowledge resolver returns, including retry/restart of identical sealed bytes.

3. **Medium — The live Linux test proves a different mount from the provider-issued one.** `TestCraftRunViewLinuxEngineKnowledgeBindIsReadOnly` in `internal/container/craft_runview_knowledge_mount_test.go:68-100` invokes a separate `docker run` whose source is `material.root/knowledge/runs/<RunID>` and destination is `/workspace/knowledge`. The production provider binds `material.knowledge` to `<generation directory>/knowledge`; the test never inspects or reads through that provider-created container. Its read/write result proves Docker can make a sealed package read-only, but does not prove the actual RunView mount exposes the exact path or excludes siblings. **Smallest correction:** run the probe in the provider-created Linux container and inspect its actual bind, read the accepted Run package through the generation destination, and confirm writes fail there. Keep the current isolated Docker bind test as supplemental evidence if useful.

4. **Medium — H2's negative and replay behavior is mostly untested.** The new focused tests cover one `ReadOnly` drift, a missing resolver and a foreign Run ID. They do not cover foreign digest for the same Run, source drift, extra mounts, stale/recreated containers, candidate-only or tampered packages, sibling/symlink entries, or identical retry/process restart at the `Execute` seam. The underlying R3/H1 tests cover parts of these behaviors separately, but not the H2 composition that precedes `inner.Execute`. **Smallest correction:** add focused runtime tests around the actual H1 resolver and provider-issued handle for those cases; assert zero inner executions on each denial and one on identical sealed replay.

## Verdict and evidence

- **Scoped Spec compliance: FAIL.** The current H2 seam does not enforce an exact accepted knowledge view before prompt. Findings 1 and 2 violate handoff Task H2 and the approved Spec's selected-and-authorized-source boundary. H3's missing central `container.go` wiring is deliberately excluded from this verdict.
- **Scoped code quality: FAIL.** The mount configuration reinspection and fail-closed missing-resolver checks are useful, but the final gate validates mount metadata without validating mounted content. The live test exercises a different Docker bind, leaving the production engine proof incomplete.
- **Checkpoint integrity:** all four current owned files and `task-local.patch` match the SHA-256 values in `h2-checkpoint/checkpoint.json`. `craft_runview_container_provider.go` is unchanged from its preimage. The H2 task delta is preserved separately from concurrent shared-file edits.
- **Verification:** independent focused `go test ./internal/container -run 'TestCraftRunViewMaterialRevalidationRejectsChangedKnowledgeMount|TestLocalCraftRuntimeRequiresAcceptedKnowledgeBeforeDispatch|TestLocalCraftRuntimeRejectsForeignAcceptedKnowledgeBeforeWorkspaceDispatch' -count=1` passed (2026-09-24). The checkpoint records focused race PASS and an opt-in Linux Docker test PASS on image ID `sha256:9678e13bd1c7dc9650aef26623ef8ab276d46565bbd6cb006b8e308229968f11`; this review did not rerun either. The Linux test's coverage limit is finding 3, independent of its pass result.

The exact H2 checkpoint should not release H3 until findings 1–3 are corrected and reviewed. Finding 4 identifies the behavioral checks needed to show those corrections work at the dispatch seam.
