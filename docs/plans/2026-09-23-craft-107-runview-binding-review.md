## Verdict

- **Scoped binding Spec compliance: FAIL pending retention correction.** Allocation and bind identity are otherwise correct: exact admitted tenant/owner/Task/Run scope, server-random stable generation, no stored host path, one immutable runtime binding with idempotent replay. The schema currently deletes a view binding automatically with its Run, before unresolved external creation or retained draft lifecycle can be reconciled.
- **Scoped code quality: FAIL on the Medium finding below.** The store uses a guarded `INSERT ... SELECT` and CAS update, validates all coordinates, rejects partial runtime identity and returns the same view on retry. I independently reran focused domain/repository RunView tests; both packages passed. The migration's cascade policy breaks the design's retention invariant. PostgreSQL repository concurrency subtests were skipped by the implementer (`TRPC_TEST_POSTGRES_DSN` unset), although I independently applied the actual PG up/down DDL in a disposable PG17.9 transaction and rolled it back successfully.
- **T01/T05 acceptance: NOT VERIFIED.** The row and typed port do not supply per-Run filesystem mounts, a distinct OpenCode process/session, event filtering, read-only input/knowledge mounts, output collection or real Run A→B exclusion proof.

## Finding

### Medium — Run deletion silently removes unresolved runtime identity

**Evidence / affected files:** Both `migrations/versioned/000192_craft_run_views.up.sql:22-23` and `migrations/sqlite/000113_craft_run_views.up.sql:22-23` declare the composite Run FK `ON DELETE CASCADE`. Existing `agent_runs` has a Session FK with `ON DELETE CASCADE` (`migrations/versioned/000093_agent_runs.up.sql:39-41`; SQLite equivalent). The T01 isolation design requires retaining the view/session through retry observation, stop reconciliation and draft/evidence retention, deleting only after durable terminal/retention checks. I independently inserted an `allocating` view under a Run in SQLite with FK enforcement, deleted the Run, and observed view rows fall from one to zero without any cleanup check. The tests cover allocation/binding but not Run or Session deletion while the external effect is unknown.

**Impact:** A cancellation/Session cleanup path that deletes a Run can erase the only persisted generation and container/OpenCode session identity while an external process may still exist. Recovery cannot identify that resource, and lifecycle cleanup may lose retained draft/source evidence. This is particularly consequential when external create succeeded but its response was lost and the row is still `allocating`.

**Smallest defensible correction:** Remove automatic cascade and use a restrictive Run FK, then make central lifecycle cleanup explicitly reconcile/stop the external runtime, verify terminal and retention conditions, and delete the view before deleting its Run. If Run deletion must remain possible earlier, persist the unresolved binding in a separately retained tombstone with equivalent scope and generation; test Run/Session deletion with both `allocating` and `bound` views in SQLite and PostgreSQL.

## Confirmed behavior and verification limits

`CraftRunViewStore.Allocate` validates a full `RunViewKey`, generates 32 random bytes, inserts by selecting only the matching admitted Run and returns the existing row on conflict (`craft_run_view.go:104-145`). `Load` rechecks the authoritative Run owner/Session (`:68-101,147-171`). `BindRuntime` changes `allocating` to `bound` under a generation and scope CAS, requires all three identifiers and permits only exact-value replay (`:173-227`). The domain validator rejects incomplete and path-like identities (`internal/modules/craft/run_view.go:58-113`). The SQL primary key and unique generation support concurrent allocation; the state/binding CHECK excludes partial runtime rows, and `(state,updated_at)` supports recovery scans.

The focused `go test ./internal/modules/craft ./internal/application/repository -run 'TestValidateRunView|TestCraftRunView' -count=1` passed independently; `git diff --check` for these Go files passed. I also ran actual PG up → insert/read `allocating` → down in a disposable schema on PostgreSQL 17.9, with `ON_ERROR_STOP=1`, exit 0 and transaction rollback. This verifies DDL syntax and FK compatibility, not PostgreSQL lock ordering or production runtime binding. The implementation report records a full repository package pass and an unrelated concurrent T05 knowledge test failure in the broad craft module suite; neither proves Run A→B isolation.
