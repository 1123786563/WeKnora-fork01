## Finding

### High — ambiguous Run response retry changes the input refs under the same request ID

**Evidence / affected symbols:** `CraftRoutes.enrichedSend` retains `pendingRequestIdRef` after every failure (`apps/web/src/features/craft/routes.tsx:601-606,640-645`) but calls `submitDraftWithAttachments` again on retry (`:608-639`). The bridge invokes `uploadAndAssociate` for every attachment before each `submitDraft` (`packages/core/src/craft/command-bridge.ts:63-89`). That route reuploads and calls `addInput`, then returns its newly accepted canonical ref (`routes.tsx:553-583`). The backend constructs a snapshot containing those refs and hashes it (`internal/application/service/craft_session.go:774-805` in the T01 worktree); `AgentRunStore` rejects an existing `(tenant,owner,request_id)` whose `RequestHash` differs (`internal/application/repository/agent_run.go:263-278`). The route test at `routes.access.test.tsx:346-376` explicitly obtains a fresh input decision on retry; its fake increments the returned ref (`:69-75`) but asserts only that the two request IDs match.

**Failure path and impact:** First upload yields ref A, Continue is acknowledged, and POST `/craft/runs` commits Run A but its response is lost. The UI keeps request ID K. Retry uploads/associates again, receives ref B, reauthorizes B, and POSTs K with `input_refs:[B]`. The server has K bound to the original snapshot containing A and returns conflict instead of replaying the admitted Run. If the first response was a definite pre-commit failure, reusing K with new refs still means the alleged same intent changed silently. This breaks safe recovery and can strand the user after an ambiguous response.

**Smallest defensible correction:** Once the first submit body is ready, retain the canonical input refs and the **entire** frozen submit body together with K in the current Session's pending intent. A recoverable/unknown submit failure must replay those exact bytes/body and skip reupload and re-decision. An explicit new intent may use new refs only with a new request ID after the prior unknown outcome is resolved. Keep the existing fresh-upload retry for failures before any submit body was sent. Add a route test where the first submit commits but returns a lost-response error; assert the retry uses the same K, same `input_refs`, same full submit body, and no second upload/association/decision.

## Confirmed behavior and limits

`CraftApi.decideInput` posts the encoded Session path with exactly `{ref,action}`, uses the standard authenticated request transport, requires a successful envelope, and rejects a mismatched acknowledgement (`packages/api-client/src/craft/index.ts:200-221`). `uploadAndAssociate` treats missing/unaccepted recognition as failure and only suspends for `accepted && !understood` (`routes.tsx:573-583`). `decideInput` resolves a pending ref only after the server response and after checking the active Session and pending-entry identity (`:533-545`); Cancel rejects the current bridge send. Route cleanup rejects old waiters, and `submitDraft` checks the active Session before posting (`:324-337,634-637`). The route tests exercise these states with mocked transport, including narrow layout. They do not establish the backend route's deployment wiring or a real browser/screen-reader result.
