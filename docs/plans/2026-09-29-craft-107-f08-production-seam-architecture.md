# Craft #107 F08 production build receipt seam — architecture audit

Date: 2026-09-29. Scope: read-only audit of the current integration worktree against the approved web artifact Spec, `CONTEXT.md`, the relevant Issue/implementation plan, and `2026-09-28-craft-107-f08-execution-receipt-design.md`. No production code was changed.

## Proven facts

- The approved Spec requires build success, preview reachability, and a real page-load check before immutable version promotion (`docs/specs/2026-09-23-craft-web-artifact-spec.md`, lines 58–64, 74–79). T15/#130 additionally requires independent evidence bound to Run, Workspace revision, and candidate Version (`docs/plans/2026-09-23-craft-107-issue-snapshot.json`, T15 acceptance).
- `localCraftRuntime.Execute` resolves a verified RunView material capability, stages admitted inputs and knowledge, calls `e.inner.Execute`, then stages a Run-bound candidate only after delegation success (`internal/container/craft_runtime.go`, lines 399–474). It does not dispatch the pinned build command.
- Runtime construction assembles and registers `CraftWebBuildCommandGate` when a toolchain pin exists, but its comment explicitly describes a future dispatch face (`internal/container/craft_runtime.go`, lines 176–221). `newCraftDockerExecCommandFaces` constructs T03-gated normal and restricted faces; the production source search finds no caller of that factory (`internal/container/craft_exec_policy_wiring.go`, lines 89–125).
- Normal execution requires `grantID`, `activityID`, `CraftCallBinding`, a `sandbox.RemoteSandboxHandle`, and a staged request (`internal/application/service/craft_docker_normal_exec.go`, line 137). It rejects absent/non-Docker handles and a missing T03 policy before provider create. The RunView material capability contains verified host material paths and provider pointer but no remote Docker handle (`internal/container/craft_runview_material.go`, lines 16–29).
- `CraftCallBinding` requires model and funding facets as a logical call identity (`internal/application/service/craft_budget.go`, lines 174–183). `AuthorizeSandbox` is a separate sandbox ledger path keyed by durable activity (`craft_budget.go`, lines 846–890); it does not produce the binding consumed by normal exec. The F08 design records that a latest prior model call is not an authorized billing rule.
- A durable, append-only terminal receipt repository exists (`internal/application/repository/craft_web_build_receipt.go`, lines 25–75, 113–121), but the only `RecordTerminal` calls in the current source search are tests. The runtime evidence wrapper calls `CraftWebBuildEvidence(log, pin, nil)` because the writable build log has no server-observed process outcome (`internal/container/craft_web_build.go`, lines 331–382). Thus a current production build cannot establish `BuildRan` from the receipt.

## Architecture conclusion and smallest safe contract

An exact Spec-compliant producer **cannot be attached using the existing stable interfaces alone**. The missing inputs are upstream authority, not syntax: (1) a named budget owner must define and persist authorization for this fixed sandbox build activity, including how it maps to or replaces `CraftCallBinding`; (2) the RunView/sandbox provider must issue a live `RemoteSandboxHandle` after verifying the admitted tenant/Task/Workspace/Run/generation and observed container identity. Synthesizing a Docker handle from persisted `ContainerID`, borrowing the newest model call, or trusting `output/build-log.json` would cross those authority boundaries.

Once those two contracts exist, T20 can own a narrow build coordinator at the successful delegation → candidate/capture boundary. Its input should be the admitted Run identity, verified generation, deterministic server-only build activity key, provider-issued handle, and explicit budget authorization. It must construct the T04 pinned request, run T04 review and T03-gated T19 normal exec, persist the complete terminal observation under exact request identity, bind it to the sealed candidate manifest/output generation, and require receipt revalidation inside promotion fences. Recovery must reuse the same activity and observe the durable attempt, never launch a second build from a changed request. Likely owned files are the T20 container assembly/capture/promotion seam, repository receipt reader integration, and focused journey tests; upstream budget and provider APIs require their respective owners' interface decisions before implementation.

## Risk and status

The existing fail-closed behavior avoids false build success, but it prevents a legitimate build from promoting. F08 remains a delivery blocker. Repository persistence tests establish receipt storage behavior only; they do not establish production execution, budget authority, a live Docker handle, or promotion eligibility. Live PostgreSQL receipt coverage also remains unavailable without the configured test DSN, per the existing F08 report.
