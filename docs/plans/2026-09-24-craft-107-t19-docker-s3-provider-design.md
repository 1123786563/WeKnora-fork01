# T19 S3 Docker provider adapter design

Date: 2026-09-24. Read-only architecture decision for the integration worktree. No source or test edit, Docker call, agent, or commit.

## Sources and decision

Read the approved Craft web Artifact Spec Task Budget and Run recovery rules, `CONTEXT.md`, ADR 0004, [Docker exec recovery design](2026-09-23-craft-107-t19-docker-exec-recovery-design.md), [S2 plan](2026-09-24-craft-107-t19-docker-send-coordinator-s2-plan.md), [S2 Fix1 review](2026-09-24-craft-107-t19-docker-send-coordinator-s2-fix1-review.md), `docker_remote_client.go`, `remote_operation.go`, `RemoteExecRequest`/`RemoteExecResult`, S2 coordinator, and the pinned `github.com/moby/moby/client v0.5.1` methods. S2's receipt and durable exclusive claim are reviewed PASS, while its R3 physical send proof remains open.

**Recommendation:** S3 can safely implement a deliberately restricted, outputless Docker exec initiation behind S2. It cannot yet advertise the complete `RemoteExecInitiator` interface for ordinary commands. Detached `ExecStart` makes the acceptance RPC bounded, but Docker `ExecInspect` returns exit state without stdout/stderr, and the pinned client's `ExecAttach` is another `POST /exec/{id}/start`, not a passive read of an already-started detached exec. The existing `Exec` contract returns stdout/stderr and supports stdin and live `OnOutput`; silently dropping those is a behavioral regression. Keep production chargeable Docker command routing blocked until a durable output/input protocol is designed and proven or callers explicitly opt into an outputless interface.

## Exact sequence and ownership

1. The application coordinator authenticates the admitted tenant/Run/activity, current Run revision and grant. `Prepare` commits the budget reservation, unresolved `intent` journal and `protocol=docker_coordinator` before provider I/O. This is the only authority for inert create; replay is limited to the same unbound intent. Do not call legacy `StartBinding`/`Exec` for this activity.
2. The Docker adapter validates the handle, command, argv/shell, timeout, account, environment and workdir. It builds the existing in-container `timeout(1)` wrapper and calls `ExecCreate` only. This is inert with respect to the command. Create-response loss may leave an orphan inert exec configuration; after a confirmed unbound intent, a new create is safe, but must not be confused with a previously bound receipt. Do not restart a stopped container during this path: `ensureRunning` is separate provider activity and would blur the chargeable send boundary.
3. On an exact successful create response, bind immutable `(provider=docker, container ID, exec ID)` to the activity journal using S1's CAS and Run fence. A bind failure leaves the hold unresolved and **must not start**. A bound unclaimed replay uses `ResumeBound` and the same exec ID; it never creates another one.
4. Call S2 `Claim` with that exact receipt. Only the returned `DockerSendPermission` may authorize physical sending. Consume it in one non-reentrant function immediately before the RPC. A failed claim, replay, stale Run, canceled context, or missing permission cannot reach `ExecStart`. The claim is durable before transport; no DB transaction spans the RPC.
5. Make **one** `ExecStart(execID, {Detach:true, TTY:false})` call with a short, explicit RPC deadline, through an engine interface that includes `ExecStart`. There is no fallback to `ExecAttach`, synchronous `Exec`, a newly created ID, or a second `ExecStart` after any uncertain response. Record successful detached acceptance as a positive initiation signal only. Timeout, cancellation after claim, connection loss, malformed response or 5xx yields `RemoteOperationUnknown` with the same receipt and unresolved hold/fence. A crash after claim but before the physical call also remains unknown; safety sacrifices liveness.
6. `ObserveExec` loads the persisted receipt and calls `ExecInspect` for the **same ID**. Verify `ExecID` and `ContainerID` match before using any positive state. `Running=true` is running. A known previously-running ID observed later with `Running=false` and a terminal exit code can establish completion if the daemon still retains it. `Running=false, ExitCode=0` without previous positive start evidence is unknown: zero is also Docker's nil-exit representation. 404/daemon restart/container removal, mismatch, transport timeout and inspect error are unknown, never `definitely_unstarted`. Do not allocate another exec ID or release the hold from these observations.
7. `WaitExec` polls only that bound ID with a bounded caller deadline and the in-container timeout. It returns an authoritative result only with positive start/completion provenance and the restricted output contract below. Caller cancellation stops waiting, not the command; retain the receipt and fence. Failure to observe a terminal state within the bound is unknown. The idle sweeper must protect containers with unresolved claimed operations; otherwise its removal can erase the only inspectable receipt while the command may have had side effects.

## Interface restriction and output problem

The current synchronous Docker `Exec` uses `ExecCreate` with attached streams, then `ExecAttach` to *start* and read, writes `Stdin`, invokes `OnOutput` for stdout/stderr chunks, and finally inspects exit code. Pinned `client.ExecAttach` sends `ExecStartRequest{Detach:false}` to `/exec/{id}/start`. Calling it after detached `ExecStart` is a second start request and cannot be treated as a passive output attach. Detached `ExecStart` itself returns only an empty `ExecStartResult`; inspect has no output bytes. Its HTTP timeout is bounded, but it is not an exact acceptance receipt if the response is lost.

The smallest safe S3 interface is therefore a **separate outputless operation** (not an implementation of the complete `RemoteExecInitiator`): reject nonempty `Stdin` and nonnil `OnOutput` before create, accept only callers that explicitly declare `OutputPolicy=discard` (or an equivalent distinct method/type), and return exit status/duration only with `Stdout` and `Stderr` explicitly unavailable. Merely returning empty strings through `RemoteExecResult` would falsely represent a command's output as empty. If output is needed for a command, reject it before hold/create; do not silently strip it. The existing `StartRemoteExec` helper must continue to return `ErrRemoteOperationUnsupported` for Docker until a complete start/wait/observe contract exists.

A later full contract could redirect stdout/stderr to operation-scoped, size-bounded files in the sandbox and retrieve them through a fixed trusted path using a read-only archive endpoint or a provider feature that does not execute another command. It needs atomic completion metadata, truncation/error semantics, symlink-safe path ownership, durable recovery after client crash, cleanup after reconciliation, and a separate plan for stdin (pre-stage immutable input before create; never stream it after a possibly accepted start) and `OnOutput` (either ordered replay semantics or explicit unsupported status). This is larger than a narrow S3 transport change. Without it, ordinary command output and stdin-dependent execution remain blocked.

## Failure invariants

- A committed claim authorizes at most one application call to `ExecStart`; the provider has no application idempotency key. A lost response never grants another send.
- `ExecInspect(false,0)` and 404 cannot prove no send or no side effects. A stopped/removed container cannot justify replacing the ID. Preserve `unknown`, the budget hold and Run fence until an authorized reconciliation outcome.
- A positive detached Start response alone proves request acceptance, not command success. `Running=true` proves the exact ID started. A later terminal inspect can prove exit but cannot reconstruct discarded output. Exit code 124/137 must be interpreted with the existing timeout wrapper's semantics, not equated automatically with transport cancellation.
- Legacy `DockerRemoteClient.Exec` remains available only for existing non-coordinator paths; it is never a recovery fallback for a marked `docker_coordinator` journal row. Do not use `StartBinding` on marked rows. Do not expose S3 capability to Cube, E2B or Docker create.

## Verification gates

Unit/fake-engine tests should count actual `ExecStart` calls, not token consumption. Exercise two claimants, crash before create, lost create response, bind DB failure, crash after bind, crash after claim before RPC, context cancellation before/after claim, Start timeout/lost response/5xx, replay, and daemon 404. Assert same ID, at most one physical send, unchanged unresolved hold/fence on ambiguity and zero calls to `ExecAttach`/legacy `Exec`. Reject stdin, callback and output-requiring caller before create. Inspect tests must cover wrong container/exec ID, running, observed-running then exit 0/nonzero, false/zero without prior positive evidence, and 404. Include a fake that reports `ExecStart` response loss after executing a side effect; replay must not duplicate it.

A disposable real Docker integration test with the pinned daemon/client should: (a) create a command that writes a unique marker, bind/claim, detached-start once and inspect the same ID to completion; (b) demonstrate detached Start yields no stdout/stderr through the existing result path; (c) verify `ExecAttach` is a start request and is never used for output recovery; (d) observe inspect false/zero for an unstarted ID and inspect 404 after removal/restart where feasible; (e) simulate client deadline loss without re-sending and count marker writes exactly once. Run under an isolated container with bounded `timeout(1)`, no network and cleanup. Pair these tests with SQLite/PostgreSQL S2 claim races and current Run-fence tests. Only after exact checkpoint validation and independent review should any restricted path be wired; full T19 acceptance remains open for normal output, stdin, provider recovery liveness and other Issue requirements.
