# T08 denial audit Task 1 — independent scoped review

**Scope and evidence.** Reviewed the approved Craft web Artifact Spec, `CONTEXT.md`, ADR-0004, the T08 denial-audit plan, Task 1 report, checkpoint manifest, pre/post snapshots, and task-local patch. The three owned current source hashes and patch hash match the checkpoint manifest. This review covers that exact delta, not the whole concurrently changing integration worktree. No OCR was run.

## Finding

**F1 — Medium — HTTP audit acceptance is underasserted.** In `internal/router/craft_b5_joined_test.go:180-254`, `assertDenied` checks response privacy and unopened storage for several direct Session/version/download requests, but the added audit check only requires *some* `craft.access_denied` row after the entire request matrix. A route that returns a denial without writing its own audit row would still pass. The exact `+1` assertion at lines 255-275 applies only to the Viewer access-mutation request; the post-revoke requests at lines 351-357 have no audit count or attribution assertion. The preview issue path at lines 331-337 is disabled by an earlier production gate, so it does not prove a revoked Viewer preview denial is audited. This leaves the plan's highest-seam requirement—one durable row per logical direct read/preview/download denial, with current actor and bounded action—unproven. **Smallest correction:** for each reachable denied HTTP action, take a before/after count and inspect the one new row's tenant, authenticated actor, Task ID, action, and bounded details; test the preview ACL through a route/service configuration that reaches its access check. Preserve the existing no-storage-open and no-bytes assertions. This is a behavioral-test finding; the shared policy-seam implementation appears to write one row per reached `CheckTaskAccess` refusal.

## Spec and quality verdict

**Scoped Spec compliance: PASS by code inspection, with F1's HTTP proof gap.** `CheckTaskAccess` records a known tenant-scoped Task refusal after `Role` returns `ErrForbidden` or a known role rejects the action (`craft_access.go:114-151`). `Role` itself stays read-only, so nested role lookup does not double-write. `knownTask` rechecks the active tenant-scoped Craft session, and `ErrNotFound` or storage errors from `Role` do not write Task-targeted rows. Audit fields are a fixed action/outcome, current `scope.UserID`/tenant/Task identity and an allowlisted `TaskAction` plus fixed reason; the new write takes no request path, query, body, filename or content. `RequireTaskAccess` validates scope/action before this seam. The audit insertion error is logged and the original refusal is returned, so sink failure cannot authorize access. Grant/revoke audit remains transactional and its existing exact-row checks are retained.

**Code quality: FAIL pending F1.** The service test covers no-grant, Viewer write, repeated independent decisions, missing and cross-tenant Task, malformed scope, inactive membership, allowed reads, bounded row fields, and audit-sink failure. The joined test proves an exact single row for access mutation and preserves no-content-byte checks, but its aggregate row check does not establish the per-route audit behavior requested by the Task plan. No source-level security or data-consistency defect was found in the task-local production delta.
