# T08 denied Task authorization audit plan

**Goal:** Persist a bounded audit record when the authoritative Craft Task ACL refuses an authenticated actor, while preserving response privacy and existing grant/revoke audit behavior.

**Sources:** Approved `docs/specs/2026-09-23-craft-web-artifact-spec.md` (Task roles on every Craft operation and highest API journey seam); `CONTEXT.md`; `docs/adr/0004-task-is-session.md` (Task ID = Session ID); #126 snapshot in `docs/plans/2026-09-23-craft-107-issue-snapshot.json` ("Authorization is server enforced and audited"); current `internal/application/service/craft_access.go`, `internal/modules/craft/web_contracts.go`, `internal/application/service/audit_log.go`, and `internal/router/craft_b5_joined_test.go`.

**Global Constraints:** Keep this within T08 Task membership/access ownership. Do not audit raw bodies, file paths, source names, tokens, query strings, headers, or exception messages. Preserve current 403/hidden 404 response contract and fresh membership checks. Audit failure must not make authorization succeed. No new public API or schema migration is needed for the existing `audit_logs` fields.

**Review Focus:** One durable denial per logical ACL decision; no row for nonexistent or tenant-invisible Task; current tenant and actor identity only; no duplicate row from nested `Role`/`CheckTaskAccess`/`RequireTaskAccess` calls; no content bytes released before denial.

## Evidence and interpretation

- `CraftAccessService.CheckTaskAccess` is the shared real policy seam. It calls `Role`, which checks the tenant-scoped Craft session, current active tenant membership, explicit grant, then action matrix. Grant/revoke call it through `owner`; direct reads, preview, knowledge and Session routes call it through `RequireTaskAccess` or directly.
- Grant/revoke insert `craft.member_added` / `craft.member_revoked` success rows in the same transaction as the grant mutation. `craft_b5_joined_test.go` explicitly observes zero audit rows after denied content requests and before those mutations. Thus current evidence proves mutation audit only. The wording does not expressly prescribe a denial event format, but treating success-only membership changes as full audit coverage of authorization decisions leaves the highest-risk refused access unrecorded. Recommend adding denial audit; do not claim the requirement is already verified.
- Generic `rbac.access_denied` is emitted by middleware RBAC, not by Craft Task ACL. Its one-minute CountSince dedup uses actor/path and may omit Task/action distinction; do not reuse it unmodified for Craft decisions. `audit_logs` is already append-only and tenant scoped.

## Task 1 — durable denial at the policy seam

**Depends on:** reviewed B5 Task1 fix1 ACL and joined HTTP checkpoint. **Role:** backend implementer; backend validator and independent reviewer. **Owned files:** `internal/application/service/craft_access.go`, `internal/application/service/craft_access_test.go`, `internal/router/craft_b5_joined_test.go`; if a bounded denial key requires a repository helper, `internal/application/repository/audit_log.go` and its tests only after review of the existing interface. Avoid changing generic RBAC semantics.

**Consumes:** `craft.Scope`, `craft.TaskAction`, current `audit_logs` schema, current `CraftAccessService.CheckTaskAccess` and `Role` error contract. **Produces:** a single Craft ACL denial event per request/decision with `tenant_id`, authenticated `actor_user_id`, `scope_type=session`, `scope_id=Task/Session ID`, `outcome=denied`, and allowlisted action/reason code in `Details`; unchanged `ErrForbidden`/`ErrNotFound` outward behavior. Use a stable action such as `craft.access_denied` only after checking the existing audit action validation/reader. Do not persist arbitrary IDs or raw error strings in details.

1. **RED:** At the real production router seam, assert a Viewer write and revoked Viewer direct read/preview/download return their current status and produce durable denied rows with tenant, actor, Task ID and bounded Task action. Assert no file bytes/reader or sensitive marker from request body, upload filename, URL query or content appears anywhere in rows. Assert owner and allowed Viewer read create no denial rows; grant/revoke success rows remain exactly once.
2. **RED:** At service seam, cover same-tenant non-grantee, tenant Admin without grant, inactive/stale membership, Viewer `TaskWrite`/`TaskShare`, and cross-tenant/nonexistent Task. `ErrForbidden` for a real tenant-visible Craft Task should create a denial row. A missing, deleted, tenant-mismatched or intentionally hidden Task returning `ErrNotFound` must create no Task-targeted denial row, since audit readers must not learn its existence. Invalid/unassembled scope and database faults should not be reported as a proven authorization refusal.
3. **RED:** Exercise one HTTP request traversing nested access helpers and an identical retry. Require one row per logical decision, not a row at both `Role` and `CheckTaskAccess`; repeated independent requests may be recorded separately unless a documented idempotency key exists. If retry suppression is needed, use a request-scoped decision key or a database-enforced bounded idempotency key that includes tenant, actor, Task, action and request identity. Do not use a time-only suppression window that erases distinct denied requests. Test concurrent retry collision if introducing a persistent unique key. Existing middleware RBAC audit can coexist for a separate middleware refusal, but one Task ACL decision must not double-write.
4. **GREEN:** Write at the end of the `CheckTaskAccess` policy decision after determining that the Task exists in this tenant and the actor has been refused. Keep `Role` pure to avoid a duplicate from callers using it to display role. Distinguish a known Task `ErrForbidden` from `ErrNotFound` and storage errors. Insert with an allowlist of fields, not `fmt` of scope, error or request. Log the audit write error through safe operational logging if needed, while returning the original denial; document whether audit-sink outage is fail-closed for an authorization decision, as the existing generic RBAC service is best-effort. Do not silently turn a denial into success.
5. **REFACTOR / verify:** Run `go test ./internal/application/service/... -run 'Craft.*Access|SessionShare' -count=1`, `go test ./internal/router -run 'CraftB5JoinedCurrentProduction|CraftAccessProductionSessionAssemblyAuthAndAudit' -count=1`, focused handler tests, and `git diff --check`. Record exact command outcomes and snapshot hash for Review. Inspect the final diff for test assumptions expecting zero rows after denial and update only those directly affected.

## Boundary decision before implementation

`CheckTaskAccess` is the highest shared Task policy seam, but `RequireTaskAccess` can reject a nil checker or malformed scope before reaching it; those are assembly/input failures, not a known Task authorization decision. `IsCraftTask` may intentionally return 404 before a grant check to hide a missing or cross-tenant Task. Keep both cases outside Task-targeted denial audit. If reviewers decide operational policy requires recording these attempts, use a separate coarse security event without Task existence or raw path; that is a separate product/security decision, not implied by #126.
