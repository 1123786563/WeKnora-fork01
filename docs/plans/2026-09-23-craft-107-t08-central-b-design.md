### Relevant policy and provider seams

- `internal/modules/craft/web_contracts.go:8-39` defines the narrow `TaskAccessChecker.CheckTaskAccess(ctx, Scope, TaskAction)` port and fail-closed helper. Scope's `SessionID` is explicitly the Task ID. Actions include Read, Write, Share, OpenSource and Preview.
- `internal/application/service/craft_access.go:92-121` derives owner or explicit active-incarnation grant and enforces actions. `ListAccessibleTaskIDs` (`:198-220`) is an additional concrete application service query, not part of `TaskAccessChecker`; listing needs a separate port or query seam rather than widening the checker silently.
- Central A provider helper `internal/container/craft_access_wiring.go` resolves the same concrete `*service.CraftAccessService` as `craft.TaskAccessChecker` and registers access routes against the per-assembly feature registry. `newCraftSessionService` at `internal/container/container.go:2519-2538` currently does not receive the checker. `newCraftPreviewService` at `:2541-2552` currently receives versions/files/checks and origins only; T14 must first stabilize its config additions (including any network/browser-boundary dependencies).
- T01's `CraftSessionConfig` and service (`internal/application/service/craft_session.go:92-145`) currently lack access fields. Recommended post-T01 seam: required/fail-closed `Access craft.TaskAccessChecker` for per-Task read/write checks, plus a separate narrow task-list query port implemented by `CraftAccessService` (or an equivalent bounded query interface). Keep owner-scope persistence for actual workspace/version storage; use caller scope solely to evaluate current Task ACL. Suggested map: View/ListVersions/GetVersion/OpenVersionFile → TaskRead; AssociateInput/StartRun → TaskWrite. Run status/events/stop/restore/snapshots/usage/interaction endpoints are adjacent Craft surfaces and must be inventoried by their owning lane before claiming the whole Craft API is covered.

## Separate frontend product mount/API seam note

The app already mounts Craft through `apps/web/src/features/craft/routes.tsx`: `parseCraftRoute` is at lines 42-48, API construction at `:146`, and `CraftWorkbench` render at `:603+`. The API client is `packages/api-client/src/craft/index.ts:102-200`, currently exposing create/list/workspace/input/run/versions/preview/download but no access methods. A reusable presentational panel already exists at `packages/views/src/craft/access.tsx:1-36`; repository search found it imported only in its own test, not the product route.

Frontend follow-up after backend endpoints are verified: add access response/request types and `members`, `grant`, `revoke` API methods to the Craft API client using the standard `WeKnoraClient` authenticated request transport and the already-mounted endpoints; mount `CraftAccess` from `routes.tsx` in the workbench feature/side-panel composition, passing server-returned role/members and callbacks. Do not infer ownership from local `/auth/me` or use frontend `canWrite` as authorization; backend routes/services stay authoritative. Keep this frontend work in the UI lane and separate from central backend files.
