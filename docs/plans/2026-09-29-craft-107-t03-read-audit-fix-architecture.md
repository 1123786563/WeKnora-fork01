# T03 read-audit repair: architecture note

Read-only audit on 2026-09-29. Sources: `CONTEXT.md`, approved `docs/specs/2026-09-23-craft-web-artifact-spec.md`, ADR-0013/0014, T03 acceptance in `docs/plans/2026-09-23-craft-107-dag.md`, and `2026-09-29-craft-107-t03-java-source-and-read-audit-fix-review.md`. No code or tests changed or run.

## Recommended boundary

Keep operand classification and admitted-input matching in `internal/modules/craft/input_code.go`; keep durable Run identity and audit storage in `internal/application/service/craft_execution_policy.go`; keep provider outcome interpretation in `internal/application/service/craft_docker_normal_exec.go`. The normal executor must receive a reviewed observation containing the *complete* canonical read set and an activity/request identity. A plain `error` from `CraftExecutionPolicyGate.ReviewNormalExec` cannot carry that observation through to completion.

1. **Preflight (R1):** Before `prepareOrRecover` creates, binds, claims, or sends, persist one `craft.input.read` row with outcome `accepted` and details containing the complete, sorted input set (canonical admitted path, digest, and ref), Run, workspace, and activity/request identity. Treat a missing audit sink or failed `Log` as a gate error. One row uses the existing single-row `AuditLogService.Log` API and prevents a partly written read set. The row describes permission/intent, not actual use. A command with no input file operands needs no input-read row. The shared audit service currently propagates write errors, while `CraftMaterialPolicy.writeAuditRow` swallows them; make the T03 required path return an error rather than changing global best-effort audit policy. Keep denial logging best-effort, since denying already fails closed.
2. **Operand identity (R2):** Parse only the allowed reader grammar (`cat`, `head`, `tail`, `grep`/`egrep`/`fgrep`, `wc`) and identify *file operands*, not every nonflag argument. For grep, consume `-e`/`--regexp` values as patterns, `-f`/`--file` values according to their actual file-reading semantics, and the first positional pattern when no explicit pattern option exists; remaining positional operands are files. Handle `--`, option values, and combined/attached forms explicitly. If the parser cannot tell whether an argument is a pattern or a file, refuse the command rather than asserting a read. Match the canonical container path to the admitted manifest and deduplicate by that path plus digest, not `Input.Ref` (refs need not be unique). If resolved alias evidence is available, use that path for matching; the Docker server face cannot resolve container symlinks, so an unproved alias must not be reported as a verified input read. Preserve any separate execute-denial checks before granting permission.
3. **Completion (R3):** At the normal executor's provider result boundary, write a separate outcome event referring to the same preflight identity and provider receipt. A `success` read observation requires a started process, terminal process success, complete transport, and sufficient durable output/result evidence; provider create/start errors, failed processes, unknown outcomes, and claimed-never-started reconciliation must never produce it. This proves successful execution of a command naming the file, **not** byte-level proof that the process opened it; label the evidence accordingly. A failed command may have read bytes before failing, so record `failed`/`unknown` command outcome without claiming either successful read or no read. Replays that only observe a claimed receipt must not create a second success fact. If completion audit persistence fails after provider execution, return an audit/unknown outcome and retain the durable preflight record; it cannot retroactively prevent dispatch. For exactly-once completion across restart, the durable audit store needs an idempotency key or unique command outcome record keyed by activity and receipt; an in-memory flag is insufficient.

## Exact seams and failure modes

- `CraftMaterialPolicy.ReviewExecution` in `craft_delegate.go:409–424` currently writes `AuditOutcomeSuccess` during policy review and drops audit errors in `writeAuditRow:374–402`. Separate pure policy decision from required preflight persistence; `AuditInputRead` callers should keep their own semantics and not silently inherit a dispatch guarantee.
- `CraftDelegateExecutionPolicy.review` in `craft_execution_policy.go:181–239` resolves the durable Run and returns only `error`; return a typed reviewed read set/preflight identifier to the normal executor, or provide a dedicated preflight method alongside the existing gate. Bind it to the exact staged request and Run so a later request cannot reuse a different authorization.
- `CraftDockerNormalExecService.Execute` in `craft_docker_normal_exec.go:137–270` gates before `prepareOrRecover`, then owns create/send and joins `StartEvidence`, process state, transport, and sealed output. Its `observeClaimed` path at `:342` can recover terminal status but explicitly lacks complete transport evidence; do not upgrade that observation to successful read without a durable terminal completion fact. Avoid reauditing a replay as a fresh attempt unless the preflight key is idempotent.
- `AuditLogService.Log` in `internal/application/service/audit_log.go:48` returns repository errors, but its interface in `internal/types/interfaces/audit_log.go:56` only writes one row. A single accepted event with the whole read set is the smallest atomic preflight option. Multiple per-input rows require a transaction-capable API and an all-or-nothing repository implementation.

## Regression evidence to request

- Module tests in `internal/modules/craft/input_code_test.go`: `grep -e inputs/<digest>/one.csv /workspace/app/generated.txt` records no input read; positional grep pattern versus file, `--`, `-f`, attached option forms, and malformed/ambiguous options; two admitted paths with the same ref but different digest/name yield two identities; resolved alias is recorded only with actual resolution evidence.
- Gate/service tests in `internal/application/service/craft_execution_policy_wiring_test.go`: nil/failing sink and a two-input read refuse before provider/create; one accepted row contains the full canonical set; no partial set or false `success` row. Exercise the actual `ReviewNormalExec` route, not only `MaterialPolicy.ReviewExecution`.
- Normal-exec tests in `internal/application/service/craft_docker_normal_exec_test.go`: success, create/start failure, terminal failure, unknown transport, claimed-never-started, and replay/restart observation. Assert accepted preflight versus completed success/failed/unknown, provider call count, and completion idempotence using the same activity/receipt.

## Integration dependency

T03's current Docker normal-exec gate is a prepared service seam; the review identifies the default-off T19/T20 authoritative production dispatch route as an integration blocker. T20 must assemble the required audit sink and policy gate on the actual dispatch path, propagate preflight failure before any send, and verify outcome linkage in an end-to-end Run. T19 budget/claim ordering must retain its existing authoritative checks; a read-audit preflight must not become a substitute for budget permission or cause an unauthorized provider send on retries. Until that wiring is proven, these repairs establish seam behavior only, not production-wide audit coverage.
