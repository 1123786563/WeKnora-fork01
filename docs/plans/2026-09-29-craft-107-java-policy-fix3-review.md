## Finding

### HIGH — Shell Java launch skips `req.Environment["JDK_JAVA_OPTIONS"]`

- **Evidence:** `internal/modules/craft/input_code.go:291-322` detects Java in `req.CommandText`, rejects raw command-text `JDK_JAVA_OPTIONS=` assignments and `@argfile` shell tokens, then proceeds to the existing shell scan. It never checks `req.Environment["JDK_JAVA_OPTIONS"]`. That check exists only in the non-shell interpreter branch (`input_code.go:387-405`). The earlier generic environment scan (`input_code.go:273-288`) rejects paths inside the input tree, but a value such as `@/workspace/generated/launch.args` remains outside that tree and is not recognized as an argfile there. Thus a shell request with `CommandText: "java Main"`, generated-target evidence and `Environment: {"JDK_JAVA_OPTIONS": "@/workspace/generated/launch.args"}` can be allowed, while the real Java launcher expands the uninspectable argfile into options. Oracle's [Java 21 launcher documentation](https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html) confirms that `JDK_JAVA_OPTIONS` is prepended to launcher argv and supports `@argfile` expansion.
- **Impact:** An argfile outside the input tree can name an uploaded executable Java agent or module path; the policy cannot inspect that file at this seam. The shell route therefore retains the class of uploaded-code execution that Fix3 says it closes. It also contradicts the report's stated decision to deny non-empty `JDK_JAVA_OPTIONS` for detected Java launchers.
- **Smallest defensible correction:** Apply the exact same non-empty `req.Environment["JDK_JAVA_OPTIONS"]` check in the Java-detected shell branch before the shell form can be allowed. Add a shell request regression with generated-target evidence and non-empty environment value, asserting `interpreter_input`, plus an empty-value compatibility case.

## Scoped assessment and verdict

- Direct argv Java `@argfile` and wrapped Java forms are now rejected before the positional-operand state machine (`input_code.go:387-405`); shell quote-normalized tokens are screened (`input_code.go:291-322`). Non-shell environment and `env` wrapper assignments for Java are screened. Ordinary `-jar` and generated module path plus `-m` tests remain allowed; Fix2 module/class/patch path handling remains present. The report records focused and broader policy test passes, which this review did not rerun.
- The Fix3 plan says generated/outside-input argfiles remain allowed, whereas the report records a later fail-closed decision to reject all Java argfiles because the seam cannot inspect their content. The latter is consistent with the approved no-execution Spec but has a stated compatibility cost; the execution record should preserve this change of decision.
- **Spec compliance: FAIL.** The shell environment route above can reintroduce unreviewed Java startup options and uploaded code execution.
- **Code quality/security: FAIL.** One high-severity branch inconsistency remains. No concurrency or data-consistency issue was found in this local policy delta.
