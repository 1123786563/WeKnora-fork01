## Finding

1. **Medium — material resolution does not validate the current admitted writer fence before external work.** `CraftRunViewProductionAssembly.ResolveMaterial` (`internal/container/container.go:2747–2766`) builds its key using `task.Fence.TenantID` and `task.Scope` fields, then immediately calls `coordinator.Resolve`. It does not require `task.Fence.TenantID == task.Scope.TenantID`, a nonempty fence owner, a positive/current epoch, or a matching durable Run snapshot/actor. `CraftRunViewStore.Allocate` confirms the Run's tenant/owner/session identity (`internal/application/repository/craft_run_view.go:105–154`), but does not compare the fence epoch or snapshot. `Resolve` can allocate a generation and create/start a container and OpenCode session (`internal/container/craft_runview_runtime.go:120–194`) before `MaterialHandle` performs its later identity checks. The R5 plan calls for a *durable admitted Run*; the H3 prerequisite report explicitly requires reloading it through `AgentRunStore.Get` and validating tenant, Task/session, actor, generation and immutable snapshot. **Impact:** a stale or internally inconsistent Task can trigger sandbox/session side effects and potentially receive a handle for an otherwise valid RunView before its writer authority is proved. The existing `localCraftRuntime.admittedRunForCraftFence` guard protects some later runtime paths, but the exported assembly capability does not enforce that contract for its downstream consumer. **Smallest correction:** inject the durable Run reader into this assembly, reject inconsistent Task scope/fence and stale epoch/snapshot/actor before calling `coordinator.Resolve`, and add focused tests that require zero engine/session calls on these denials. Keep later runtime fence checks as an independent guard.

## Spec compliance verdict

**FAIL for Task 2's admitted-Run resolver contract; otherwise the scoped assembly is consistent with the plan.** `BuildContainer` registers a lazy assembly only (`container.go:485–492`); it does not enable a production route. Missing pins, including the currently null registry digest in `docker/craft/opencode.lock.json`, leave Provider and ResolveMaterial nil. The provider constructor requires a well-formed digest and an image reference ending in that digest (`craft_runview_container_provider.go:243–249`), and there is no workDir fallback in the Task 2 patch. Successful resolution delegates to the durable RunView store, coordinator and provider-issued material handle, which rechecks exact bound container/session/layout identity. The finding above prevents a PASS for the stated admitted-Run boundary. H3 integration, deployable registry digest and live R5 handoff remain later gates.
