## Findings

1. **Low — the API-key user lookup is also faked, contrary to the fixture's stated boundary.** `internal/router/craft_b5_joined_test.go:43-60,152-159` overrides both `ValidateToken` and `GetUserByTenantID`; `internal/middleware/auth.go:513` calls the latter when constructing a tenant API-key session. The real tenant and active-membership repositories are used for bearer users, and production `middleware.Auth` and the route authorizer are mounted. The test API-key identity backing user, however, always becomes `owner`, so “only credential verification is mocked” is too broad. **Impact:** API-key principal and capability denial are exercised through real Auth, but this fixture cannot detect drift in production tenant API-key backing-user lookup. **Smallest correction:** use a persisted user service for `GetUserByTenantID`, retaining a narrow `ValidateToken` adapter, or explicitly narrow the fixture/report claim. This does not invalidate the observed 403 for a chat-capable key: production Auth constructs the tenant API principal and the Craft access check still denies it.

2. **Low — the `/p/` assertion establishes the correct host and denial response, but not the cause of denial by itself.** `internal/router/craft_b5_joined_test.go:314-323` sends `Host: preview.example.test` and checks `AcceptsPreviewHost`, so the request passes the handler's host check (`internal/handler/session/craft_preview.go:116-120`) and enters `CraftPreviewService.Open`. That service checks `BrowserNavigationProtected` before token lookup (`internal/application/service/craft_preview.go:311-320`), and this fixture leaves the gate false. Yet the test uses `not-a-ticket`; if the gate were enabled, this token would also return 404 with no storage open. **Impact:** the configured-host path is now covered, while this single response is not a regression detector for fail-closed preview capability handling. **Smallest correction:** retain the disabled issue-route assertions and current source/config gate evidence; when T14 enables the production gate, add the planned valid ticket/capability, revoke and byte assertions. If a stand-alone disabled-gate regression assertion is desired earlier, exercise a known issued grant through a focused service fixture without claiming that it proves production browser isolation.
