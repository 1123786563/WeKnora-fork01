# 08｜开发执行说明

## 1. 启动顺序

先执行MP00-T01-01固定当前源码和原基线差异；再并行进行版本/环境、共享导出、权限、支付资格和设计系统。身份与任务查询可在契约冻结后并行；页面可用本包fixture先开发，但必须等待真实接口完成联调验收。

任务调度依赖`tasks/task-index.json`，不要只按文件名前后顺序。波次是拓扑深度，不是周、日期或人天。领取任务前检查硬依赖和锁；共享根配置、锁文件、ports、client与router只能由指定集成人合并。

## 2. 交给单任务代码Agent的提示词

```text
在1123786563/WeKnora-fork01中执行指定任务，任务编号由调度者提供。
先读取：README、对应tasks/<任务编号>.md、相关详细设计、页面developer-mapping，以及依赖任务的已合并证据。
先核对当前HEAD与基线；若路径/接口不同，记录差异并提出最小兼容方案，不把建议字段假装成已有字段。
输出本次实际文件范围、Consumes/Produces、需要的文件锁和失败测试场景；领取锁后再改代码。
保持平台Go为账号、租户、权限、任务、预算、订单和权益的真值。
Taro API只在platform层；共享contracts/domain不得反向依赖Taro、DOM或RN。
从tokens生成样式；依据对应高保真页面实现Taro组件，不使用整页截图或WebView代替。
先添加能证明目标行为的失败测试，再实现；运行任务测试、同模块回归和受影响端构建。
未知网络结果先对账原request_id/order_id；不能用重建业务意图修复界面状态。
不得把demo账号、价格、余额、模拟付款/审批开关带进生产。
不得修改其他任务持有的文件；确需共享接口变更先交集成人评审。
交付：修改文件、合同变化、测试命令/退出码/日志、截图、风险、PR与合并提交。
没有真实测试与合并证据时不得把任务标为verified或merged。
```

## 3. 接口变更请求

请求必须包括调用者、旧行为、新字段/签名、兼容方式、受影响页面/任务、所需迁移、回归样例和回滚策略。交易类合同不允许用`any`强转掩盖缺失；微信支付参数只在资格和实际官方版本确认后由对应provider登记。

## 4. 评审与台账

每个PR评审两个方面：是否符合任务/权限/契约，以及是否达到UI/状态/测试质量。检查已有Web/Expo是否被共享修改影响；不能以小程序能跑为由忽略其他端。

台账状态planned → ready → in_progress → review → verified → merged。blocked应记录原因、阻塞依赖与负责人。一个任务一组最小可审查提交，不将未经授权的商户或微信操作夹在代码PR中。

## 5. 设计还原

先复用tokens与原子组件，再实现业务卡片和页面。核对本次原型的主要层级、间距、文字与状态，真实微信胶囊、安全区与键盘用运行时尺寸替代视觉占位。允许为真实平台行为调整布局，但修改需回写页面规格并更新截图基线。
