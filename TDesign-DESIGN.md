# TDesign Web / Desktop Design System

## Overview

TDesign Web / Desktop is a restrained, efficient enterprise language for dashboards, operations consoles, data administration, forms, workflow tools, and other middle/back-office products. Its official values—**inclusive, diverse, evolving, and connected**—do not mean decorative variety. They mean a stable shared foundation that can serve different businesses, remain usable in complex scenarios, and still leave controlled room for product identity.

The default visual character is professional, neutral, compact, and information-first. Use Tencent Blue to make interaction legible; use typography, alignment, spacing, and neutral surfaces to carry most hierarchy. Prefer predictable task completion over marketing-page spectacle. Do not transfer gradients, oversized display type, illustration treatments, or campaign layouts from TDesign's own promotional pages into general application UI.

This document distinguishes three kinds of guidance:

- **Official fact** is directly stated in TDesign design guidance or implemented semantic tokens.
- **Source-derived mapping** translates official TDesign CSS/Less tokens into the flat Google DESIGN.md alpha schema.
- **Conservative convention** fills a required field without claiming a new TDesign rule; such cases are called out explicitly.

## Colors

Use semantic roles, never raw palette steps, in application code. TDesign's own contributor guidance explains why: the light and dark themes can map the same semantic role to different palette steps. The YAML values above are the resolved defaults from `tdesign-common` and are normative for this file.

### Light theme

- **Brand interaction:** `{colors.primary}` is the default actionable blue. Use `{colors.primary-hover}`, `{colors.primary-active}`, `{colors.primary-focus}`, and `{colors.primary-disabled}` only for their named states. `{colors.primary-light}` is a selected or highlighted background, not a second CTA color.
- **Functional semantics:** success, warning, and error communicate outcomes or risk. Pair strong semantic foregrounds with their `*-light` backgrounds for tags, alerts, validation, and status summaries. Never use these colors merely to decorate categories.
- **Text:** `{colors.text-primary}` is the default for titles and body; `{colors.text-secondary}` is metadata or supporting copy; `{colors.text-placeholder}` is placeholder/explanatory text; `{colors.text-disabled}` is only for unavailable content. Links use `{colors.text-link}` and interactive brand text uses `{colors.text-brand}`.
- **Layers:** `{colors.page}` is the application canvas, `{colors.container}` is the main content surface, and container/component state colors create restrained interaction feedback. `{colors.border-subtle}` separates regions; `{colors.border-default}` defines controls.

### Dark theme

When `theme-mode="dark"`, replace each light role with the matching `dark-*` role; do not invert colors mechanically. The implemented dark theme deliberately shifts brand steps and neutral layers: page `#181818`, container `#242424`, then progressively lighter hover/active/selected layers. Preserve the same semantic hierarchy and use softened, lower-saturation colors to reduce visual vibration.

Dark text follows TDesign's four alpha levels: 90%, 55%, 35%, and 22% white. Recheck real foreground/background pairs at implementation time. TDesign calls for at least WCAG 2.0 AA 4.5:1 for normal text; a token's presence does not prove every composition is accessible. Disabled state must also be communicated by affordance, cursor, label, or control behavior—not color alone.

## Typography

The desktop default is `{typography.body-medium}`: 14px/22px, weight 400. The official core rule is a compact `font-size + 8px` line-height relationship for the common range. TDesign limits the regular hierarchy to weights 400 and 600 so Windows and macOS remain visually consistent.

- **Page title:** use `{typography.headline-small}` (24/32, 600) for a primary workspace heading. Reserve larger headline tokens for overview dashboards or exceptional display moments, not routine forms and tables.
- **Module title:** use `{typography.title-medium}` (16/24, 600); use `title-small` for dense cards and `title-large` for major sections.
- **Body and control labels:** use `{typography.body-medium}`. Use `body-small` for secondary metadata, helper text, and dense table supplements; never shrink desktop UI below the official 12px minimum.
- **Emphasis:** use the matching label token at weight 600 before adding a new color. Avoid a third ad-hoc weight.
- **Numeric information:** use `{typography.data-medium}` or enable tabular figures for aligned metrics and tables. TCloud Number is an official downloadable resource, but the monospace fallbacks keep the intent when it is unavailable.

Every typography token includes `letterSpacing: 0em` as a **conservative format-completion convention**. Current public TDesign Web tokens do not publish role-specific tracking; do not introduce tight or expanded tracking without product evidence.

## Layout

Build application frames from Header, Sider, Content, and optional Footer. Choose the navigation model by information architecture:

- **Top navigation:** for fewer, weakly related modules and maximum horizontal content area. TDesign's middle/back-office guide suggests top-level navigation generally fits fewer than nine modules.
- **Side navigation:** for many related modules and frequent switching. Use `{spacing.sider-expanded}` (232px) and `{spacing.sider-collapsed}` (64px).
- **Mixed navigation:** for complex parent/child or cross-cutting structures. Keep global domains in the header and local structure in the sider; do not duplicate the same level in both.

Use a 12-column content grid. The official base unit is 8px, with a 16px gutter and 24px minimum safe page margin. Place blocks from column boundary to column boundary. The 4px and 12px steps are official exceptions for compact internal spacing; 2px and 6px exist in the implementation size scale for fine component geometry, not broad layout.

For a typical desktop page: page header to main content 24px; major sections 24–32px; card padding 16–24px; control-to-control gaps 8–16px; icon-to-label gaps 8px. These combinations are source-derived from the semantic size and component tokens. Do not create arbitrary 5px, 10px, 18px, or 30px gaps when a declared step fits.

TDesign's official design canvases are 1440px or 1920px. They are design references, not fixed viewport requirements. Keep data-heavy content fluid, and use an intentional max width only when reading stability matters.

## Elevation & Depth

TDesign is primarily layered through surface tone and borders; shadows identify actual elevation. Do not put a shadow on every card.

- **Level 0:** page, containers, cards, and ordinary controls use surface contrast and 1px borders only.
- **Level 1:** hover-lifted tables or low overlays use the official light shadow `0 1px 10px rgba(0,0,0,.05), 0 4px 5px rgba(0,0,0,.08), 0 2px 4px -1px rgba(0,0,0,.12)`.
- **Level 2:** dropdowns, selectors, popovers, and drawers use `0 3px 14px 2px rgba(0,0,0,.05), 0 8px 10px 1px rgba(0,0,0,.06), 0 5px 5px -3px rgba(0,0,0,.10)`.
- **Level 3:** global messages and notifications use `0 6px 30px 5px rgba(0,0,0,.05), 0 16px 24px 2px rgba(0,0,0,.04), 0 8px 10px -5px rgba(0,0,0,.08)`.

Dark mode has stronger official shadow values because the surfaces are darker; do not reuse light shadows unchanged. Because Google DESIGN.md alpha has no top-level shadow-token group, these verified values live in prose rather than an invented YAML group.

## Shapes

The shape language is compact and engineered. The default control radius is `{rounded.default}` (3px), not a large consumer-app pill. Use `{rounded.small}` for small internal pieces, `{rounded.medium}` for cards/dialogs/messages, and 9–12px only where the component source explicitly uses a larger container. Use `{rounded.round}` only for intentional pills or fully rounded controls.

Icons should come from TDesign Icons. Official icon guidance uses a 24×24 authoring grid, a centered 20×20 live area, and commonly delivers 16×16 in UI. Align strokes to integer pixels. Preserve optical balance when geometric centering conflicts with visual centering. Rounded icon corners should support meaning; do not round every angle indiscriminately.

## Motion

Motion must improve understanding, guide focus, or preserve spatial continuity. If deleting an animation leaves the task equally clear, prefer the static result. Never sequence an entire enterprise page on first load; use a skeleton or a restrained fade when feedback is necessary.

Official system durations are:

| Context | Base | Moderate | Slow |
| --- | ---: | ---: | ---: |
| Mobile / tablet | 100ms — micro change or fade | 120ms — collapse, popup, message | 140ms — selector, menu, drawer, tab, overlay |
| Desktop / laptop | 200ms — micro change or fade | 240ms — anchor, tab, menu, list/tree response | 280ms — drawer, notification, global message |

Use standard `cubic-bezier(.38,0,.24,1)` for movement inside the frame, `cubic-bezier(0,0,.15,1)` for entry, and `cubic-bezier(.82,0,1,.9)` for exit. Use linear only for a fast fade synchronized with another movement. Axis movement expresses spatial relation, container transformation expresses shared-container continuity, and fade expresses a transition without spatial/container relation.

**100ms** is the official mobile base and the threshold of basic motion recognition in TDesign's guidance. **200ms** is the desktop base. **300ms is not an official system duration token**: current Web component CSS contains isolated 300ms transitions, while the canonical desktop slow token is 280ms. Do not normalize the system to 300ms; use it only when matching an existing component implementation or a documented product convention.

Respect `prefers-reduced-motion`: remove nonessential translation/scale, retain immediate state changes, and keep necessary feedback short and non-looping. This accessibility behavior is a conservative implementation convention; the public motion page does not publish a reduced-motion token.

## Components

The YAML component entries are source-derived mappings of `tdesign-common` variables. For unlisted variants, compose declared global tokens rather than inventing color or geometry.

### Buttons

Default height is 32px; supported compact and large sizes are 24px and 40px. Use one primary action per task region. Secondary outlined/default buttons use the container and border roles; text buttons are for low-emphasis actions. Destructive actions use error semantics and require explicit copy or confirmation when irreversible. Hover, active, focus, and disabled must match their dedicated entries; focus includes a visible 2px semantic ring rather than relying on color change alone.

### Inputs and selection controls

Inputs and selects are 32px by default with 3px corners, 14px body type, an explicit 1px border, and 8px horizontal padding. Hover and focus use brand border; focus adds a 2px focus-color ring. Error uses error border, helper text, and ring. Disabled controls use disabled surface/text and must not accept interaction. Checkbox and radio marks are 16px; selected, indeterminate, disabled, and keyboard-focus states must remain distinguishable.

### Navigation and cards

Navigation uses secondary text by default, neutral hover, and a light brand background plus brand text for selection. A selected item is a location, not another primary button. Cards use 6px corners, 16–24px internal padding, a container background, and at most a subtle border. Add elevation only when a card actually moves above its siblings.

### Tables

Tables are dense work surfaces: 14px/22px body, 16px horizontal cell padding, and semantic row backgrounds for hover and selection. Use placeholder-level header text only when contrast remains sufficient; use 600 weight where stronger hierarchy is needed. Align numeric columns right and enable tabular figures. Keep sorting, filtering, selection, empty, loading, error, and pagination states visible without changing column geometry. Do not encode status by color alone.

### Tabs, pagination, and tags

Tabs use secondary text by default and brand text/indicator when selected; disabled tabs remain visible but unavailable. Pagination uses 32px controls (24px small), a brand-filled current item, and dedicated hover/disabled states. Tags are 24px by default (20px small, 32px large). Use semantic light tags for status and pill rounding only for explicitly rounded tags; do not turn every label into a colorful badge.

### Dialogs, drawers, dropdowns, and feedback

Default dialog width is 480px with 32px outer padding and a 6px radius. Use dialogs for blocking decisions and short focused tasks; do not place full application pages inside them. Default drawer width is 300px with 16px padding; drawers preserve parent context for supplementary or longer tasks. Dropdown items use 28px height and Level 2 elevation.

Messages and notifications use container surfaces, semantic icons, 6px corners, and elevated placement. Messages communicate brief global feedback; notifications support richer content. Errors must state what failed and how to recover. Success feedback should be concise and should not block continued work.

### High-frequency enterprise compositions

- **Dashboard:** summary hierarchy first; filters are compact; charts use TDesign/TVision semantics rather than arbitrary brand colors.
- **List page:** search/filter region → primary/batch actions → table/list → pagination. Preserve filter state and show selection count during batch operations.
- **Form page:** group by task, align labels consistently, place helper/error text near the field, and keep the primary submit action predictable.
- **Detail page:** lead with identity and status, then structured descriptions, related records, and state-transition actions.
- **Result/onboarding/import flows:** expose progress, outcome, next action, and recovery. Choose blocking dialogs only when the user must read or decide before continuing.

## Do's and Don'ts

### Do

- Do use semantic tokens and component variants; theme switching depends on semantic roles.
- Do keep the 8px layout rhythm, using 4px/12px only for compact needs and 2px/6px for verified component geometry.
- Do build hierarchy with type, spacing, alignment, and neutral layers before adding color or shadow.
- Do preserve visible hover, active, focus, selected, disabled, loading, empty, and error states.
- Do keep normal text at WCAG AA contrast or better and retest every real foreground/background pair.
- Do use 400/600 weights, 14px desktop body, and tabular figures for scannable numeric data.
- Do select top, side, or mixed navigation from module count and relationship, not from fashion.

### Don't

- Don't replace the default 3px control radius with 8–16px rounded consumer-app geometry.
- Don't use pills for ordinary buttons, inputs, cards, table rows, or navigation containers.
- Don't create gradients, glassmorphism, neon glows, oversized hero type, or floating decorative blobs in enterprise workflows.
- Don't make every card elevated, every status saturated, or every action Tencent Blue.
- Don't use raw palette steps where a semantic role exists, and don't assume light/dark roles use the same step.
- Don't shrink desktop text below 12px or create unverified font weights and tracking.
- Don't animate all page content on load, exceed the official duration ranges without evidence, or use elastic motion for standard UI.
- Don't guess dimensions from TDesign screenshots or promote marketing-page CSS into reusable application rules.

## Responsive Behavior

TDesign's published Web layout is desktop-first. Apply these official thresholds before adding product-specific ones:

- **≥ 992px:** side navigation may remain expanded at 232px; content uses a fluid 12-column grid with 16px gutters and at least 24px page margins.
- **768–991px:** collapse the sider to 64px by default. Keep the 12-column grid fluid, reduce nonessential horizontal density, and move secondary actions into overflow menus.
- **< 768px:** the official fixed desktop grid otherwise reaches its minimum and may scroll horizontally; for a genuinely responsive product, treat this as a product adaptation: move the sider to an overlay/drawer, stack form and card columns, allow tables to scroll or switch to a designed record list, and keep task-critical actions reachable.

Tablet and mobile motion uses 100/120/140ms rather than desktop 200/240/280ms. Do not merely scale the desktop canvas. Preserve content priority, touch target usability, and reading order while collapsing secondary navigation and density.

In dark mode, retain the same layout, information priority, and component state model. Change semantic colors and shadows, not hierarchy. Never flatten page, container, hover, active, and overlay surfaces into a single black plane.

## Iteration Guide

1. Read this file before generating or changing UI; treat YAML values as normative and prose as application logic.
2. Reuse an existing semantic token or component variant. If none fits, locate a first-party TDesign semantic token or component variable before adding one.
3. Add each new interactive state as a separately named component entry such as `component-hover`, `component-active`, or `component-error`; do not hide state values in prose alone.
4. Keep light and dark semantic mappings paired. Verify contrast in the actual composition, including disabled and focus states.
5. Record source URL/file, platform, and selection rationale when official site guidance, common tokens, and framework implementation diverge.
6. Keep product-specific branding in a controlled override layer; do not mutate base spacing, type hierarchy, and component geometry casually.
7. Run `npx @google/design.md lint ./TDesign-DESIGN.md`, resolve every error and broken reference, then review warnings before merging.
8. Recheck the official source when `@google/design.md` leaves alpha or TDesign theme/component tokens change.

## Known Gaps

- **Font-family conflict:** the TDesign typography page publishes a broad cross-platform Web stack, while current `tdesign-common/_font.less` uses `PingFang SC, Microsoft YaHei, Arial Regular` and a separate medium family. This file chooses the broader official design-page stack for agent portability; teams matching a specific framework build should inspect its emitted CSS.
- **Letter spacing:** no role-specific tracking tokens were found in the reviewed public Web theme. `0em` is a conservative schema-completion convention, not a new official TDesign measurement.
- **Breakpoints below 768px:** the official Web layout page specifies desktop behavior and a 768px minimum more clearly than native mobile reflow. The `<768px` rules above are conservative product guidance and require designer validation for each application.
- **300ms motion:** the system motion page defines desktop 200/240/280ms. Isolated component CSS uses 300ms; there is no evidence for a general 300ms token. Confirm before standardizing it.
- **Shadow serialization:** Google DESIGN.md alpha has no top-level elevation token group. Exact official shadows are documented in prose, so consumers must map them into their local CSS token format.
- **Data visualization:** the official color page points to TVision and extension palettes but the reviewed public material does not provide a complete stable chart-token contract suitable for this frontmatter. Do not invent chart series colors.
- **Accessibility coverage:** TDesign documents WCAG 2.0 AA text contrast, but the current Google linter cannot prove all non-text contrast, forced-colors behavior, target size, screen-reader semantics, or keyboard flows. Validate these in implementation.
- **Framework drift:** TDesign React/Vue component APIs and component-local variables can change independently of `tdesign-common`. This file captures the common Web semantic layer and verified shared component variables, not every framework prop or one-off override.
