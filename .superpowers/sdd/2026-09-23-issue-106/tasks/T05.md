## OCR 分流记录（2026-09-24，任务级增量 OCR）

报告：`docs/plans/issue-106-ocr-T05.md`。发现 1 条 medium（T05-OCR1-F2），经
systematic-debugging 四阶段核验后分流：

**OCR-REJECT: T05-OCR1-F2**（误报——按报告自己的验收口径「不修改，声明理由
与代码证据」处理；生产代码零改动，仅补回归钉子）：

- **主张**：Client.Timeout 先于整体 ctx deadline 触发时，net/http 返回不实现
  Unwrap 的 *httpError，errors.Is(err, context.DeadlineExceeded) 为 false，
  真实超时落入 jira.go 的 failed 分支、不含小写 timeout。
- **Phase 1 复现（探针，go1.26.3 darwin/arm64，真实
  `utils.NewSSRFSafeHTTPClient` + sleep 400ms httptest）**：Client.Timeout(150ms)
  先触发时错误为 `Get "http://127.0.0.1:PORT": net/http: request canceled
  (Client.Timeout exceeded while awaiting headers)`，且
  **`errors.Is(err, context.DeadlineExceeded) == true`**、`os.IsTimeout(err) == true`
  ——与主张的 false 相反；报告引用的 "context deadline exceeded (Client.Timeout
  ...)" 文本在本工具链上不出现（该形态属 Go 1.23 之前 *httpError 无 Is/Unwrap
  的旧行为；仓库 go.mod 要求 go 1.26，实测 go1.26.3）。
- **stdlib 事实源**：go1.26.3 `$GOROOT/src/net/http/transport.go:2768-2775`，
  `type timeoutError` 明确实现 `func (e *timeoutError) Is(err error) bool
  { return err == context.DeadlineExceeded }`（类型注释 "implements net.Error and
  wraps context.DeadlineExceeded"）；`client.go:737` 将 Client.Timeout 的
  awaiting-headers 错误包成该类型——两条超时触发顺序都命中 jira.go:154 的
  `errors.Is` 分支并带 timeout 措辞浮出。
- **回归钉子（Phase 4）**：`TestJiraErrorsSurfaceWithoutFabrication/jira-client-timeout`
  换入 150ms Timeout 的同款 SSRF-safe client（`maxToolCallTimeout` 保持默认 60s，
  页级必然先触发），断言错误含 "timeout"、result 为 nil——**对未改动的 jira.go
  即 PASS**（运行证据见下节），现状已覆盖该路径；未来 Go 版本漂移破坏此语义时
  该测试先红。
- 附注：os.IsTimeout 对 `*url.Error` 直接类型断言不逐层 Unwrap——本仓 SSRF-safe
  client 即裸 `*http.Client`（security.go:798→781-792，RoundTripper 原样透传
  传输错误），故即便采纳建议亦无额外覆盖面；不改。
