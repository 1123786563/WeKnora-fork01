## Rulings（按任务书要求记录；模型路由 Ruling 见下）

- **R1（前端范围）**：计划「`require_approval` 开关——与 T18 enabled 开关同行」预设 T18 已交付前端治理面，但 T18 Brief 所有权纯后端、`plugins.ts`/面板当时无任何治理面代码。Ruling：T19 前端交付**补全整条治理行**（API 客户端 GET tools/PUT policy + 面板 enabled 与审批双开关同行）——审批开关无法脱离治理行独立存在，Spec US22 要求配置面完整。代价：T19 前端 diff 比字面预期大（含 enabled 开关），但这是最小完整交付。
- **R2（二次 Resolve 断言）**：Brief 说「二次 Resolve 被拒」未定状态码。`awaitCall` 后 waiter 已被 `RequestAndWait` 的 defer 删除 → 确定性 `ErrPendingNotFound` → 404（"not found or already completed"）。Ruling：断言 404 而非 400（400 是删除前竞态窗口的 already-resolved 面；两者都是拒绝）。代价：若未来 Gate 改为持久 waiter（如 DurableGate 路径），此断言需随语义更新。
- **R3（停用文案口径）**：停用工具经 `ToolCallMCPTool` 的旧 ref 调用，拒绝发生在 ref 解析层（"no longer available or enabled"）而非 `MCPTool.Execute` 的 "MCP tool is disabled"。Ruling：断言 `Contains "enabled"`（两层文案都含，与 T18 describe 断言同口径）。代价：若文案重构去掉 "enabled" 字样需同步。
- **R4（测试 harness 错误面）**：直调 `ResolveToolApproval` 必须挂 `middleware.ErrorHandler()`（router.go:173 生产同款），否则 `c.Error` 不写状态码、4xx 面失真（RED 阶段实测 200）。Ruling：harness 补挂而非改断言。代价：无——更接近生产 HTTP 语义。
- **R5（停用插件断言面）**：停用安装后无 Enabled 服务在场时 `discover_mcp_tools` 也不注册（"tool not found"），describe 断言不可用。Ruling：改断言 `ListEnabled` 空 + 旧 ref 在新会话 `ExecuteTool` 报错 + 零写计数。代价：断言经仓储面而非目录面，仍覆盖「停用后不可达零派发」。
