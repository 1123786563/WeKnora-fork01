## Z3 — Order lifecycle: same-ID polling, at-most-once createOrder, retry semantics — PASS

- **orderId prop path never creates.** CheckoutPage.tsx:53-59 — if `orderIdRef.current` is non-empty the effect does ONE getOrder and returns before the quote/create block. `orderIdRef` is initialized from the prop (40) and never overwritten from outside.
- **refreshOrder queries only the current order.** 91-95: reads `orderIdRef.current`, early-returns when empty (93), calls only `client.commercial.getOrder(id, …)`. There is no createOrder call anywhere outside the one guarded site (70). Polling (111-115) invokes only refreshOrder and stops at `isTerminal` (24-26: fulfilled or closed).
- **At-most-once per idempotency key, within a mount — verified on the retry path.** The key is generated only `if (!idempotencyKeyRef.current)` (67-69) and never reset; the retry button (134) bumps `retryToken` which re-runs the effect, but refs persist across effect re-runs, so the re-run skips the quote (60-66) and reuses the SAME key at createOrder (71). Lost createOrder response (server committed, client saw an error) → retry sends the identical key → backend dedupe returns the original order instead of charging twice. That is exactly the claimed behavior and the code supports it. Error-before-quote retry: key still '' → fresh generation — safe, since no createOrder was attempted.
- **Polling never re-creates.** The interval effect (111-115) depends on `[refreshOrder, order?.id, order?.payment, order?.fulfillment]` — it only ever re-reads state-derived fields and calls refreshOrder; createOrder is reachable only from the load effect, and only when `orderIdRef.current` is empty (53), i.e. at most once per mount before the first successful create sets it (75).
- **Honest cross-remount note (implementer's claim was scoped to "within the same mount" — accurate).** Refs die with the component: a FULL unmount+remount with an empty orderId prop generates a NEW key and would create a second order. The created orderId is not persisted anywhere (no callback/storage) — fine today because the page is only re-exported (App.tsx:59), but whoever wires it into navigation must persist the orderId before a remount can occur. Flagged as Improvement #2, not blocking: the brief's double-purchase boundary (错误重试不重复购买) is the retry path, which is correct.
- **Exotic scope-switch-mid-create edge, honestly noted:** if scope switches while createOrder is in flight and the aborted call never sets `orderIdRef`, the re-run under the new scope reuses the same quote/key (refs are not scope-keyed) — still exactly one order per key (no double charge, idempotency holds), but the ready view could render the old tenant's order under the new scope's space label. Display-only mislabel in a rare path; see Improvement #5.
