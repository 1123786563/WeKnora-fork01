## AC2 — Approval integrity: digest binding, edit→new digest, conflict handling — PASS

- **Approve submits id+digest+expected_version.** ActionApproval.tsx:78-81: `approveAction(detail.action.id, { digest: detail.action.digest, expected_version: detail.expected_version })` — both values come from the last server response (getAction/prepareAction/approveAction), never from local edits; the id rides the path. api-client body is exactly `{ digest, expected_version }` (appconnector.ts approveAction; asserted `assert.deepEqual(seen[0].body, { digest: 'd1', expected_version: 0 })`).

Server-side second wall: ApproveAction (app_connector.go) rejects `row.ArgsDigest != input.Digest` → 409 ACTION_DIGEST_MISMATCH "the approval was issued for different content; prepare the new content again", and stale fence → 409 ACTION_VERSION_CONFLICT; the A03 service re-checks digest and state itself (service action.go:190-195, SaveApproval CAS + conditional SetActionState awaiting→authorized :196-201), so even a TOCTOU race between handler read and service write is caught inside the service. - **Conflict handling surfaces typed.** api-client test 'action envelope errors are typed ApiErrors' feeds `{success:false, error:{code:'ACTION_DIGEST_MISMATCH'}}` and asserts `error instanceof ApiError` with `.code === 'ACTION_DIGEST_MISMATCH'`; the React side renders the thrown message in a Status tone="error" (ActionApproval.tsx:88,108,137) and keeps the server snapshot on screen — no state mutation on failure.

## Improvements (non-blocking)

1. **TaskBudget used/held go stale if the host re-renders with a new snapshot prop** (TaskBudget.tsx:30-31: `const [used] = useState(snapshot?.used)` captures the initial value; only limit is updated, and only locally after extend). Fine for the current inject-once seam; derive from props (or sync on prop change) once a live task-detail host exists.
2. **NewBudgetService is constructed per request** (commercial_task_budget.go: NewBudgetService on every extend call) — which also runs `db.AutoMigrate` each time. Correct but wasteful; wire one service in the container alongside SetActionService-style injection when the entitlement check lands.
3. **Container never calls SetActionService**, so prepare/approve/execute are 501 in this environment (disclosed). When wiring, remember the handler also needs the service's approval TTL/guard deps configured — and consider wiring the entitlement check into the budget service in the same pass (currently nil = allow, disclosed in the handler comment).
4. **No AbortSignal on mount-time load in ActionApproval** (client.apps.getAction(id) without signal) — the activeRef guard already prevents stale setState; a signal would also cancel the request itself on unmount/space switch, matching the W02/W04 page pattern.
5. **extendTaskBudget lives on the `apps` api namespace** (client.apps.extendTaskBudget) although the endpoint is commercial-routed and commercial-group-gated. Path is asserted exact so behavior is right; a commercial namespace (or a shared re-export) would read cleaner.
6. **Panel requires both taskId and actionId as required props** (TaskDetailCommercePanel.tsx:9-10) — a task with no pending action forces the host to fabricate an id; making actionId optional (render budget-only when absent) would fit real task-detail states better.
7. **Re-approve is offered in state authorized** (ActionApproval.tsx:173-175) — matches the service's idempotent re-approval (refreshes TTL, service action.go:193 allows authorized), but the button copy could say 续期/重新确认 to avoid implying a second approval is needed.
