## Finding

### FR1-R2-1 — Low — Broad framework substring rejects a valid non-framework dylib name

- **Evidence:** The new fallback at `verify-ios-framework-closure.py:91` checks `if ".framework" in load` without requiring a `.framework` path component. `@rpath/Foo.framework.dylib` names a dylib file, not a framework bundle, yet the production checker returned exit 1 with `UNSUPPORTED_FRAMEWORK_LOAD_PATH: WeKnora.app: @rpath/Foo.framework.dylib` in a disposable fixture. Earlier checker behavior skipped non-framework dylib loads; the FR1 brief scopes this closure guard to framework dependencies. This is a false rejection, not a false closure success.
- **Impact:** A future valid Release app using such a dylib basename could be blocked by the framework gate. The retained app has no reported instance, and current R4/FR1 framework acceptance is unaffected.
- **Smallest correction:** Recognize `.framework` only as a complete path component (followed by `/` or end of load token); keep malformed framework detection and unknown framework-token rejection. A positive non-framework dylib fixture would pin the boundary.
