## Findings

### T31-F1 — Medium — Release framework gate falsely accepts a missing non-system framework

`apps/mobile/scripts/verify-ios-framework-closure.py:77-86` only recognizes loads matching `@rpath/<name>.framework/<path>`. A Mach-O executable or embedded framework can also name a bundled framework through `@loader_path` or `@executable_path`; those load commands are silently skipped. The Release entry point invokes this checker after the build (`apps/mobile/scripts/ios-release-build.sh:65`), and the R4 plan explicitly calls for complete non-system framework closure and a fail-closed production guard.

I exercised the checked-in checker, without modifying the repository, on a temporary `.app` fixture with `CFBundleExecutable=WeKnora`, valid source-mode properties and fake `otool -L` output containing `@loader_path/Frameworks/Missing.framework/Missing`. The framework was absent. The command exited **0** and printed `FRAMEWORK_MODE=source-expo-modules` and `FRAMEWORK_CLOSURE_OK`. This is a direct false pass for the promised gate. The fixture tests in `apps/mobile/src/ios-framework-closure.test.ts:44-159` cover only `@rpath` dependency forms, so they do not catch it.

Impact: a future clean Release build with a missing framework loaded by `@loader_path` or `@executable_path` can be certified by this gate and then fail at launch. The retained T31 executable's observed framework loads use `@rpath`, and the installed simulator app launched; this finding does **not** assert that the current binary has an unresolved load. The smallest repair is to classify and resolve all supported non-system Mach-O load path forms relative to the owner/app executable, fail on unknown non-system forms, and run the production checker in positive and missing-dependency fixtures for each form. Recheck the retained Release artifact and any affected native build evidence after changing the gate.
